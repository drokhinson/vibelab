# Database migrations

One shared Supabase project backs every app in this monorepo. Migrations are
organized **per app** under this directory, plus a `_shared/` subdirectory for
cross-app concerns (analytics, admin RPCs, project roles).

## Layout

```
db/migrations/
  _shared/        cross-app: analytics, admin RPCs, project roles
  <app>/          one subdirectory per app (sauceboss, plantplanner, …)
    001_baseline.sql   tables + indexes + RLS + grants + RPCs
    002_seed.sql       reference data (optional; some apps have none)
    003_<desc>.sql     future migrations, per-app counter
    archive/           a collapsed history, kept for reference, never run
```

The schema-final form for each app also lives in `db/schema/<app>.sql` as a
read-only snapshot. Snapshot stays in sync with the latest migration —
update it whenever a migration changes table shape.

## BoardgameBuddy is not here

**`projects/boardgame-buddy/db/migrations/`** holds its migrations, and
`projects/boardgame-buddy/db/{schema,functions}/` its snapshots. There is no
`boardgamebuddy/` subdirectory under this one, and no
`db/schema/boardgamebuddy.sql` — that project was isolated into its own tree,
with its own API service and its own deploy workflows. See
`projects/boardgame-buddy/CLAUDE.md`.

What did **not** move is the database. One Supabase project still backs every
app including that one, so:

* `_shared/003_project_roles.sql` here still registers `boardgamebuddy_role`
  against the `boardgamebuddy_` table prefix. It is the authority on those
  grants; the project's own tree has no copy of it.
* `_shared/001_analytics.sql` and `_shared/004_api_logs.sql` are duplicated
  **byte-identically** into that project's own `_shared/`, so it can stand up
  a database without this directory. Both are `IF NOT EXISTS` throughout, so
  running one after the other is a no-op rather than a conflict. Change one
  and change the other.

Its layout differs in two ways worth knowing before reading it. The baseline is
split three ways — `001_baseline.sql` (structure), `002_seed.sql` (data),
`003_rpcs.sql` (functions) — because 48 RPCs in one baseline was unreadable.
And its counter has run well past `004`: check the directory for the next
number rather than trusting any number written down here.

## Execution order on a fresh DB

Run per-app baselines first, then `_shared/` last so the project-roles
migration can `GRANT SELECT` on tables that already exist and `REVOKE EXECUTE`
on app-defined RPCs.

```
db/migrations/<app>/001_baseline.sql   (every app under THIS directory)
db/migrations/<app>/002_seed.sql       (where present)
db/migrations/_shared/001_analytics.sql
db/migrations/_shared/002_admin_rpcs.sql
db/migrations/_shared/003_project_roles.sql
```

To include BoardgameBuddy, run its own tree's `001_baseline.sql`,
`002_seed.sql` and `003_rpcs.sql` (in that order) with the other per-app
baselines, **before** `_shared/003_project_roles.sql`. Getting that order
wrong does not error, which is the problem: that migration grants SELECT by
looping over the tables that exist *at the time it runs*, so an empty prefix
means `boardgamebuddy_role` is created with no table grants and nothing says
so. Skip its `_shared/` copies; the ones here are the same files.

Within an app subdirectory, run files in numeric order. **Skip `archive/`** —
those files are superseded history and re-running them would replay drops and
renames against a schema that has already moved past them.

## Production state

Production was migrated from a flat layout (`001_…sql` … `064_…sql`) on
2026-05-01. The pre-consolidation HEAD is tagged `pre-migration-consolidation`
for recovery — note the tag is not in a default clone, so treat it as gone
unless someone fetches it deliberately.

BoardgameBuddy was collapsed a second time on 2026-09-01, from 73 files to
three, with the history committed to its own
`projects/boardgame-buddy/db/migrations/archive/` rather than left in a tag.
The collapsed files were generated by replaying all 73 archived migrations
into an empty Postgres and reading the end state back, then verified
by diffing a database built from the three files against that replay —
`pg_dump --schema-only`, every function body via `pg_get_functiondef()`, and
row-level checks on the reference tables all come back identical.

Consolidated baselines reproduce the production end state when run against an
empty DB — they are **not** re-run on the live database.

## Adding a new migration

1. Pick the next number for the app by listing its directory —
   `db/migrations/<app>/NNN_<desc>.sql`, or
   `projects/boardgame-buddy/db/migrations/NNN_<desc>.sql` for that one.
2. Run the SQL in Supabase Dashboard → SQL Editor → New Query.
3. Update `db/schema/<app>.sql` if table shape changed (BoardgameBuddy's is
   `projects/boardgame-buddy/db/schema/boardgamebuddy.sql`).
4. Commit the migration + snapshot together.

**Nothing tracks which files have run** — there is no migrations table and no
runner, only step 2 and a human. Two consequences. A migration must be safe to
apply to the live schema as it stands, not merely correct in sequence. And the
numbers carry no state, so a pair that cancels out (a create and its later
drop) can be deleted and the rest renumbered once both are applied — the
contract to keep is that a fresh database replays to the production end state.

See `.claude/rules/database-supabase.md` for RLS, grant, and naming conventions.
