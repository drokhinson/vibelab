The note you wrote, and the way to say nice

Two things the feed card's front face does not do. It never shows the note — ui/play-card.js:265 says outright that "notes live exclusively on the back", so the one line a person actually typed costs a tap and a round trip to read. And there is no way to answer a play at all: grep the migrations, the routes package and every file under web/ for kudos|like|reaction|comment and you get nothing. A buddy's game night scrolls past in silence.

The card's geometry is not up for discussion here — two widths, one 230px photo frame, nothing cropped, settled by the previous board. Every option below is judged against it, and the heights in the captions are measured at runtime, not asserted.

Where we are

the problem

The note is on the back, and the back is empty until a flip fires Play.get(playId) — so reading one sentence costs a tap and a network round trip, and nothing on the front hints there is anything to read. Meanwhile FeedPlayCard.notes has been on the wire of every feed card all along (models.py:1500, filled at feed_service.py:50), unread by the front end. Nothing on the card can be responded to.

01

Four ways to put the note on the front

One constraint decides this. One height, two widths — both variants share a single caption spec so a session rail sits on one baseline, and .play-card__caption-meta even pins line-height: 16px because a winner line carrying a score measured 1px taller than one without. So an option either costs zero height, or costs the same height on every card — including the majority that have no note at all. (Notes are sparse: the "Table Chronicler" achievement fires at one play with a note.) Flip the Note control to "None" — that is where the difference actually bites.

The number in each caption is measured off the DOM after every repaint, not typed in. Today's card is 324px; if an option ever shows two numbers, that option has broken the contract in front of you.

Four ways to say nice

Strava's kudos is one gesture, one per person per activity, with a count and a face list — and its power is precisely that it is not a menu. The mark here is the meeple: it is already the project's own sprite (web/assets/sprites/bgb-meeple.svg), it is what a player is, and "give them a meeple" is a sentence a board gamer can hear. Everything below varies the placement and the grain, not the vocabulary.

One mechanical constraint applies to all four: the whole <article class="play-card"> is role="button" and a tap flips it, so a kudos control must be a real <button> carrying data-no-flip. Double-tap-to-kudos is off the table for the same reason — the first tap has already flipped the card.

Both at once

the actual decision

This is why one board and not two: A and K1 want the same square inch. The note band and the kudos chip both live at the bottom of the photo, and stacking them buries the picture. Two resolutions, plus the pairing that has no conflict at all because B puts the note below the photo instead.

05

What each one costs to ship

The two features are not remotely the same size, and the pick should be made knowing that. The note preview is an afternoon; kudos is a migration, an RPC signature change, two endpoints and a fourth arm on the notification feed.

Note preview

front end only
  • No backend work at all. FeedPlayCard.notes already ships on every feed card — the RPC returns it, the service maps it, the model declares it.
  • Two files: renderFront() in ui/play-card.js, and one new CSS family in styles.css.
  • Clamp it hard. boardgamebuddy_plays.notes is bare TEXT with no constraint, and no input anywhere sets a maxlength — AI- and BGG-imported notes are arbitrary length. escapeHtml as well, obviously.
  • One open question: do stack cards (a run of identical imported plays) get the preview? They share one note, and widgets/play-run-sheet.js:159 already shows it.

Kudos

full stack · reaches the bell
  1. Migration 013. A boardgamebuddy_play_kudos table keyed (play_id, user_id), plus ENABLE ROW LEVEL SECURITY and a GRANT SELECT … TO boardgamebuddy_role — every table in the schema has one. Update db/schema/ and db/functions/ in the same commit.
  2. The feed RPC. bgb_feed_plays gains kudos_count and viewer_kudosed. Adding OUT columns means DROP + CREATE, not CREATE OR REPLACE. Read them with row.get(…, default) so an unmigrated RPC still answers — the pattern is already in feed_service.py for group_count.
  3. Two routes. POST/DELETE /plays/{id}/kudos, each with a response_model=. Reject kudos on your own play, as Strava does.
  4. The bell — the expensive half. The notification feed is derived: no events table, just a UNION of three sources in bgb_notifications. A fourth kind is a fourth query arm plus its supporting index, plus a fourth value on NotificationKind. Not an insert.
  5. Optimistic, and out of the cache. Copy the per-id Map + _busy Set pattern from feed-view.js:597. It must not route through _invalidatePlayDeps() — that clears the whole feed cache, so every tap would refetch the feed.
