> Previously: 2026-09-17 (**the play importer can read Board Game Arena**. The source picker has carried a disabled *Board Game Arena — coming soon* row since the wizard shipped; it is real now. Sign in on the account step, the sweep reads your finished tables, and you land on the same shared review and summary every other source lands on. Each table arrives with its date, its scores and its whole roster, so there is no model in the loop and nothing to be wrong about except **which person a handle belongs to** — and BGA gives no email and no other identifier, so the app remembers handle → person mappings (`boardgamebuddy_bga_player_links`) and the second import is a glance rather than the work the first one was. Handles resolve on a ladder, best evidence first: your own handle, a mapping you made before, another BoardgameBuddy account that linked the same handle, then the local name ranker — which for this source ranks **username before display name**, the opposite of the note importer, because a BGA handle *is* a username. Every row says which of those it was, because "Tiggy_42" tells you nothing about whether the match is right. > Previously: 2026-09-17 (**the trending rail remembers yesterday**. > Previously: 2026-09-16 (**there is a Discover tab, and it knows what you play**. A fourth bottom-nav tab — Feed · **Discover** · Play · Profile, at `/discover` — turns the two things the app knows that BoardGameGeek does not, the shelf and the play log, into games worth a look. ## What It Does
A Strava-style log for board game plays. The home view is a chronological feed of plays from the user and their accepted buddies, interspersed with "hot games this week" and suggested buddies. Logging a play is a guided three-screen cascade — Gather → Play → Settle Up — that walks the host through the play and mirrors read-only to everyone else (the host is the only person who scores; joiners and spectators watch the grid update live). The Play tab is split in two: hosting on top (host a game, replay the last one, or browse the Game Explorer) and joining on the bottom (enter a short code, or pick a live session hosted by a buddy). Hosting also works with no connectivity at all — the cascade runs from cache, the play queues on the device, and it uploads on the next online session. That switches itself on and off with the device's connection; there is nothing to toggle. Profiles are fully public and show a Strava-style stats strip + collection grid. The reference-guide system is fully user-driven: each user builds their own per-game guide by adding "chapters" — either creating new ones or browsing the community pool. The pool sorts by popularity. Reports on offensive chapters route to admin review.

Logging a play also surfaces the reference guide in-line: once a game is picked, a collapsed Expansions section lets the player toggle which expansions are active for this session — its rows paint from the device's warmed `game.bundle` cache in the same frame as the pick, with `GET /games/{id}/expansions` refining them in place behind a dimmed-with-a-sweep treatment, so an owned game never waits on a round trip to show what it has — and a Reference guide section appears below Scoring (on both the host's Play step and the spectator's mirror) with a centered Rulebook button + the parchment scroll merging chapters from the base game and every active expansion (each tagged with a colored dot matching the expansion's identity color). Adding chapters from this in-play scroll routes through the same Browse/Create UI, with each chapter saved against its source game's pool so it propagates automatically the next time the user opens the guide. A header bell collects everything that has happened **to** the account — being seated in somebody's play, a buddy request, a request of yours being accepted — all three derived rather than stored, so answering one empties it by construction. Since migration 017 that same set can also leave the app as **push notifications**, behind one Settings control with three positions: everything, only the things that need you, or off. It is opt-in, per-account (so it follows you to a new phone) with a subscription per device, and on iOS it requires the app be added to the Home Screen — which the install prompt already asks for. Bulk paths deliberately stay silent: a 214-play BGG import that seats six buddies fills the bell without waking six phones.

## Design system — "Lamplight Study"

Game night under a warm lamp: espresso ground, amber glow, terracotta wins. Full write-up in `Docs/ARCHITECTURE.md` §4; the repo-wide rules are `.claude/rules/theming.md`, `overlays.md` and `mobile-web.md`. The four things to know before touching any UI here:

- **Two themes, equal.** Light and dark, switched by `data-bgb` on `<html>` — set by a pre-paint inline script in `index.html`, owned thereafter by `domain/theme.js`. `data-theme="luxury"` is DaisyUI's attribute and is deliberately *not* the lever; leave it alone. Settings offers Light / Dark / **Auto**, and Auto is the absence of a stored key, so the app keeps following the OS live (including across a backgrounded appearance change, which needs more than a media-query listener on iOS).
- **Every colour is a token**, declared in one of three blocks at the top of `styles.css`: theme-independent scales, dark, light. The only legitimate inline colour is data-derived (`--game-accent` from a game's `theme_color`, `--exp-color` from an expansion's).
- **Three kinds of surface, and the trap is picking the wrong one.** *Ground* is the page. *Paper* is anything that is a photograph — play cards, the Gather grid, the parchment scroll — and it is light in **both** themes. *Chrome* is plain UI cards — the profile hub, the five spokes, Settings, the picker sheets — and it follows the ground. Point a ground token at a paper surface and it inverts.
- **Four layout tiers, one attribute.** `data-bgb-layout` on `<html>` — `phone` (< 768px, the layout everything above was drawn for), `tablet` (768–1023px: a 720px column, bottom bar stays), `wide` (≥ 1024px: a left rail replaces the bottom bar and the header, 1040px column) and `land` (a phone held sideways — landscape and ≤ 560px tall: the same rail drawn compact at 64px, content filling the width beside it). `land` is the one tier keyed on height rather than width, because a phone on its side is 852×393 and passes the tablet width test. Set pre-paint by an inline boot in `index.html`, owned by `domain/layout.js` (`BgbLayout`), published to the store as `layout`. `#app`'s width and every docked bar's width are the `--bgb-col-max` token; the rail's width is `--bgb-rail-width`; fixed chrome centres on `--bgb-col-center`. Per-tier rules select `:root[data-bgb-layout="…"]`, never a `min-width` media query, so every tier goes through one lever. The tier is the viewport's alone — the Settings **Layout** control that used to pin one is gone, along with the `bgb.layout` key it wrote and every reader of it. Full write-up in `Docs/ARCHITECTURE.md` §4.6; the design boards are `Docs/mocks/tablet-layout-mock.html` and the live `Docs/mocks/landscape-phone-mock.html`.
- **Choice lists are bottom sheets**, on the shared `ui/bottom-sheet.js` shell, never `position: absolute` dropdowns; centred cards share `ui/modal-shell.js` the same way, and every confirm, alert or prompt is `PolaroidPopup` (never `window.confirm`/`prompt`). The app-wide status sheet, the Stats by-game picker, both Gather pickers, the data export and the buddy-alias sheet among them. A new sheet must be added *by name* to the theme re-point list in `styles.css`, because a body-level sheet lands outside the screen that opened it.

suggestion RPCs, is never shown to the person dismissed, and is **not a block**:
they can still find the viewer, still send them a request, and still turn up in
`/profiles/search` — which is also the way back from a mis-tap, since sending
that person a request deletes the row (`buddy_service.send_request`). Blocking
is a `status` on `boardgamebuddy_buddy_edges` and cuts both directions; if it is
ever wanted it belongs there, not here.

No surrogate `id`: the pair IS the identity, and the composite primary key
serves both query shapes — everyone one viewer dismissed, and one exact pair.

### boardgamebuddy_ghost_claims
Ghost account claims — "is this you?" (migration 070). A ghost player is not an

### boardgamebuddy_user_chapters
One row per (user, chapter): this viewer's opinion of that chapter, in either
direction. Until migration 033 the row's mere presence meant "in my guide"; it
now carries a `state`, and presence means "this viewer has decided about it".

`disliked` is the thumbs-down the guide builder offers beside Add. It is the
missing middle between "this is fine" and the Report button: a chapter that is
merely bad — a sloppy scoring grid, a rules summary you disagree with — used to
come back forever, in the pool on every visit, in the "N of M" denominator that
could then never close, and in the scoring-template offer at the table. A
dislike takes it out of all three. It is per-viewer and one-directional: the
author is never told, `popularity` is unaffected, and nothing is removed for
anybody else. Set from two surfaces: the thumbs-down beside Add on an un-added
row in the guide builder, and the one beside "Use this one" on each card of the
scoring-template offer sheet (`widgets/scoring-template-sheet.js`). The sheet's
is the only answer there that does not close it — three grids you do not want
are three refusals, and being asked again next round about the two you did not
reach is the problem the feature exists to fix — so the card goes, the next
candidate is promoted into the gap from the full pool, and the sheet closes
itself only when the last one is turned down.

Reversible from the builder's Turned-down section — a `<details>`
collapsed by default, since it is a record of decisions already made and the
browse list is what the screen is for; the count rides in its header so the
collapsed state still answers "did I turn anything down here?" — and cleared
automatically by adding the chapter — the act that contradicts it — exactly as
sending a buddy request clears a `buddy_suggestion_dismissals` row.

The `state` lives on this row rather than in a `chapter_dislikes` table of its
own because the `UNIQUE` below is then what makes "kept and disliked at once"
unrepresentable, and because disliking a chapter already in the guide is one
`UPDATE` rather than a delete plus an insert.

### boardgamebuddy_release_notices

Admin-authored what's-new notes (migration 042), shown once per user in a popup on their next visit and kept afterwards in the Settings archive.

| Column | Type | Notes |
|---|---|---|
| id | UUID | PK |
| title | TEXT | one line on a 390px card |
| body_md | TEXT | markdown, rendered by `web/ui/markdown.js` |
| link_route | TEXT | a router route name for the optional "take me there" button, or NULL |
| link_label | TEXT | that button's copy; defaults to "Take me there" |
| published_at | TIMESTAMPTZ | **NULL = draft.** The only draft flag, the sort key, and the unit the watermark compares against |
| created_by | UUID | `ON DELETE SET NULL`, not CASCADE — deleting an admin must not delete the notices everyone else is reading |
| created_at / updated_at | TIMESTAMPTZ | |

`published_at` is deliberately the *only* state. A `status` column beside it would be two sources of truth for one fact, written by three routes and correct only if all three remember — the same argument `008_link_notifications.sql` uses to refuse an events table. It is written only by the publish/unpublish routes, never by the client: a backdated timestamp would sort behind watermarks users already hold and be invisible to exactly the people the notice was written for. Republishing therefore moves the stamp forward and re-shows the notice; unpublishing hides it from anyone who has not seen it and **cannot** retract it from anyone who has.

`link_route` is plain TEXT rather than an enum because the backend has no route table, so any server-side enum would be a copy that drifts the first time a route is renamed. The admin picker offers only `router.routeNames()` — routes with a `build` and no `consume`, i.e. those reachable with no params — and both render paths drop the button when `router.pathFor()` cannot build a URL, which also covers a route retired *after* the notice was written.

**The seen-state is one column on the profile**, not a join table: `boardgamebuddy_profiles.release_notices_seen_at TIMESTAMPTZ NOT NULL DEFAULT now()`, the shape `link_notifications_seen_at` has carried since 008. That default is load-bearing three ways and is what removes three separate decisions: a new account is watermarked at signup so it **never sees the backlog** (no Python change — `_load_or_create_profile` does not name the column), every pre-existing row was watermarked by the `ADD COLUMN` itself, and there is no NULL so no `COALESCE` direction to get backwards. Deliberately *not* also filtered on `profiles.created_at`: with the default the watermark at creation **is** `created_at`, so the extra predicate is tautological on day one and actively wrong afterwards — once a user marks things seen, `created_at` is older than their watermark and would re-widen the set.

Two RPCs. `bgb_release_notices_unseen(p_viewer, p_limit=5)` returns the **newest** five unseen notices sorted **oldest-first**, so the popup reads as a chronology while an account six releases behind still gets the recent ones rather than the ancient ones; the watermark is read as a scalar subquery so "what counts as unseen" lives in one place, and a missing profile row yields no rows (it fails closed, deliberately). `bgb_mark_release_notices_seen(p_viewer, p_through)` is `bgb_mark_link_notifications_seen`'s twin, monotonic under a `GREATEST`, and takes the newest `published_at` the client was **shown** rather than `now()` — a notice published between `/bootstrap` and the dismissal must not be marked seen without appearing, and since the admin publishes from inside this same app that is an ordinary sequence rather than a contrived race.

## API Endpoints

### boardgamebuddy_bgg_push_queue

Outbound queue for BgB→BGG (migration 070). One planned change per game per user, `UNIQUE(user_id, bgg_id)`, drained by a `BackgroundTasks` worker at one BGG write per throttle tick. `change` is `add` / `update` / `clear` and `target_status` is NULL exactly when `change='clear'` (enforced by `bgb_push_change_status`). `payload` JSONB is the **complete form field set, frozen at plan time** — the three flags BgB owns at their target values plus every other `<status>` attribute echoed verbatim — so the worker never re-reads BGG and a shelf edit mid-push cannot produce a half-old, half-new write set. `bgg_collid` is nullable and is what the payload branches on, **not** `change`: a game flagged only `fortrade` is invisible to the status sweep, so a change planned as `add` can still turn out to have an existing BGG collection row, and sending no collid for one of those would create a duplicate and orphan the user's rating and comment on the original — `bgg_push_routes._resolve_collids` looks those up by id before queueing. `attempts` promotes to `status='error'` after 3; a 429 backs off without burning one, and a 409 (dead session) aborts the whole run rather than hammering BGG's login with a bad password. State lives in Postgres, not memory, so a restart mid-push resumes instead of replaying. Deliberately **not** `kind='push'` on `boardgamebuddy_bgg_pending_imports`: `bgb_bgg_sync_status` counts every row for the user with no `kind` filter, so a queued push would inflate the *import* poll's `pending_count` and pin it open forever.

Each row carries `popularity` (count of users who have it) and `in_my_guide` (whether the caller has it). Sorted by `popularity DESC, created_at DESC`. Supports `?q=` (title+content ILIKE), `?chapter_type=`, `?layout=text|scoring_grid` (migration 018 — `?layout=scoring_grid`, paired with `?chapter_type=scoring_grid`, plus each row's `in_my_guide` is how the reference guide answers "does this game have scoring templates I haven't added?", which is why there is no separate scoring-templates endpoint), and `?expansion_ids=a,b,c` (comma-separated game UUIDs to merge into the pool — each merged row carries `source_game_id` / `source_game_name` / `source_color` so the FE can render colored dots tying chapters to their expansion). Disliked rows stay ON the wire rather than being dropped server-side: the guide builder needs them for its Turned-down section, and shipping them tagged with the pool it already fetches is one round trip where a second endpoint would be two. Every client-side reader therefore has to filter them — the browse list via `_activePool()`, both scoring-template offer surfaces via the single `Chapter.pendingTemplates()` they share. Auth optional — anon callers always see `in_my_guide=false` and `disliked=false`.

Supports the same `?expansion_ids=a,b,c` scoping as `/chapter-pool`, so the two always agree. Exists because the reference guide's Edit-chapters button shows "N of M" on every mount, and `/chapter-pool` would carry every chapter's full markdown body to produce that one integer. Auth is OPTIONAL and viewer-scoping is the only thing it buys: since migration 033 the caller's own dislikes come off the total, because a chapter they refused is not one their guide is missing. An anonymous caller gets the unfiltered pool size, as this endpoint always returned. The viewer's own N still comes from `my-chapters`.
- `GET /api/v1/boardgame_buddy/games/{game_id}/expansions` — list expansions linked to this base game; `is_enabled` reflects the caller's own toggle when authenticated, `false` otherwise. Each item includes the expansion's `rulebook_url`, plus both `thumbnail_url` and full-size `image_url` (the reel's polaroids crop at 132×110, which upscaled the ~200px thumbnail).
- `GET /api/v1/boardgame_buddy/collection/expansion-catalog` — every expansion BgB has for every base game on a user's owned shelf, as `{items}` of `ExpansionListItem` (each carrying `base_game_bgg_id` so the caller can group them). - `GET /api/v1/boardgame_buddy/export?dataset=collection&dataset=plays` — the archive itself, `application/zip`, one CSV per thing, plus a `README.txt` naming every file and its row count. **Plays is two ticks, deliberately.** `plays` is `plays.csv` alone: one row per play, complete on its own, with the roster folded into a `|`-delimited `roster` cell of `name:score` pairs (a bare name where a play kept no scores) beside `winners` and `expansions` cells in the same form — so the file has the same shape for a two-player game and a seven-player one and never grows a column. `plays_detail` is `play_players.csv` + `play_expansions.csv`, the same plays broken back out one row per seat and per expansion for pivoting, joined on `play_id`; it deliberately does **not** re-emit `plays.csv`, because two ticks writing one filename with different columns is a collision waiting for whoever ticks both. The summary is lossy on purpose — per-round scores only exist in `play_players.csv`, and a name containing `|` (or, in `roster`/`winners`, `:`) has it flattened to a space in the summary columns only, with the detail files carrying it verbatim. `collection` is the other multi-shape tick, and goes the other way: shelf rows and owned expansions share **one** `collection.csv` under a leading `row_type` column (`shelf` / `expansion`), because nobody thinks of their shelf and the expansions on it as two things to ask for separately. An expansion carries no shelf status, so `status` is left blank on those rows rather than given an invented `owned_expansion` value the app's own shelf never writes. Both play datasets read the same rows, so the plays/seats/expansions load is cached on a per-export build context and paid for once. **Self-only, and there is deliberately no `user_id` parameter** — profiles being public was not a decision about bulk-dumping somebody's notes, purchase prices and private BGG comments. `plays` is the union of plays the caller logged and plays they were seated in, matching what `GET /plays` shows, with `logged_by_you` telling the two apart. Nothing off `boardgamebuddy_profiles` is exported for its own sake any more — not the linked `bgg_username`, and so by construction not the encrypted BGG password or the live session cookies sitting beside it on that row. Every read is paged at 1000 (`EXPORT_PAGE_SIZE`) because a PostgREST cap would otherwise truncate an export **silently**, and the whole build runs in one `asyncio.to_thread` — the Supabase client is synchronous and this is dozens of round trips. CSVs are UTF-8 **with a BOM** (Excel reads a BOM-less file as the system codepage and mangles accented game names) and cells that would run as a spreadsheet formula are tab-prefixed. `shared-backend/routes/boardgame_buddy/services/export_{csv,reads,plays,service}.py`; covered by `shared-backend/tests/test_export.py`
- `GET /api/v1/boardgame_buddy/games` — catalog browse. `include_expansion_counts` (default **true**) gates a second DB round trip per page that fills `game.expansion_count`; the explorer's polaroid grid never renders it and passes `false`, halving the round trips on that path. Ordering is `created_at DESC, id DESC` by default, or `name ASC, id DESC` under `sort=alphabetical` (the Add Games catalog scroll — import order is noise on a browse-everything screen). The `id` tiebreaker is load-bearing on both axes, not cosmetic: `created_at` is nullable and bulk BGG imports share a transaction timestamp, and two printings of one game share a name — so without it paginated calls repeat and skip games. Backed by `idx_bgb_games_browse` (migration 051).

- `GET /api/v1/boardgame_buddy/collection/shelf` — a **whole** shelf in one response, for client-side paging. Params: `status` (owned / wishlist / played), `exclude_expansions` (default true), `limit` (default 1000, hard cap 5000), `user_id`. `status=owned` returns `prev_owned` rows too — a game you sold is still on your Owned shelf — and `parted_total` says how many of `total` those are, so the caller can show a count that means "games you own" while drawing every row. Returns `{items, total, parted_total, truncated, generated_at}`, pre-sorted the same way `/collection/grid` sorts by default so the caller can slice without re-sorting. Deliberately takes **no** search/filter/page params — one cache entry per shelf, with the visible window, filter and search all derived on the client. One DB round trip (`bgb_collection_shelf`), down from the grid's two-to-three: it reads the denormalized `game_*` columns rather than embedding the games row — `image_url` is the one exception, a LEFT JOIN added in migration 055 because 020 never denormalized the full-size art — folds play stats in as a LATERAL, and computes `expansion_count` in SQL. `truncated` marks a shelf past `limit`, and the web client then falls back to `/collection/grid` for search/filter rather than narrowing an incomplete list. - `GET /api/v1/boardgame_buddy/collection/grid` — paginated owned collection sorted by `last_played_at DESC NULLS LAST, added_at DESC` by default. Supports `search`, `players`, `playtime_min/max`, `play_mode`, `exclude_expansions` (default true), `sort` (`last_played` / `added_at` / `alphabetical`), and `user_id` (target user; defaults to the viewer — owned and played shelves are public, `status=wishlist` for another user returns an empty page, as `/collection/shelf` does). `status=owned` matches `('owned','prev_owned')` and reports `parted_total`, exactly as `/collection/shelf` does — a shelf past the shelf endpoint's row cap falls back here mid-scroll, and a different row set would reshuffle the grid under the reader. **One round trip** (`bgb_collection_page`, migration 024): the filter, the sort, the count and the page all run in Postgres, with play stats and `game.expansion_count` — the catalog-wide number of expansions pointing at that base game, which drives the tile badge — folded in as LATERALs. It previously read the *whole* shelf on every page turn and did all four in Python across two round trips (three on the played shelf); worse than slow, those reads carried no limit, PostgREST silently caps an unbounded select at 1000 rows, and the filter ran **after** that truncation — so on a large shelf a matching game could be missing because it sat past row 1000. Still the paginated/server-filtered path, used by the web game explorer; the Collection and Wishlist spokes moved to `/collection/shelf`.

Do not reach for it to change one field. The one write path that is not `bgb_log_play`, so migration 023's roster gate is a `PlayUpdate` validator instead — **422** for a body that seats nobody or seats one account twice, raised before the delete, since a roster refused halfway through would leave the play with no seats at all. Photos are read once and dropped with the request, never persisted: a play photo earns a bucket row because the play keeps it forever, whereas a picture of somebody's notebook is scaffolding for one call. - `POST /api/v1/boardgame_buddy/plays/reactions` — say **"Good game"** to plays; body `{play_ids: [...]}`. The surface is the feed's session footer, so one tap covers a whole game night and the body is a list; one play is a list of one, which is what a per-card control would send if one ever ships. The server mints one `reaction_group_id` for the tap, **drops any play the caller logged** (you don't congratulate yourself, and a session can contain plays logged by several people) and upserts `ON CONFLICT DO NOTHING`, so a double tap keeps the original row's group id and `created_at` rather than re-stamping them. - `POST /api/v1/boardgame_buddy/bgg/sync` — pull the **collection** (`own=1`, `prevowned=1`, `wishlist=1`, `wanttoplay=1`, `showprivate=1`) from BGG, and **count** the plays that are missing. Per-user calls go through `fetch_bgg_as_user`, which sends the stored cookies so BGG evaluates the request AS the linked user — that's what unlocks the `<privateinfo>` block (purchase price, private comment, acquisition date, …) which we mirror onto `boardgamebuddy_collections.bgg_*` columns.   **THE PLAYS HALF IS A COUNT, NOT A WRITE.** This endpoint used to insert BGG plays straight into `boardgamebuddy_plays` / `_play_players` — the one importer in the app that wrote plays nobody had reviewed, reaching past `bgb_log_play` and re-implementing migration 023's roster rules in `_player_rows`. Plays come in through the play importer now (`POST /bgg/plays/pending` → the wizard → `POST /plays/import`). What survives here is the read: `/plays` is still walked, the missing ones counted against `(user_id, bgg_play_id)`, and `plays_new` is what the done screen's **Import N plays** button hands to the wizard. `plays_read_failed` exists because `plays_new = 0` from a read that never landed looks exactly like `plays_new = 0` from an account that is up to date, and telling somebody with four hundred plays waiting that they are up to date is the worse of the two lies. The read is parked in `services/bgg_plays_cache.py` for five minutes so following that button costs nothing; a failed read is never parked. `plays_imported` / `plays_pending` were **renamed rather than zeroed** — a count that silently means something else is precisely the failure this change is about. `unique_games_to_import` narrowed to the collection at the same time: a game that exists only to carry a play is the importer's to fetch on demand, and promising it to a worker queue nobody is filling would strand the progress bar.

- `POST /api/v1/boardgame_buddy/bgg/plays/pending` — the play importer's BoardGameGeek source. Reads BGG, writes nothing. Prefers the read a sync just parked (`services/bgg_plays_cache.peek`) and falls back to walking `/plays` itself; **the "already in BgB" filter runs live against the database on every call**, because the cached thing is the BGG bytes and a cached filter would offer back the plays the last run just imported. That is also why the cache is *peeked*, not popped: a check's plan is a decision and is spent when acted on, but this is data, and the path into the wizard is a real loop (pick a source, back out, come back, refresh mid-wizard). Returns `{bgg_username, plays[], total_new, truncated, fetched_at, reused_read, read_failed, players[]}`, newest first and capped at `MAX_BGG_PENDING_PLAYS` (500, matching `MAX_IMPORT_PLAYS`) — truncating is safe here in a way it would not be for a pasted note, because every imported play keeps its `bgg_play_id`, so "run it again for the rest" terminates. Each play carries `{bgg_play_id, bgg_id, bgg_game_name, played_at, notes, quantity, players[], game}`, where `game` is the catalog row or `null`. Games the catalog lacks are **not queued**: the wizard's Games step imports them on demand through `POST /games/import-bgg/{id}`, so nobody spends a BGG `/thing` call on a game whose plays they never bring over. `quantity` is echoed and never expanded — BGG lets one `<play>` stand for N sittings, and N rows sharing one `bgg_play_id` would be rejected by the partial UNIQUE, so the import would land one and report N. A POST for the same two reasons `POST /bgg/check` is one: it spends 20-40s inside the handler against a third party, where a GET invites the browser and the service worker to turn one press into four walks, and it holds the shared BGG session — so it 409s against a running push or import.
- `GET /api/v1/boardgame_buddy/bgg/sync/status` — `{bgg_username, auth_state, pending_count, errored_count, last_completed_at, session_started_at, session_total, session_done, session_errored}`. `auth_state` is `unlinked` / `linked` / `relink_required`; the session_* counts are scoped to the most recent sync (rows with `created_at >= profiles.bgg_last_sync_started_at`) and counted in distinct BGG ids so they line up with the per-game `/thing` calls the worker makes. The Settings BGG card polls this every 2s while `session_done + session_errored < session_total` to drive an "Importing X of Y" progress bar.
- `POST /api/v1/boardgame_buddy/bgg/check` — the comparison both sync buttons act on. Sweeps the live BGG collection (the same 8 throttled `(subtype, status-flag)` requests the import makes, reused via `bgg_collection_read._fetch_collection_items`), reads the BgB shelf, and classifies every game **in both directions from one sweep**: the push view (`add` / `update` / `clear`) and the pull view (`add` / `update` / `held`). Statuses are compared **derived, not raw** — the importer collapses BGG's `wanttoplay` into `wishlist`, so a wanttoplay-but-not-wishlist game derives to `wishlist`, matches a BgB wishlist row and is left alone; comparing raw flags would push `wishlist=1` onto it purely because the import is lossy. `held` is the pull-side expression of `_hold_prev_owned`: a game marked Prev. owned in the app is never resurrected as owned. A POST, not a GET, because of one write — games on the BGG shelf that BgB's catalog has never seen are queued as `kind='catalog'` pending imports so the comparison can name them instead of listing bare ids; that imports the **game only, never a shelf row**, so those games still read as "only on BGG" and the push still decides their fate. Returns `{bgg_username, checked_at, in_sync_count, local_total, remote_total, push_total, pull_total, push_changes[], pull_changes[], unpushable[], truncated, catalog_pending, warm_up_retry_pending}`; item lists cap at 500 while the totals stay true. 409s while an import or a push is draining. The finished plan — and the sweep it was built from — is parked in the in-process cache for 5 minutes (`services/bgg_check_cache.py`, matching the FE's `DIFF_MAX_AGE_MS`) so **neither sync button repeats this work**; `checked_at` is the key the push matches its stored plan against. Same in-process argument as `bgg_progress`: the sweep dies with the request that ran it, so a durable row would outlive the only thing that could vouch for it, and a miss just means the sync sweeps as it always did.
- `GET /api/v1/boardgame_buddy/bgg/check/progress` — what an in-flight comparison is doing right now, so the flow screen can tick a checklist instead of spinning for 40 seconds. Returns `{state, kind, check_id, started_at, updated_at, steps[], warm_up_failed, error}`, where each step is one phase (`guards` / `collection` / `shelf` / `compare` / `catalog` / `collids` / `queue`) carrying `state`, an optional `done`/`total` and an optional `retry` `{attempt, of, wait_seconds, resume_at}` while BGG is warming up. Polled at 1s **alongside** the in-flight `POST /bgg/check`, which is only possible because that handler spends most of its time in `asyncio.sleep` between throttled BGG calls. The ledger lives in the in-process cache (`services/bgg_progress.py`), not the DB, because the sweep is in-handler work: a restart kills the sweep, the connection and the result together, so a record that dies with them is correct where a durable row would outlive all three and lie. `state='unknown'` therefore means *no record* — a restart, or a second uvicorn worker — and the client renders it as **still working**, never as done; completion comes from the POST's own resolution. `POST /bgg/push` writes the same ledger under `kind='push_plan'` while it re-plans, which is otherwise a blank 10-40s wait.
- `POST /api/v1/boardgame_buddy/bgg/push` — make BoardGameGeek mirror the BgB shelf. **Collection status only** — `own`, `prevowned`, `wishlist` — with every other `<status>` attribute echoed back verbatim, so ratings, comments, private info and the user's own `want` / `fortrade` / `wanttobuy` / `preordered` flags are never authored. A game flagged on BGG but absent from the BgB shelf has those three flags *cleared*; the collection item is never hard-deleted, so its rating and purchase details survive. Commits the plan **the server** built for the comparison the user reviewed: the client sends only `checked_at` and gets back the stored plan or nothing, so it still cannot dictate a single write, and a stamp that does not match the stored one re-plans from scratch rather than guessing. Falls back to a full re-sweep when the cache no longer holds it (a restart, or a comparison older than 5 minutes), which is what it used to do unconditionally — charging the user the same 40 seconds a second time for pressing a button on the answer. Then writes one row per change to `boardgamebuddy_bgg_push_queue` and drains it with a `BackgroundTasks` worker (`BGG_PUSH_THROTTLE_SECONDS`, default 2.0s). **Refuses outright (503) when the sweep hit a warm-up failure**: a batch that gave up returned zero items, which reads as "not on BGG", and pushing that plan would clear flags off games we simply failed to see. Body `{checked_at}` only. Returns `{bgg_username, queued, adds, updates, clears, unpushable, warm_up_retry_pending, reused_comparison}` — `reused_comparison` is what the push log narrates, so it never claims a re-check nobody ran. The worker aborts the whole run on a `BggRefusedError` as it does on a 409: every remaining row would be refused identically. 409s while an import is draining, and `POST /bgg/sync` 409s while a push is — both directions drive the same BGG session.
- `GET /api/v1/boardgame_buddy/bgg/push/status` — the push poll target, one RPC (`bgb_bgg_push_status`). Same shape as the sync status plus `session_errors[{game_name, message}]`: a half-failed import can be re-run and idempotency cleans up, but a half-failed push has left flags on a third-party account in an unknown state, so the games have to be named.
- `GET /api/v1/boardgame_buddy/bga/link` — `{bga_username, bga_player_id, auth_state, last_import_at}`. `auth_state` is `unlinked` / `linked` / `relink_required`, the same three states the BGG card uses and deliberately a separate enum — the two accounts link independently. Read by the import wizard's account step on enter. The encrypted password decides the state and never leaves the server; `api/tests/test_bga_secrets.py` asserts no `/bga/*` response model has a credential-shaped field.
- `POST /api/v1/boardgame_buddy/bga/link` — body `{username, password}`; GETs BGA's login page for its CSRF token, POSTs the form BGA's own login submits, and stores the handle + Fernet-encrypted password (**`BGA_CREDENTIAL_KEY`**, its own key — rotating BGG's must not orphan these) plus the returned session cookies as one `bga_session_cookies` JSONB blob. One JSONB column rather than BGG's three named cookie columns, because BGA's cookie set is not documented and three named columns would bake in a guess. **A rejected password comes back as HTTP 200 with an error in the body**, so classification happens in `routes/bga_endpoints.login_result` and never by status code; a status-first reading stores a session that was never granted. Two-factor gets its own message rather than "check your password" — an importer cannot answer a second factor, and saying otherwise sends the user round a loop with no exit. 400 bad credentials or 2FA · 429 throttled · 503 unreachable · 502 anything else.
- `DELETE /api/v1/boardgame_buddy/bga/link` — clears every `bga_*` column in one write (a half-cleared link reads as `relink_required`, which offers a re-link nobody asked for). **The only way to unlink**, because the link deliberately has no Settings → Connections row — so the wizard's account step carries the control. Already-imported plays keep their `bga_table_id`: unlinking is "stop using my account", not "forget what I imported", and clearing it would silently offer all of them again on a future re-link.
- `POST /api/v1/boardgame_buddy/bga/tables/fetch` — the sweep. Walks BGA's finished-table history newest-first and **stops at the first table already imported** (`idx_bgb_plays_user_bga_table`); BGA history is chronological, so that early exit is what makes the second import of a heavy account cost one page rather than five hundred. Enriches per table only when the history page did not carry rosters and scores. Returns `{tables[], handles[], games[], skipped, truncated}` — `games` is the same `ParsedGameRef` list the note parse returns, from the same `play_import_service.match_games`, so the wizard's Games step renders identically for both sources and there is no second round trip. **Writes nothing:** the output is a draft the user reviews, and the write goes through `POST /plays/import` like every other source. Bounded by `BGA_MAX_TABLES` (500) / `BGA_MAX_PAGES` (20) / `BGA_SWEEP_BUDGET_SECONDS` (90), first to trip wins; past a cap it reports `truncated` and the wizard asks for another run, so the history is complete **across** runs and bounded per request. Every request is throttled at `BGA_THROTTLE_SECONDS` (default 2.0, stricter than BGG's 1.5) behind a **process-wide single-flight lock** — BGG rate-limits, BGA bans. 409 while a sweep is already running for this user. `BGA_DRY_RUN` defaults **on**: nothing reaches boardgamearena.com until somebody sets it false on purpose.
- `GET /api/v1/boardgame_buddy/bga/tables/progress` — what the in-flight sweep is doing, so the fetch step ticks a checklist instead of spinning for minutes. `{state, fetch_id, started_at, updated_at, steps[], truncated, error}`, one step per phase (`sign_in` / `history` / `known` / `detail` / `match`). In-process ledger (`services/bga_progress.py`), not a table, for the same reason as `/bgg/check/progress`: the sweep is in-handler work, so a record that dies with it is correct. `state='unknown'` means *no record* and the client renders it as **still working**. Note the contrast with `POST /bgg/sync`, which IS a BackgroundTask over a queue table — that one defers catalog **writes** worth having whether or not anyone is watching; this one writes nothing, so deferring it would leave a durable record of a proposal that died with the connection. It is also what keeps every BGA request inside a request a person is watching, which is what this feature's terms require of it.
- `POST /api/v1/boardgame_buddy/bga/players/remember` — body `{links: [{bga_handle, player_user_id?, player_display_name?}]}`; upserts this owner's handle → person mappings into `boardgamebuddy_bga_player_links`. Fired **fire-and-forget after a successful import**: a failed remember costs the NEXT import one tap and must never cost this one. This is the whole payoff of the matching step — the first import is work, the second is a glance.
- `POST /api/v1/boardgame_buddy/games/{game_id}/chapters` — create a brand-new chapter (type + title + markdown) and auto-add to the creator's guide
- `POST /api/v1/boardgame_buddy/games/{game_id}/chapters/generate` — AI-draft a chapter of the given `chapter_type` for this game and return `{chapter_type, title, content}`. Body also takes an optional `prompt` (≤500 chars, 422 past that) — the free-text steer from the create wizard's head-start step ("just the endgame trigger"); blank or absent drafts a general chapter for the type. **Saves nothing** — the wizard loads the draft into its form and the user reviews, edits, and saves it themselves. Synchronous (the user is waiting in the wizard), backed by Gemini Flash Lite via the shared `shared-backend/gemini.py` caller; 400 on an unknown chapter type, 404 on an unknown game, 502 when the model call fails (missing `GEMINI_API_KEY`, safety block, transport error). The prompt is four banner-delimited sections in a fixed order — **1** what to write (game, year, chapter type), **2** supported formatting and preferences, **3** the player's optional guidance, **4** the output format — and the markdown spec in section 2 is the app's own authoring guide, so see the sync note below. The game's BGG `description` is deliberately **not** in the prompt: up to 1500 characters of publisher marketing copy was the most expensive part of it and the least load-bearing, since a model that doesn't know the game is told (section 1) to write a fill-in skeleton rather than lean on a blurb. Section 3 is untrusted text a player typed into a form, so it is delimited, truncated, and told by name which sections it cannot change. Lives in `chapter_ai_routes.py` with the grid drafter below, not in `chapter_routes.py`.
- `POST /api/v1/boardgame_buddy/games/{game_id}/chapters/generate-grid` — AI-draft the **rows of a scoring grid** for this game and return `{grid: {v, rows[]}}` — the same shape `ChapterCreate.grid` takes, so the wizard can post it straight back. Body takes an optional `prompt` (≤500 chars, 422 past that) and an optional `mode` (`add_on` / `replace`, 422 on anything else): a grid is one chapter type by definition, so there is no `chapter_type` on the wire and no 400 for an unknown one. **`mode` changes what is drafted rather than steering it** (migration 032) — an add-on gets the two or three rows the expansion BRINGS, told by name not to restate the base game's since the app appends them underneath, and a replacement gets the whole reprinted sheet. It is resolved against the game the route has just read, by `chapter_grid.resolve_mode` — the same rule and the same add-on default the write path uses, split out of `resolve_grid_mode` so it can be asked before a grid exists — so a client that guesses wrong about a game cannot have rows drafted for one shape and saved under another; the reply echoes the resolved mode, making it a `ScoringGrid` that could be stored unchanged. An expansion costs one extra lookup for its base game's NAME, which is what lets the prompt say *"do not repeat Everdell's rows"*; a `base_game_bgg_id` that resolves to nothing (it is a soft reference) falls back to "the base game" rather than failing an optional step. **Saves nothing**, like the chapter drafter above; 404 on an unknown game, 502 when the model call fails. A separate endpoint rather than a branch of `/generate` because the two share neither a prompt nor a reply shape — `/generate` 400s a `scoring_grid` type outright and names this path in the message. The prompt (`services/chapter_grid_ai.py`) uses the same four banner-delimited sections and the same untrusted-guidance framing, through the shared `banner()` helper: **1** what to build, **2** what a row looks like, **3** the player's optional guidance, **4** the output format. Section 2 is where the real work happens — every constraint in it (`~10` rows asked for against a hard 24, a ≤24-character label, a colour from the closed `ScoringRowColor` slug set, an optional ≤200-character note) is re-checked in `_coerce` on the way back, because the rows go straight into `ScoringGrid` and its limits are a 422 rather than a nudge. The coercion **truncates rather than rejects**: an over-long label is cut, an unknown colour slug falls back to `neutral`, a duplicate label is dropped (case-insensitively — a sheet listing one category twice double-counts it), and only a reply with no usable row at all is an error. Runs cooler than the chapter drafter (temperature 0.2 vs 0.4): a scorepad is a fixed list of what the game scores, so variety between two authors' drafts of it is noise rather than voice.
- `PATCH /api/v1/boardgame_buddy/chapters/{chapter_id}` — edit own chapter (creator-only)
- `DELETE /api/v1/boardgame_buddy/chapters/{chapter_id}` — delete from pool (creator or admin); cascades to user_chapters + reports
- `POST /api/v1/boardgame_buddy/chapters/{chapter_id}/report` — body `{reason?}`; flag a chapter for admin moderation. Idempotent per user.
- `GET /api/v1/boardgame_buddy/games/{game_id}/my-chapters` — chapters the caller has added to their guide for this game (empty list when none). Supports `?expansion_ids=a,b,c` to also merge in chapters from the listed expansions in one round-trip; each row carries `source_game_id` / `source_game_name` / `source_color` for FE colored-dot rendering.
- `POST /api/v1/boardgame_buddy/games/{game_id}/my-chapters` — body `{chapter_id}`; add an existing pool chapter to my guide (idempotent)
- `DELETE /api/v1/boardgame_buddy/games/{game_id}/my-chapters/{chapter_id}` — remove from my guide (does NOT delete the chapter). Scoped to `state='kept'`, so it can never silently clear a dislike.
- `POST /api/v1/boardgame_buddy/games/{game_id}/disliked-chapters` — body `{chapter_id}`; turn a chapter down (migration 033). Hides it from the caller's chapter pool, from the `/chapter-pool/count` denominator and from the scoring-template offer, and drops it from their guide if it was in it — one row, one state, so all four follow from the single write. Per-viewer, never shown to the author, and NOT a report (`POST /chapters/{id}/report` is still the moderation path). Idempotent, and 200 rather than 201 because a second tap creates nothing — the same call `POST /plays/reactions` makes. 404 if the chapter does not belong to that game.
- `DELETE /api/v1/boardgame_buddy/games/{game_id}/disliked-chapters/{chapter_id}` — undo a dislike. The chapter returns to the caller's pool and counts; it is NOT added to their guide, because taking back a refusal is a different act from adopting. Scoped to `state='disliked'`, so it can never drop a chapter out of the guide. Idempotent.

  There is deliberately no `GET` for dislikes: the rows come back tagged on the chapter pool the builder already fetches.
- `POST /api/v1/boardgame_buddy/games/{base_id}/expansions/{expansion_id}/toggle` — body `{is_enabled}`; per-user expansion toggle. Read back by this module's expansion list and joined into `bgb_game_detail_bundle`; the chapter system does not consume it, and the web client does not call it (kept for the bundle's `is_enabled` column)
- `GET /api/v1/boardgame_buddy/admin/chapter-reports?status=open|resolved` — *admin-only* list chapter moderation reports
- `POST /api/v1/boardgame_buddy/admin/chapter-reports/{report_id}/resolve` — *admin-only* mark a report resolved with no further action
- `GET  /api/v1/boardgame_buddy/games/admin/missing-images` — *admin-only* list of games whose `image_url` or `thumbnail_url` is NULL
- `POST /api/v1/boardgame_buddy/games/admin/{game_id}/refresh-images` — *admin-only* re-fetch one game's box art + thumbnail from BGG and re-host in Storage
- `POST /api/v1/boardgame_buddy/games/refresh-images` — *admin-only* bulk refresh of all games with missing or BGG-hosted image URLs
- `GET  /api/v1/boardgame_buddy/admin/review-counts` — *admin-only* one call returning `{chapter_reports, missing_images, missing_descriptions, missing_stats, missing_publishers, total}`. Counts only (PostgREST exact-count, no rows) — it backs the notification dot on the Settings gear, so it runs on every boot for every admin
- `GET  /api/v1/boardgame_buddy/games/admin/missing-descriptions` — *admin-only* list of games whose `description` is NULL
- `POST /api/v1/boardgame_buddy/games/admin/{game_id}/refresh-description` — *admin-only* re-fetch one game's description from BGG
- `POST /api/v1/boardgame_buddy/games/admin/backfill-descriptions?limit=N` — *admin-only* bulk description backfill. Batches 20 games per BGG call and caps the pass at `limit` (default 200), returning `{updated, failed, remaining}`; the admin panel re-invokes until `remaining` is 0. Note this sits under `/games/admin/` unlike the older bulk image route at `/games/refresh-images`
- `GET  /api/v1/boardgame_buddy/games/admin/missing-stats` — *admin-only* list of games whose `bgg_stats_synced_at` is NULL
- `POST /api/v1/boardgame_buddy/games/admin/{game_id}/refresh-stats` — *admin-only* re-fetch one game's BGG rating / rank / weight
- `POST /api/v1/boardgame_buddy/games/admin/backfill-stats?limit=N` — *admin-only* bulk stats sync, the descriptions backfill's shape (20 ids per `/thing?stats=1` call, `{updated, failed, remaining}`) plus a `BGG_THROTTLE_SECONDS` pause between chunks. A game BGG carries no statistics for is still stamped synced so it leaves the queue
- `GET  /api/v1/boardgame_buddy/games/admin/missing-publishers` — *admin-only* list of games whose `publishers` is NULL
- `POST /api/v1/boardgame_buddy/games/admin/{game_id}/refresh-publishers` — *admin-only* re-fetch one game's publisher credits
- `POST /api/v1/boardgame_buddy/games/admin/backfill-publishers?limit=N` — *admin-only* bulk publisher backfill, the same shape as the two above (20 ids per `/thing?stats=0` call — publishers are plain `<link>` rows — `{updated, failed, remaining}`, `BGG_THROTTLE_SECONDS` between chunks). A game BGG omits, or credits to nobody, is written `'{}'` so it leaves the queue rather than being re-requested forever
- `PATCH /api/v1/boardgame_buddy/games/admin/{game_id}/rulebook-url` — *admin-only* set or clear a game's `rulebook_url` (body `{rulebook_url: string|null}`)
- `GET /api/v1/boardgame_buddy/release-notices/admin?status=` — *admin-only* every notice, drafts first (`status` is `all` / `draft` / `published`)
- `POST /api/v1/boardgame_buddy/release-notices/admin` — *admin-only* create a notice. Always a **draft**: `published_at` is deliberately absent from the write model, because publishing is its own act
- `PATCH /api/v1/boardgame_buddy/release-notices/admin/{notice_id}` — *admin-only* edit the copy or the link. Never touches `published_at`, so a typo fix on a live notice reaches only people who had not seen it yet. `clear_link: true` is how a link is removed, since `null` is also the "leave it alone" value
- `POST /api/v1/boardgame_buddy/release-notices/admin/{notice_id}/publish` — *admin-only* stamp it live with `now()`
- `POST /api/v1/boardgame_buddy/release-notices/admin/{notice_id}/unpublish` — *admin-only* pull it back to a draft. Weaker than it looks: it hides the notice from anyone who has not seen it and cannot retract it from anyone who has, which is what the confirm says before the fact
- `DELETE /api/v1/boardgame_buddy/release-notices/admin/{notice_id}` — *admin-only* remove it

- `POST /api/v1/boardgame_buddy/feedback/{id}/resolve` — (admin) take an item off everyone else's board
- `POST /api/v1/boardgame_buddy/feedback/{id}/reopen` — (admin) put it back. Resolving is reversible on purpose: it is an admin's read of "this is done", and a read can be wrong. Nothing deletes

  - `/admin/release-notices` — write and publish the what's-new popup (`views/admin-release-notices-view.js` + `widgets/release-notice-editor.js`). The one admin tool that **authors** rather than moderates, so it is the one row with no badge: an unpublished draft is not work waiting, and `forAdminTool("releaseNotices")` matching no signal returns zero, which renders nothing. **Inbound-only, and deliberately NOT in the router's path table:**

- `/b/<token>` — the add-a-buddy QR link. `init.js` matches it before `matchPath()` and rewrites it to `{name: "buddies", params: {qr: token}}`, which inherits the `pendingRoute` stash and therefore the bounce through `/auth` for a signed-out scanner. It stays out of `_routes` because nothing in the app ever navigates *to* it, and `pathFor()` resolves by name with `.find()` — a second entry named `buddies` would silently make every future `router.go("buddies")` build the wrong URL. `buddies-view` consumes the param and `replaceUrl`s the token straight back out of the address bar, so a refresh or a much later back navigation can't replay a spent code.

**Routes intentionally not in the URL:**

- `splash` — transient loading view between boot and Supabase auth resolving. Never pushed to history, never appears in the back stack. It is also the one screen with no bottom nav, so a boot that never finishes has no escape hatch: `init.js` arms a **12s watchdog** that routes forward anyway — to the normal destination when a session is in hand (the destination paints its own skeleton and reconciles when `/bootstrap` lands), to `/auth` when nothing resolved at all. The fallback never sets `_bootRouted`, so a late auth callback still routes the user correctly on its own.

**Back-stack semantics:** `router.back()` defers to `history.back()`; the popstate handler replays the entry's state (or falls back to `matchPath()` for direct loads). An internal `_stack` is kept in parallel only because the browser doesn't expose history-entry metadata — `peekBack()` reads it to label back affordances ("Back to game details", etc.).

## Screen Flow
Bottom nav has four tabs: **Feed**, **Discover**, **Log**, **Profile**. On the wide layout tier (≥ 1024px) the same nav stands on its end as a left rail and also carries the header's brand mark, bell and gear — see the design-system section above.

1. Auth (login/signup) → splash → **first-run setup, when the profile carries `needs_setup`** → 2. **Feed** (home): chronological mix of plays from the viewer and their accepted buddies, plus inline "hot this week" / "buddies you may know" rails. A search pill at the top opens the **Game Search** screen.

   **Cards are bundled into sections client-side, on two different keys, because the feed carries two different things** (`groupCards` / `sessionKey` in `views/feed-view.js`). A **game night** keys on `played_at | participants`: the people at the table are what make it one night, and they are the clickable names in its header — "You and Sam played 3 games". An **import** keys on `played_at | logger` and is headed "**JasBot imported 19 games**". Grouping an import by roster is what the second key exists to stop: a pasted notebook writes a play per line and the rosters differ line to line, so one afternoon's import used to land as five or six stacked sections — each with its own border, header and "Good game" footer, all under one date heading, each saying almost the same thing. The flag is `import_batch_id` (on the feed payload since migration 022), **not** `import_group_id`: the group id is set only on plays the importer judged indistinguishable from another in the same paste, so every one-off in an import carries no group id and would have been left behind as its own section beside the runs it arrived with. Both keys deliberately stay within one day, since `render()` prints the date once above each day's sections; two pastes covering the same day still merge, because to the person reading the feed they are one day's import. Each card inside a section keeps its own winner line, and a run of identical plays keeps its `group_count` stack ("4 PLAYS"), so collapsing the sections costs no information — only the repeated chrome. A live-logged play never joins an import section: it carries no batch id, so it keys on its roster as it always did.

   **First-run setup is five counted steps, run from `init.js` and nowhere else.** (The step-by-step below predates the slide deck that replaced the three modals — see `Docs/ARCHITECTURE.md` §4.3c for the current shell; the steps themselves are unchanged, plus **Notifications** at position three: the offer that turns an opt-in feature nobody would otherwise find into a real choice, placed straight after Add buddies so "we'll tell you when they accept" lands on requests the user sent ten seconds earlier. Turning them on there sets `push_tier` to `all` and subscribes the device; declining leaves the account off and writes the receipt `ui/push-prompt.js` reads, so the boot-time card does not immediately ask again.) Step one is the existing "Create your profile" card (`PolaroidPopup.avatarCustomizer` with `includeNameField`); saving it clears `needs_setup`, and dismissing it leaves the flag set so the whole sequence returns next load. Step two is **Add buddies** (`widgets/add-buddies-modal.js`): a wrapping grid of suggestions the user multi-selects, with one button that sends every tick as a single batch and one that skips. That card is no longer setup-only — the Buddies screen's Add button opens the same one, which is why its dismiss label is a parameter ("Skip" only makes sense inside a sequence) and why it tolerates an empty suggestion list, since its search field always gives the user something to do. The guard that stops first-run opening an empty one survives for its own reason: an account ninety seconds old has nobody to search *for*. Step three is **Link BoardGameGeek** (`widgets/onboarding-bgg-modal.js`). All three are modals rather than router views — the sequence has no URL worth deep-linking and a real view would leave a back-stack entry that means nothing once setup is done.

   **The BGG step goes last because it is the only one that can take minutes.** The two before it are a tap and a batch of taps; an import of a large collection legitimately sits on screen while the worker fetches a game at a time, and what waits behind the last card is the user's own feed rather than another step. Second, it would have parked "Add buddies" behind an import nobody asked to watch to the end.

   The buddy grid's tiles are **the same canonical buddy-suggestion tile the Feed and Buddies rails render**, in its `select` mode instead of its `add` mode (`ui/buddy-suggestion-rail.js`, one component with an `opts` variant per `.claude/rules/ui-object-design.md` §2). Step two is entirely best-effort: if the suggestion fetch fails, or returns nobody, it is skipped silently and the user moves on with a finished profile — an "Add buddies" screen with nothing on it reads as a broken feature in the first minute of the app. A transport failure *during* a send keeps the modal up with the ticks intact and an inline retry, because nothing was sent; per-target rejections come back inside a 200 and close it.

   **Step three is one card in two states.** The first is the pitch plus a BGG username / password pair, with **Skip** and **Link account** as equal-weight 52px buttons — skipping is a real destination here, and the copy says the link is still one tap away in Settings. On a successful `POST /bgg/link` the card switches, in place, to the import: `POST /bgg/sync` goes out immediately and the step log stays on screen, polling `GET /bgg/sync/status` every 2s, so the user watches the collection and play counts land and then each previously-unknown game's title stream into a bullet list as the worker fetches it (~1.5s each). The heading and the intro line are patched alongside the log — "Importing your games / this may take a while" while it runs, "Your games are in" when it lands — because a screen still claiming to be importing above a finished log is a contradiction. **Leaving does not stop the import**: the primary button reads *Continue* while the queue drains and *Done* once it is empty, ×/Escape/backdrop all mean the same thing, and the collection status map and the feed are invalidated on the way out because a half-drained import has already written every game we already knew about. The link form is never re-rendered — errors and the "Linking…" state patch in place, so the credentials being typed survive them; a rejected login clears only the password and puts the caret in it.

   **The step log is one component, `ui/bgg-import-log.js`, shared with Settings' Sync button** — it was `SettingsView._renderBggProgress` before this step needed the same readout of the same import (`.claude/rules/ui-object-design.md` §4). It is a pure function of the `POST /bgg/sync` summary and the latest `GET /bgg/sync/status`; the caller owns the poll. Two behaviours it made shared rather than doubled: `Bgg.importDrained(status)` is the one definition of "the queue is empty" (session counters, not the lifetime `pending_count`, so a row left over from an earlier failed sync can't pin the poll open), and `Bgg.invalidateImportedData()` is the one post-sync cache drop. `Bgg.sync()` also runs on a **120s deadline** rather than the client's 15s default (`api.post(path, body, {timeoutMs})`): the handler fetches a whole BGG collection and play history before it answers, and a 15s abort was both routine and a lie — the server finishes the sync and queues the worker whether or not the client is still listening, so both surfaces now report a tripped deadline as "still importing in the background", not as a failure, and offer no *Try again* beside it.

   Step three is best-effort like the one before it: a failed link keeps the user on the form, a failed sync offers one retry and a Done, and every exit lands them on their feed with a finished profile. Note it can only be *offered* once — saving the profile in step one already cleared `needs_setup`, so a reload mid-sequence skips straight to the feed. That is the same trade step two makes, and the reason both steps say where to find the thing again.
3. **Log a play**: the Play tab is split — **Host on top, Join on the bottom**.
   The Host half offers three cards: **Host a game** drops straight into the cascading three-screen flow (`play-flow`) with an empty game slot; **Another Round** (only when there's a recent play) reseeds the last game + roster and lands on Gather; **Game Explorer** opens `/games`, where players / play time / type filters over the user's collection or the whole library help pick a game — selecting one opens Gather with it prefilled. A "Resume hosting?" banner sits above the cards whenever a non-terminal draft exists.

   **Host a game always means a NEW game** — fresh draft, fresh session code, empty game slot — even when a resumable draft exists. The Resume banner is the only thing that continues a session. Starting a new play ends the previous one (`bgb_create_session` abandons the host's other open sessions), the same way Another Round already abandons deliberately. Until 2026-08-25 the card skipped its draft-clear whenever a resumable session existed, so a host who tapped it landed back in the old session, code and all.
   The Join half is the `JoinPanel` widget: a 5-char code input plus a 10s-polled list of active sessions where the user is a participant or the host is a buddy (sessions past Gather are labelled **Spectate**).
   The Log a play cascade has three snap-scroll screens:
   - **Gather** — pick a game, set game type (competitive/team/co-op), manage the player list. Both pickers are **bottom sheets** (`widgets/game-search-sheet.js`, `widgets/player-picker-sheet.js`) on the shared `ui/bottom-sheet.js` shell. They replaced inline `position: absolute` dropdowns: the Players card is the lowest on the screen, so with a few players seated `ui/dropdown-fit.js` had to squeeze the buddy list to its own 132px "keyhole" floor on top of the docked Continue CTA, and it still ran off the bottom edge. A sheet is `position: fixed` and sized off `--bgb-vv-h`, so there is no fit pass, no flip, and no z-index race with `.cascade-cta-wrap`. The player sheet is **multi-select** — tick several, then Add — and tick order is the seating order. Ticked people ride at the top under **Selected**, in that order, and leave the body list, so the sheet always shows what it is about to do rather than scattering your picks back through forty buddies the moment the search box empties; a query filters that section like every other row, because a pick that does not match what you typed is not an answer to what you typed. The game sheet hosts the same `widgets/game-finder.js` as before, its results the sheet's own scroller rather than an overlay (the finder has no other mode now); library search and the BGG escalation are unchanged; the offline branch is gone — a failed `/search` falls back to the device pool instead of a check taken before the request. The Game card also surfaces the three most recently played games as tappable tiles, which used to be invisible until the search input took focus. **Each player row carries a drag handle: hold it and drag to reorder the roster.** The players array *is* the scoring grid's column order — `round-score-grid.js` maps it straight to the columns with no sort anywhere — so moving a row here moves a column there, and the order is pushed to the lobby (`PUT /participants/order`, debounced 300ms and flushed before the phase advance, since the RPC is Gather-only) so every spectator's mirror follows. The gesture lives in `widgets/player-reorder.js`: one *delegated* pointer machine per `<ul>` (the poll rebuilds the rows with `innerHTML`, which would orphan per-row listeners), pick-up after a 120ms hold or 3px of movement *on the grip only*, a fixed-position clone with the live input values copied across (`cloneNode` copies the value attribute, not the property), and the dragged `<li>` moved through the live list as the pointer crosses each row's midpoint — the list parts around it, so there is no separate drop indicator to keep in sync. The lobby poll stands down while a drag is in flight (`PlayerReorder.isDragging()`) because its repaint would replace the row under the user's finger, and a capture-phase click swallower stops the post-drop synthetic click from hitting whichever row landed there. `_movePlayer` repaints both index-keyed surfaces rather than patching them, because `_patchScoringCells`, `_refreshTotalsCells` and `_setInitials`'s `heads[i]` all address columns positionally. A session code opens on entry and is shown at the top of the screen; other phones can join via code while the host is on Gather. Joiners stream into the player list via polling.
   - **Play** — scoring grid on top, full-width reference guide below. (It was the other way round until the guide's parchment scroll, open by default, grew long enough to push the grid off the first screen: the grid is what the host touches every round, the guide is what you reach for occasionally, so the thing you use most is the thing you don't scroll to. The spectator mirror carries the same order.) **The host is the only person who scores.** They have full grid access (add rounds, override winners) and every cell they touch streams one-way to everybody else via Supabase Realtime against `boardgamebuddy_play_session_scores`; joiners and spectators get the same grid, read-only, and cannot write at all (RLS enforces it — migration 053). Guests are on the table like anyone else: scores are keyed by participant row rather than by account, so a guest's column streams too. Scores may be negative; a "± Negative" header toggle (default off, remembered) reveals per-cell +/− sign buttons for keyboards that lack a minus key.

     **Tapping any column header switches every column between the player's bubble and their name, and the choice is remembered.** One preference (`RoundGridNames`, `bgb.scoring.headerNames`) shared by the host grid, the spectator mirror and the play-detail popup, so the next game opens on the last setting. It is an *override*, not a default: while the key is absent each surface keeps its own starting look (the live grids on names, which is what you scan mid-game; the popup on bubbles), and the first tap anywhere settles it everywhere. The header button mutates the `is-named` class on every `.scoring-head` in the document directly rather than routing through a host repaint — the two states differ by one class, so there is nothing to rebuild, and an `outerHTML` repaint would reset `.scoring-table-wrap`'s horizontal scroll (snapping a 6-player grid back to column 1), blur whatever cell was being typed in, and hand the read-only spectator mirror a host contract it has never needed. Reading the preference at paint time is also what makes the choice survive the repaints that used to silently reset the old per-column toggle: a round added, the ± pill, a play-mode change, a player added, or the popup's re-render on every keystroke.

     Joiners used to own their own column. Collapsing that to host-only removed the whole reconciliation problem it created — the per-column edit mode in the grid widget, the caret-preservation dance on every repaint of the mirror, the two-principal RLS policy, and the finalize-time merge of "what the host typed" against "what joiners streamed in" that migration 052 existed to un-break.

     The read-only grid is the same widget in its other mode: same columns, same score font, same round labels, same Total row, minus the input chrome. Read cells carry `.scoring-cell--read` and deliberately **not** `.scoring-cell` — the border/fill/radius there is input chrome, and a table of boxes nobody can type in reads as a different component.

     **The mirror is built out of the host's screen, card for card.** The spectator's Play step carries the same cards in the same order the host sees: the game (`Now playing`), the session code, the scoring grid, then the reference guide (with the game's Rulebook CTA — the bundle has carried `rulebook_url` all along). Both sides use the same `.cascade-card` / `.cascade-invite` / `.cascade-game` families and the same three-column screen header, whose left 44px slot rolls the phase back for the host and leaves the session for the spectator. Two things went the other way: the crumb bar that used to sit above the cascade (`Session {code}`, the view's only back affordance) is gone — the code has its own card now and the back arrow moved into the screen header — and `<main data-view="session-viewer">` dropped its `px-4 py-4`, which had been stacking on top of `.cascade-screen`'s own 12/16px gutters and squeezing every spectator card, the scoring grid included, narrower than the host's.

     **Watching a session is what earns the live grid — being seated is not.** Reads on `boardgamebuddy_play_session_scores` and `boardgamebuddy_play_sessions` are scoped to host **or** seated player **or** watcher (migration 027). The viewer screen registers the watch on open (`POST /sessions/{code}/watch` → a row in `boardgamebuddy_play_session_viewers`), so a spectator who joined after Gather — no participant row, since `bgb_join_session` only seats during Gather — reads the same table and gets the same Realtime stream a seated player does. **Writing is untouched and still host-only** (`bgb_session_scores_write`: phase='play' AND you are the host). Watching is deliberately its own table rather than a seat: the participants roster is what the scoring columns and the finalized play's player rows are built from, and a spectator seated there would become a column in everyone's grid and then a player on the saved play. The policy was **not** broadened to all authenticated users either — an unfiltered grant would let anyone list every open session's scores, host ids and 5-char join codes; a viewer row keeps the read addressed to sessions you actually opened. Two older mechanisms stay as the fallback for a client whose watch never landed (an API older than the deployed web app, or a failed POST): `bgb_session_bundle` folds a `scores` array into the (unauthenticated, code-as-token) `GET /sessions/{code}` response while phase='play' (migration 054) and `LiveScores.seed()` takes it; and the session viewer's poll drops to a 4s cadence on that seeded path (`isSeedOnly()`), because there the poll *is* the live channel and the "Realtime is carrying it, stand down" gating would freeze the grid. A readable table always wins over the seed, so an empty read from a client that can see the table means "the host cleared it", not "fall back to a stale bundle".

     **The Total row is the visible cells, added up — always.** `widgets/round-score-grid.js` owns the one implementation (`window.roundGridTotal`), summing the same `getCellValue` resolver over the same round count it just rendered; there is no "total resolver" opt for a caller to supply its own arithmetic, and any surface that repaints the totals row between renders (the host grid, the joiner's mirror, the play-detail popup) calls that same helper. Two rules keep it honest upstream: every player carries a dense `roundScores` array of the grid's full length (`_normalizeRoundArrays`), and a typed edit repaints the total from local state *before* mirroring to Realtime, never awaiting the write. On Save the host folds the live overlay into its own draft (`_commitResolvedScores`) so the recorded play is the grid that was on screen, and `PlayerEntry` on the backend re-derives `score` from `round_scores` whenever a breakdown is present.
   - **Settle Up** — host only. Date, a **Where** card, optional photo upload + "Key moments" notes textarea (reuses the play's `notes` column), then Save. The Where card arrives already filled in — `domain/geo.js` resolved the country from the device timezone when the draft was born — and opens `widgets/country-picker-sheet.js` (search matches the localized country name *and* the raw code, with a pinned "Don't record a country" row above the results). It is shown rather than recorded silently on principle: a value the app writes onto a play and never admits to is not a thing this app should have, and showing it is what makes it correctable, which is the only way the eventual by-country numbers are worth reading. Save calls `/sessions/{code}/finalize` which merges live scores into the canonical play and marks the session finalized.
   When the host advances Gather→Play, the lobby closes (`POST /sessions/{code}/join` returns 409 thereafter). When the host enters Settle Up, every non-host joiner sees a polaroid splash popup centered on the screen with the game thumbnail and current winner; tapping the X dismisses to a refreshed feed.
   **The host's Save doesn't wait for anything.** Tapping Save puts the same "Well played!" polaroid up in the same frame, with the host-only **Another round?** and the corner **X** live immediately, and runs the finalize behind it (photo uploading *in parallel* rather than after). The card carries no save state at all: the upload queue guarantees the play is recorded, so there is nothing for the host to watch. A failed write — any failure, not just a network one — hands the play to `domain/outbox.js` under the same `client_key` the live attempt carried, so a request that actually landed and only lost its response can't be written twice; the header's upload indicator owns it from there, and the card says "Saved on this device" if it's still up. The one case that stops the host is the queue write itself failing (no room in localStorage): that gets a modal and puts the draft back on Settle Up. A failed photo upload is still just a warning line on the card. **Another round?** opens a *new* session pre-seeded with the same game, expansions, play mode and roster — teams included, scores and winner reset — landing on Gather under a new code. Because it can now be tapped mid-write, two things are guarded: every post-write touch of view state is skipped when the draft it belonged to has been replaced (`_isStaleSave`), and the new lobby's `POST /sessions` waits for the previous write to settle (bounded at 8s) — `bgb_create_session` abandons the host's other open sessions, and minting early would close the lobby the finalize is about to write to, leaving spectators on 'abandoned' instead of their wrap-up card. The carried-over roster is pushed to the new lobby as participants, so the previous joiners see it in their Join list.
   The draft auto-persists to localStorage (metadata only, plus current phase); the photo blob stays in memory. The chooser surfaces a "Resume hosting?" banner when a non-terminal draft exists.

   **The roster reaches the lobby however the run started.** `POST /sessions` seats only the host, so every other player needs an explicit participant row before anyone else can see them — and since migration 053 keys live scores by participant, a player without one has *no column at all* on a spectator's screen, not merely no name. That row used to be pushed only by `_addPlayer`, one player at a time, plus a bulk `_syncRosterToLobby()` on two paths that both required the lobby to have been *replaced*. A run that arrived already holding a roster therefore never pushed it: `_ensureLobbyOpen` guards its bulk sync on `priorCode`, which is null on a fresh draft, so **Another Round** on the Play tab (`log-play-view._anotherRound`, which seeds the whole roster from the last play) minted a lobby containing one row. Spectators watched a six-player game as a one-column grid with nothing in it. Four things close that now: a fresh mint pushes the roster it was born holding; `_syncRosterToLobby()` awaits `_lobbyReady()` instead of bailing when the code hasn't landed yet, and is single-flight so the poll, the mint and the phase advance share one batch; the Gather poll re-pushes anyone still missing a row (bounded by `ROSTER_RECONCILE_MAX`, refilled whenever the pending set changes size, because `_withLobby` swallows every failure that isn't a 404/410 and a dropped POST would otherwise cost that player the whole game); and `_advancePhase` flushes the roster **before** the gather→play PATCH, because `bgb_add_participant` is Gather-only and answers `roster_locked` afterwards. `POST /participants` returns the whole bundle, so each push adopts its own `participant_id` immediately rather than waiting up to 2s for the poll to match it back by name, and the grid is republished once the phase reaches `play` so cells typed under a late-arriving id still reach the table. Stale ids are cleared on entry when the run's code has changed — deliberately *not* in `_resetRunState()`, which also runs on a plain refresh, where a host who reloads mid-Play holds ids that are still valid against a roster that is now locked. `_onLobbyReplaced` re-adopts the host's own row from the replacement bundle for the same reason: it clears every id, `_syncRosterToLobby` skips the host by design, and mid-Play the Gather poll is disarmed, so the host's own column would otherwise stop streaming.

   **The lobby is a nice-to-have; recording the play is not.** Nothing about the session code can stop the host from playing and saving — the cascade runs off the draft, and Save falls back to `POST /plays` when there is no usable code. Every `/sessions/{code}` write goes through `_withLobby()`, which on a *definitive* dead-lobby answer (404/410/403/409, and the 400 for a transition out of a terminal session) drops the lobby, mints a replacement and retries once; a blip (offline, 5xx) is left alone, because minting abandons the host's other open sessions and reacting to a hiccup would kill a live one. Healing is single-flight (`_healLobby`) — `_syncRosterToLobby` fails N writes at once, and without it each would mint a session that abandoned the one before it. When the code does change mid-run, `_onLobbyReplaced` clears the now-dangling `participant_id`s, re-pushes the roster, restarts live scores, and the invite card says *"New code — share it again"* for a few seconds. No toast, no modal: the swap can happen while the host is typing in the scoring grid.

   `PlayFlowView` is a singleton, so `onMount` drops `_lobby` unless it still matches the draft's (or the URL's) code — `_resetRunState()`. Without that a finished session's code survived into the next one: `_lobbyReady()` short-circuits on `_liveLobbyCode()`, so `_ensureLobbyOpen()` never re-ran, the invite card showed a code nobody could join, and Continue bounced off a 404 with the phase rolled back. `_advancePhase` no longer rolls back or reports at all — the local phase is the truth the host is looking at and the lobby only mirrors it.

   **Recording a play offline.** This is the *only* place in the app where being offline is a concept the user is told about, and the scope is deliberate: it is the one flow that genuinely changes. The same three screens with the entire lobby subtracted — no `POST /sessions`, no code, no 2s poll, no Realtime, no phase PATCH, no photo. All of that exists to serve joiners, and there can't be any without a server. What remains already ran locally: the game and player picker sheets paint from `bgbCache` (`game.recent` / `buddy:all`, warmed by `/bootstrap` at 24h fresh / 7d stale), the draft lives in localStorage, and Save hands the play to `domain/outbox.js` instead of the API. The host is told two things and no others — **the play saves to this device and uploads next time you're online**, and **scores won't sync live** — in exactly two places: the Gather invite card (`_renderInviteCard`) and the Play step's game-info strip (`widgets/game-info-bar.js`, `state: "offline"`). Both sit in the slot the session code would have occupied, so the notice is where the missing thing was.
   - **Everywhere else there is no offline mode at all.** `domain/net.js` is internal truth, not something the app renders. There is no banner, no switch, and nothing that disables itself or hides because the latch is set — that was the old design, and it answered questions nobody had asked and was wrong every time the latch was stale. Instead **every action is attempted**, and one that turns out to need the network says so, naming the action: `helpers.js#notifyRequestError(err, action)` → *"You're offline — joining a game needs a connection."* Screens holding cached data keep showing it and say nothing, because a cached feed is an answer and a toast on top of it is noise. `api.js#_fetch` short-circuits while the latch is set, throwing the exact shape a real network rejection throws, so the failure is instant instead of 15 seconds late and every call site still handles one path rather than two. The one throttled exception is the game picker, where every keystroke is a search: it says it once per open, not once per row.
   - **Entering — entirely automatic, never chosen.** `domain/net.js` (`window.BgbNet`) is the single source of truth. Two signals decide: `navigator.onLine === false`, and **two** consecutive `fetch` network failures (two, not one — a single request can fail for reasons unrelated to the link, and flipping the whole app on that is worse than the problem). A completed HTTP response outranks both: it is direct proof of reachability, so it overrides a stale `navigator.onLine === false`, which would otherwise strand the app with no way out since every probe would be judged by the flag it was trying to correct. The Play tab's cards are identical online and offline — only the Host card's copy changes. `PlayFlowView` latches the answer once at mount so its guards can't disagree mid-cascade; **Save is the one place that re-checks**, so a host who walked back into signal gets a live write.
   - **Every request has a deadline** (`domain/api.js`): 15s for JSON, 60s for a photo upload, with one automatic retry for a stalled `GET` on a fresh connection. A dead network *rejects* and the app recovers; a stalled request never settles at all, and no browser imposes a timeout worth waiting for — so one stalled first-paint call used to be the whole app, hanging on a loader with no error and no retry (reported from an iPhone's first launch of the freshly-installed PWA). A timeout is normalized into the same shape as a network error (`err.offline`, `err.status = 0`, plus `err.timeout`) and counts as one strike toward offline mode: a link on which requests never complete is offline as far as this app is concerned, and the outbox's `client_key` de-duplicates a write that may in fact have landed.
   - **Leaving.** Four paths, all converging on `BgbNet._publish()`'s offline→online edge, which is also the single place the outbox is drained: the browser's `online` event, any ordinary request succeeding, the backing-off auto-probe ladder (5s → 60s, only while the page is visible), and **any request the short-circuit blocks**, which kicks a probe of its own. That last one is what replaced the offline banner's *Try again* button: with the banner gone, the user's own retry tap is the active probe, so a first tap reports and a second one goes through if the link really is back. It is throttled to the ladder's own first rung so a background poller that forgot to stand itself down can't turn it into a continuous probe. The probe hits `GET /health` (unauthenticated, and mandated on every project by `.claude/rules/backend-python.md`, so it can't fail for a reason that isn't connectivity) and passes `allowWhileOffline` so it isn't short-circuited by the very latch it exists to clear; any status counts as reachable, since a 500 still proves we got there.
     - **Known gap:** on a connection that resolves and then times out (captive portal, one bar), auto-detection has to wait for two requests to actually fail, so the host sits through those timeouts before the app flips. Narrower than it was: until the latch sets, the cost is those two requests rather than a whole app painted as offline. A per-request timeout would close it, but not a blanket one — a photo upload on bad mobile upstream can legitimately run long.
   - **Uploading.** `domain/outbox.js` (`window.Outbox`) queues finished plays in `localStorage['bgb_outbox_v1']` — deliberately NOT a `bgbCache` namespace, which evicts its oldest 25% under quota pressure. Each entry carries a `client_key` UUID and the account that recorded it (a shared device must never file one user's play into another's history). `flush()` runs on boot once a profile load reaches the server, on the `online` event, and on the debounced tab-focus refresh. A network failure stops the loop with everything intact; a definitive 4xx parks that one entry as `failed` so a bad play can't wedge the queue behind it, surfaced in Settings → Pending uploads for manual discard. The queue is also where a *live* write goes when it fails, not just an offline one — see the host's Save above. When a flush lands anything it re-pulls the feed's first page and dispatches `plays-uploaded` carrying it, so a feed the user is sitting on splices the new play in rather than showing it only on the next mount.
   - **What fails, and how each one says so.** Joining (the lobby is server-side; the code field and Join button stay live and a tap toasts), signing in (the auth screen's own error line, since an auth SDK carries none of `api.js`'s error normalisation and the message has to outlast a toast), BGG search/import, and live scores and photos inside the cascade (the blob is never persisted, so a queued play can't carry one — said up front on Settle Up, because the host would otherwise attach a photo that quietly never reaches the play). Picking a game degrades rather than fails: `PlayCreate.game_id` is required and the catalog can't be searched, so a failed `/search` falls back to the device pool — `game.recent` plus every warmed `game.bundle`, i.e. the user's whole owned collection — which is what the picker paints provisionally on every keystroke anyway. The reference guide keeps working: its chapter and template reads take the full stale window unconditionally (`Chapter.cachedMyChapters(..., { stale: true })`), because a guide cached yesterday beats an empty scroll at the table, while the *freshness check* behind `prefetchMyChapters` deliberately does not — a stale entry must not look like a reason to skip the refresh that would replace it.
   - **Cold start.** `web/sw.js` precaches the app shell so BgB opens from a home-screen icon with no signal at all; without it the feature would only work for people who left the tab open. See Active Development Notes.
4. **Game Search** (search pill on Feed/Profile): single ranked list — collection hits first, then DB matches. A "Search BoardGameGeek for more" button appends BGG hits on demand. **Expansions never appear here** — base games only, on every source. They live in the base game's Expansions section instead.
4b. **Profile → Achievements** (`/profile/achievements`): twenty-three medallion badges of the BoardgameBuddy character, grouped into At the table (10 / 100 / 300 plays logged, a two-player-only game, and a five-player table), On the road (plays in 2 countries, plays on 2 continents, plays in 5 countries — from `plays.country_code`, which the client resolves from the device timezone, so these start at zero for everybody and fill forwards; a country with no continent in `boardgamebuddy_countries` still counts toward the country tiers), Victories (10 / 100 / 300 wins, then the same win narrowed to the mode the table was playing in — 20 wins in **team** plays and 20 in **co-op** plays, the second being the table beating the box rather than each other. Both sit at 20 with no first-win tier under them, because a badge for the first team or co-op win fires on the night somebody first ticks a box on the log screen, which is a fact about the UI rather than about the evening. The mode comes off `plays.play_mode`, not the game's, so a co-op game played in a competitive variant counts as what the table actually did, and both are strict subsets of the 10/100/300 tiers, which keep counting every mode), The reference guide (1 / 10 / 50 chapters kept, a chapter of yours that someone else keeps, a play you recorded on a custom scoring grid, and a scoring grid of yours that 5 other players keep — the last of those is a MAX over your own grids rather than a sum, so "Gold Standard" means one grid everybody uses) and Making it yours (first buddy, notes on a logged play, the BGG link, the app installed to a home screen). Every badge but one is derived from data the app already writes; the install is reported by the web app itself, because an installed PWA is indistinguishable from a browser tab server-side. Earned badges are **permanent** — the unlock row is what `earned` reads, so deleting a play later does not take the badge back. Each group is one horizontally-scrolling rail, ordered done → in progress → not started. Locked badges keep their art (desaturated) and print what they still want; tapping any badge opens its detail sheet, which shows the same grey medallion plus the badge's flavour line and what it takes to earn it. **Earning a badge mid-session pops an "Achievement unlocked!" polaroid** (`ui/polaroid-popup.js#achievement`, queued by `ui/achievement-popup.js`): the medallion as the photo, the name and flavour line under it, and a **See my achievements** CTA that jumps straight to the spoke. The writes that can move a badge schedule the check (`Achievements.invalidate` → `scheduleUnlockCheck`, debounced 1.5s) rather than anything polling. The queue waits for a clear screen before showing anything — the commonest way to earn a badge is finishing a game, which is the one moment the app is already showing the "Well played!" wrap-up card, and `PolaroidPopup` is a singleton — and it shows several unlocks one at a time with a "2 of 3" counter. Nothing pops while the user is already on the Achievements spoke.
5. **Game Detail** (tap any game card): box art hero, status pill (a labelled `--lg` variant of the app-wide status tag — tapping it opens the same bottom-sheet radio group every other surface opens, not a cycling toggle), Log a Play button, BGG + Rulebook links, Expansions section, a rolled-up parchment **Reference Guide scroll** (tap either roll to open/close), and recent plays. The scroll is per-user per-game and starts empty; tap **Add a chapter** at the bottom to either Create a new one or Browse the community pool.

   **Your stats** sits between the scroll and the recent plays — a win-rate ring, then plays, wins, average winning score, your average and your best, over every play of this game the viewer logged or sat in. It is `web/ui/game-stats-panel.js`, the same renderer the Stats spoke's *By game* card uses, fed by the detail bundle's `viewer_stats` block (migration 030) rather than by a second fetch — so the ring here and the ring one tap into the profile are the same number by construction, down to migration 020's rule that a play nobody won and nobody scored is a blank rather than a loss. A game the viewer has never played renders no section at all: an empty ring and five dashes are not an invitation to play it, and the hero already carries the affordances that are. The panel is written for the spoke's paper card, so the one thing this screen adds is a card of its own in the theme re-point list (`.game-detail__statspanel`, `.claude/rules/theming.md` §6) — the ground tokens would invert it.

**Add games** (the `+ Add` on the Collection spoke, `/games/add`): the whole BgB catalog as one alphabetical scroll, 30 rows a batch behind the shared scroll sentinel. The back row, an **"Add to:"** label with the Collection / Wishlist pills, and the search box are all pinned to the top of the screen — the label is the screen's whole explanation, and the shelf the pills select is what every row's + writes to, so neither may scroll away from a list this long. Each row is a game tile that opens the game page, with a quick action beside it: **+** puts the game on the active shelf, **✓** means it is already there and takes it off. A game sitting on the *other* shelf (or one you've only played) says so in a chip, and the same tap moves it — `POST /collection` upserts on (user, game), so wishlist → owned is one tap, not a remove and an add. The Collection ↔ Wishlist toggle at the top retargets every button without a single request. A search box narrows the catalog server-side; below it, **Import from BoardGameGeek** opens the import sheet for the one case a catalog scroll can't cover — a game BgB has never imported.

**Import from BoardGameGeek** (`widgets/bgg-import-sheet.js`) is a bottom sheet, and it **opens on the search you already ran**: reaching that button means the catalog came up empty on it — the button says so — so the query comes along, prefilled and already running, and the sheet lands showing BGG's answer rather than an empty box. Reopening on an unchanged query keeps what is on screen instead of spending a second round trip; a changed one, or a query the last search came up empty on, re-runs. Otherwise the search in it is an explicit act rather than a keystroke: hitting **Search** blurs the field, so the software keyboard collapses and the panel grows into the space it gives back — results land in a list that is nearly the whole screen. The box takes a **title, a BGG id, or a pasted boardgamegeek.com link** — the number off a shelf label or a forum post reaches the game directly, which BGG's own name-matching search cannot do. Every row prints its `#id` beside the year, which is also what makes a numeric search legible: search `1830` and the game with that id comes back alongside the game with that name. The row's second line carries only what its button does not already say — the year, the id, `Expansion`, and then either why an import failed or which shelf it landed on.

**Expansions appear here, ranked below base games** rather than excluded as they are everywhere else. This is the one screen whose job is reaching what BgB doesn't have, and an expansion is one of those things; importing one records its `base_game_bgg_id` exactly as the dedicated expansion import does, so it lands under its base game. It has no step two — expansions are never top-level shelf entries — so the row stops at **In library**.

The list is **windowed at 25 rows a batch**, revealed on scroll with a count line underneath (`Showing 25 of 412`). Everything is already in memory, so a reveal is a synchronous append with no request behind it — an append rather than a repaint, so a row mid-import keeps its animation and the scroll position holds. `ui/infinite-scroll.js` is deliberately not used: it observes against the viewport, and this list scrolls inside a fixed panel. Each result carries one button, and it names which of two steps it is. **Import** pulls the game into the *shared library* and stops there; the row then offers **Add to collection** (or wishlist, whichever shelf you came from) as a second, separate tap. Importing has never put a game on your shelf since — looking up whether BgB has something is not the same act as owning it.

An import is `domain/bgg-import.js`'s, not the sheet's: it keeps running when the sheet is closed, and `ui/bgg-import-toast.js` pops a notification when it lands — carrying that same **Add to collection** button, so step two is still reachable from wherever you have got to. While a job is on the wire its row sweeps a progress bar along its bottom edge, because a BGG fetch takes seconds of BGG's own throttling and a static "Importing…" reads as a hang.

**Expansions section.** Rendered on every base game — on the Game Detail page (a reel of expansion polaroids) and on the host's Gather card (a collapsible toggle list). The Gather list caps at five visible rows and scrolls, with a sliver of the sixth showing so it reads as scrollable; past five rows a client-side filter field appears above it (with a × to clear), matching the displayed label or the stored full name so typing the base game's name still hits. Import expansions sits *below* the scroll box, so it stays reachable however far down the list you are. Both carry an **Import expansions** button, and it stays available when nothing is imported yet. It opens `widgets/import-expansions-modal.js`, which lists the expansions BoardGameGeek links to this game that BgB doesn't have (`GET /games/{id}/expansions/available`); each row's name has the base game's name stripped off the front, and a **+** imports it into the catalog and pins it to this base game. A filter field above the list narrows it by name — the whole list arrives in one response, so filtering is client-side (no debounce, no second request) and matches both the displayed name and BGG's full name, so typing the base game's name still hits. Rows arrive most-owned-on-BGG first and carry an owner-count chip so that order is legible; the client never re-sorts (filtering preserves it). Rows with no count, and rows nobody owns, sit at the tail without a chip. Escape backs out of the filter before it closes the popup. Import is catalog-only — it doesn't touch the caller's collection. On the Game Detail page the new expansion appears in the reel as soon as the import returns — the endpoint answers with the finished `ExpansionListItem`, so the reel takes it directly (name-ordered, matching the bundle RPC) and only that section repaints, with a forced bundle refetch reconciling in the background. Since expansions are hidden from search, this popup is the only way one enters the catalog, so the base game has to be imported first.

**Expansion count badge.** Collection tiles carry a `git-fork N` chip counting every expansion **the catalog holds** for that base game — the same number as the game page's "Expansions (N)" heading, tooltip "N expansions in Boardgame Buddy". It used to count only expansions the viewer *owned*, which read as zero for a game with eleven of them, since importing is catalog-only. The count rides on `game.expansion_count`, which `bgb_collection_shelf` computes in SQL — so the badge is correct on the first cached paint. (It previously came from `/collection/grid` only, and the profile-bundle seed doesn't compute it, so the badge used to pop in when the grid fetch landed.) Feed rails still show the owned count (their rows come from `bgb_hot_games`, which doesn't carry the total) — their tooltip says "owned", so the two stay truthful.

**Expansion labels drop the base game's name** wherever the base game is already the surrounding context: the Game Detail reel, the host's Gather picker, the reference guide's expansion chips, and a play's expansion list. "Carcassonne: Abbey & Mayor" reads as "Abbey & Mayor" there. This is display-only via `stripBaseGameName()` in `web/helpers.js` (the frontend twin of the backend's `_strip_base_prefix` — keep the pair in sync); the stored name is untouched, the full name stays on the element's `title` and on the `gameName` navigation param, and every other surface — the expansion's own page, collection, search, feed, plays — shows it in full.
6. **Reference guide chapter add**: full-screen view. **Browse** searches the per-game pool (sorted by popularity, tap + to add); each row also carries the actions its viewer is entitled to: **Edit** and **Delete** for the chapter's creator (Delete for an admin too, matching `DELETE /chapters/{id}`, and gated behind the destructive confirm), **Report** for everybody else. **Create** is a three-step wizard sharing one fixed keyboard-safe shell, with a step counter + segment bar (`web/ui/wizard-progress.js`, shared with the play importer) above the body and a two-button footer below it. The shell hides the global header and the bottom nav under itself, so it draws its own way out: a **×** beside the game chip, present on every step and in Edit, which is Cancel exactly — same method, same discard. The footer's two slots belong to the step's own moves (its backward one and its forward one), which is what lets step 2 spend both on Skip / Generate. Every exit — the ×, Cancel, backing off the front of step 1, and the device back gesture — goes through `_exitEditor` and lands where the user came from: Browse for an in-view entry (the FAB), and a router pop back to the opening screen for a routed one (`mode=edit`, `mode=create&layout=scoring_grid`). **Only the in-view wizard arms the back guard** — it is a mode of the Browse screen and needs an entry of its own; a routed wizard already has the screen's entry, and arming a second one over the same url made leaving a race between two unwinds (`.claude/rules/overlays.md` §8b):
   1. **Pick type** — the seven chapter types as 56px rows, plus the "Save to" expansion-target selector when expansions are in scope. **Scoring Grid Template** is the first row: the list is ordered by the lookup table's `display_order` and the grid type is seeded at 5, above Setup's 10, so the thing you reach for mid-game leads the list with no client-side special-casing. There is no second question underneath — the layout follows from the type, 1:1, derived in `_pickType`. Continue reads "Pick a type" and stays disabled until one is chosen. Cancel — and backing off this step with the device gesture, which is the same exit — leaves the wizard for wherever it was opened from.
   2. **Head start (optional)** — an optional free-text focus prompt (≤500 chars) and nothing else in the body: the step's two exits are its footer, **Skip** and **Generate**. Generate jumps to step 3 on success; a failure keeps the user here with the error and the prompt intact. Back from step 3 preserves the prompt, so tweak-and-regenerate is two taps. There is no footer Back — the picked type shows as a chip with a **Change** link to step 1, and the device back gesture still walks the steps. Leaving the wizard outright from here is the × above, which is the reason this step can give both footer slots to the decision. **A scoring grid gets this step too** — it used to skip it, back when the only drafter wrote markdown — and gets it from the same pure function with a `grid` flag, because the decision is identical and only the noun changes. What the flag swaps is copy: the lede offers to *rough out the scoring rows* and **says the model is small**, the field asks *"Anything it should know?"*, and Generate reaches `_onGenerateGrid` (`POST /chapters/generate-grid`) instead of `_onGenerateAi`. **When the save target is an expansion, the step also carries the add-on / replace control** — the editor's own `ScoringTemplateEditor.renderMode`, the same renderer step 3 uses, over the same `_formGridMode` and the same `_tmplSetMode`. It is here because it is an INPUT to the draft, not decoration: a drafter that has not been told which shape it is writing writes the wrong document, and the author answers the question once wherever they meet it first. Both drafters stamp the same `_genSeq`, deliberately: a wizard is one layout at a time, and a second token would let a stale chapter draft land on a grid the author switched to. Overwriting rows already named goes through `PolaroidPopup.confirm()` — the seeded blank row is not a draft — and a landed draft clears any open colour picker, since the row it was opened on is gone.
   3. **Edit** — title, Write/Preview toggle and the markdown editor. The chosen type shows as a read-only chip with a **Change** link back to step 1. The toolbar's trailing group holds the two document-level actions: **Import a file** and the authoring guide. Import opens a bottom sheet (`web/widgets/chapter-import-sheet.js`) that takes a `.md` or `.txt` file and drops it straight into the editor — a leading `# Heading` becomes the title, the rest becomes the body. Overwriting an already-drafted body — by Generate or by Import — goes through the project's `PolaroidPopup.confirm()` first.

   Steps 1 and 2 are pure-function bodies in `web/widgets/chapter-wizard-steps.js`; step 3 stays in the view because its toolbar reads and writes the live textarea selection. All three steps are walked by **every** layout — the grid's old 0 → 2 jump, its mirror in `_wizBack` and its two-of-two step bar are gone, so the counter reads "of 3" whatever is being authored. The device back button walks the steps rather than popping the view (one `ui/back-guard.js` guard for the whole wizard, re-armed from its own close).

   **Edit does not enter the wizard**: `mode=edit` and the browse-row Edit both open step 3 directly, with no step bar and with the horizontal type pill scroller instead of the read-only chip — the chapter already has a type and a body, and re-drafting over it is not what Edit is for.

   **Scoring grids** (`layout='scoring_grid'`, migration 018) reach step 3 either empty-handed or carrying an AI draft of their rows (step 2 above), and replace step 3's markdown editor with a row list (`web/widgets/scoring-template-editor.js`): one card per scoring category, each a *Row Name* field, a colour chip, reorder chevrons and a remove ×, over a live preview rendered by `window.renderRoundGrid` itself so the author's picture and what a scorer sees cannot disagree.

   **A grid has no title field, and no name of its own.** The backend derives one from the game (`services/chapter_grid.grid_title` — "Everdell score sheet") on create *and* on every edit, so a renamed game re-titles its grids and a grid authored before the field was retired is normalised the next time it is saved. Naming was the wrong question: a grid belongs to one game, a player keeps at most one per game, and the pool already sorts by `popularity DESC` and prints the author under every row — which is what a reader actually chooses on. `ChapterCreate.title` is therefore optional for (and only for) a grid; a text chapter still 422s without one. The picker sheet leads its rows with **whose** grid it is (*Your grid* / *Dan's grid*) rather than with a title every grid for that game would share.

   **The colour picker is a disclosure, not a permanent radiogroup.** The ten swatches used to sit open under every row, costing 52px each — more than a phone screen of them on a full twenty-four-row grid, for a decision each row is done making after one tap. Now the row carries the chosen swatch as a chip in its header; tapping the chip opens the 5×2 picker under that row, and picking a colour folds it away again. A row added by hand (or the first row a new grid is seeded with) opens on the picker, because it has no colour yet. At most one picker is open at a time, and the open index lives on the *view* rather than inside the row objects — those get posted to the server.

   **Each row takes an optional description** — how that row is scored, in the author's words, up to 200 characters (`ScoringRow.note`, which the model has carried since 018 with nothing authoring it). It is a template feature and never a play one: it does not print in the row header, and reaches a reader only through an **info button on the row's label** — in the scoring grid, in the browse pool's expanded row, and in the guide's own Scoring section, all three of which draw the same grid through `ScoringTemplateEditor.preview` — which opens the text in `PolaroidPopup.alert`. That is why the whole label cell is the button rather than the glyph — a grid row is ~36px tall, so nothing inside one can carry a 44px target vertically, and width is the only dimension there is any to buy back. In the editor the description is one 28px line under the label in all three of its states (absent, written, being written), so a grid whose rows need no explanation pays almost nothing for the feature. A grid **walks step 2 like everything else** and its bar reads 3 steps: it used to skip that step and count two, back when the only drafter there wrote markdown against `CHAPTER_AUTHORING_GUIDE` — which a grid has no use for — but it now has a drafter of its own (`services/chapter_grid_ai.py`), so the step's question applies and `chapter_ai.py`'s sync obligation is still untouched. The markdown toolbar, the Write/Preview toggle and Import do not render. The type is fixed at `scoring_grid` and read-only even in Edit: a grid stranded under another type is a 400 from the backend's `chapter_grid.validate_layout_pairing`, which checks the pairing in both directions. Edit's type scroller leaves the grid type out for the mirror reason — converting prose into a grid would throw the prose away, and PATCH cannot clear a `grid` to make the trip back.

   **The round-label column pins, like the header row.** A six-player table is wider than a phone, so scrolling right to reach the last column used to carry the row labels off the left edge — a screen of bare digits with nothing saying which row is Prosperity and which is Events. It is now `position: sticky; left: 0`, the horizontal half of what `.scoring-table thead th` already did vertically. Three cells are sticky on **two** axes at once (the corner cell, the totals band's label, and — where they meet — nothing else), and equal-`z` cells settle on document order, which is the wrong answer for every corner; so the table carries one documented z ladder: score cells `< 2` round labels `< 3` totals band `< 4` totals label `< 5` column headers `< 6` corner cell. Every pinned cell also has to be **opaque**, which is why `.scoring-table tbody th` moved its `opacity: 0.7` onto the ink — a faded sticky cell lets the score columns ghost through the label sliding under it. That repair was already written twice (the totals label, the tinted template row) for exactly this reason; it now lives once, in the base rule. The column rule at the pinned edge moved from column 2's `border-left` to column 1's `border-right` so it travels with the column it belongs to — same pixels, and `nth-child(n + 3)` picks up where `:not(:first-child)` left off.

   **Adopting one changes the scoring table.** With exactly one scoring grid in the viewer's guide for the game, the Play step's grid opens already labelled and tinted, its rows locked (no remove ×) while **+ Round** still appends removable extras below them and keeps absolute numbering (R7 under a six-row template — the number a row shows is its `round_index`, which is the key live scores are stored under). With two or more, nothing auto-applies and a bottom sheet (`web/widgets/scoring-template-sheet.js`) picks *which*. Auto-apply is refused on a grid that already holds numbers, so a resumed draft is never restructured under the host. The play keeps a **snapshot** of the rows it used, so the play-detail popup and the spectator's mirror render the same labels forever, independent of what later happens to the chapter.

   **The template is a switch, not a one-way Clear.** The strip above the grid names this game's template and carries an on/off switch (`web/ui/switch.js`); *Change* joins it only when the guide offers two or more. Off is immediate and non-destructive — the rows and the scores stay exactly where they are, only the labels go — and on goes through the same confirm a Change does, because relabelling rows somebody has already scored into is the same event either way. It replaced a **Clear** link that was a one-way door: with one adopted grid, clearing removed the only control on the strip, so the labels could not be put back for the rest of the game, and a template auto-apply had declined (a resumed draft with numbers on it) rendered no strip at all — the same dead end reached from the other side. Flipping back on restores the grid that was last on rather than a guess; where there is no such history and the guide offers several, the switch opens the picker instead of choosing for the host, which is the guess auto-apply already refuses to make. Off is a **persisted field of the draft** (`scoringTemplateOff`), not the absence of a template: `scoringTemplate === null` alone cannot tell "nothing chosen yet" from "the host took it off", and reading it as the first is how a guide reload used to put the grid back on a host who had just removed it.

   **A grid is not a chapter of the guide.** It is stored as one — its own `chapter_type`, its own pool row, adopted and dropped like any other — but the reference-guide scroll does not draw it (`web/widgets/reference-guide-scroll.js#isScoringGrid`). It is the shape of the scorepad, read in the table it labels, and rendered as a section it was a heading and a table duplicating the grid two cards up the same screen — at `display_order` 5, the *first* section, pushing the rules somebody did open the scroll for below it. The rows still load on the same fetch (the play screen is fed from it, via `guide-chapters-loaded`), and Browse is still where a grid is added, edited, reported and dropped. The scroll's empty state is what a guide holding nothing but grids now shows.

   **A grid the viewer HAS is the scroll's last section; one they haven't is its offer.** The parchment scroll ends in a *Scoring* section (`_renderScoringSection`), always after the type-ordered chapter flow whatever migration 021's `display_order` says, holding both. Adopted grids draw as real tables through the same `ScoringTemplateEditor.preview` the author's editor and the offer sheet use, collapsed like any other chapter and carrying the same remove / edit / report actions — labelled with **whose** grid it is, since every grid for one game carries the same derived title. The two screens that already draw the live scorepad — the Play step and the spectator's mirror — pass `showScoringGrids: false`, because there the same table two cards apart is a duplicate rather than a reference; a game's own page has no scorepad and shows them. Under that, when the pool holds grids the viewer has not adopted, the same section carries *"…custom scoring grids are available — tap to add"* ("…more…" when they already keep one), and **tapping opens the picker sheet itself**, not the Browse screen: which grid to take cannot be answered from one-line rows that all read the same, and the sheet that draws each candidate's real grid already exists for exactly this question (`.claude/rules/ui-object-design.md` §3b). Adopting from it adds the chapter against the game it belongs to (an expansion's grid to the expansion), reloads the scroll and fires `chapters-changed`, so any other surface holding this guide reloads too. The nudge also rides in `.scroll-panel__peek` — but only while the scroll is **rolled up**, which is how the Play screen opens it and is the one state where the section is hidden with the rest of the body — and inside the empty state, which renders no peek at all and is exactly the case the nudge is most for. Dismissal is stored as the set of chapter ids turned down, per game, not a boolean, so a grid published later can say so once more; the sheet's *Continue without* writes only the ids it actually showed, the notice's own × writes every pending one. And when the pool for the game is **empty** — nobody has written a grid at all — the same slot carries *"No scoring template yet — tap to build one"* instead, which routes straight into the grid builder's **head-start step** (`mode=create&layout=scoring_grid`): step 0 picks a chapter type the button has already named, so that one would be a tap on a question already answered — but step 1 offers to draft the rows, and a game nobody has written a grid for is exactly where that offer is worth taking. Skip is beside it and the first blank row is already seeded, so an author who would rather type their own reaches the editor in one tap. Adopt-an-existing-one and write-the-first are one slot and never both, in that order — with grids already written, adopting beats authoring a second — and neither shows while the pool is still loading, since an empty list before the fetch lands is silence rather than an answer.

   **And on the Play step they ask outright.** A host with **no** scoring grid in their guide for a game that **has** some gets a sheet on arriving at the Play step: *Score on a shared grid?*, **the three most players keep**, each drawing its **real grid** through the same `ScoringTemplateEditor.preview` the author's editor and the guide use — because "6 rows · Everdell" is not enough to pick a scorepad by with your friends waiting. Every grid for one game carries the same derived title, so a card leads with **whose** it is and how many guides hold it: the author says which one, the count says which one the table usually uses, and the count is also the sort key, so it rides beside the name it is ranking rather than in the meta line under it (absent at zero — a grid nobody keeps is not a fact worth a chip). The pool already arrives `popularity DESC`, but the sheet sorts again before it takes three: "the three most players keep" has to be true of the three that survive the slice, not of whatever order the caller happened to hand over. Picking one puts it on the table **and** adds it to the reference guide, so next time it is simply there and auto-apply handles it; the table is painted first and does not wait on the write, because the draft carries a complete snapshot of the rows and only the *next* play depends on the adoption landing. *Continue without* is the other answer, and it is an answer: it writes the ids it was shown into the same dismissal store the scroll's notice reads, so the notice two cards further down the same screen goes quiet with it (`domain/chapter.js#dismissTemplates` — one store, two surfaces, or the host answers the same question twice). Backdrop, Escape and the device back gesture mean *not now* instead and record nothing.

   It is the same widget as the picker sheet with a second mode (`web/widgets/scoring-template-sheet.js#offer`) — one grid object, one CSS family — but its own panel, because "which of mine" is a list of one-line rows and "adopt one of these" cannot be answered without seeing the rows. Each candidate is a card with a real button inside it rather than one big button, since a row carrying a description renders a note button of its own inside the preview and a button cannot contain a button. Long grids are cropped in **JS** at five rows with a *+N more rows* line, not clamped in CSS: a height clamp cannot tell a preview it cut short from one that simply fits.

   **Every guard on the offer is "the host has not already answered this".** A grid in their guide, a template on the draft, the scoring bar's switch deliberately off (`scoringTemplateOff`), rounds or scores already on the table (the same bar auto-apply refuses to cross — restructuring a table mid-game is worse than never offering), a game already asked this mount, an id already turned down, or offline. It runs on the Play step and not on Gather: Gather is a roster, and the scorepad is not a question worth interrupting it with. Neither half of the question is fetched here — `views/play-flow-view.js` gets the guide from `guide-chapters-loaded` and the pool from `guide-templates-loaded`, both announced by the reference-guide scroll that mounts on the same screen in the same frame, so nothing on the Play step doubles a request the guide has already made.
7. **Profile** (own): Strava-style stats strip (plays / games / wins / hours), collection grid, recent plays. Admin users get an "Admin tools" link.
8. **Profile (other user)**: fully public — same stats strip + collection grid for any account. The header surfaces buddy-state ("Add buddy" / "Accept request" / "Request sent" / "Buddies").
9. **Buddies**: accepted mutual edges, plus incoming and outgoing pending requests. Search-by-display-name to send a new request.

   **Ghost account claims — "is this you?" (migration 070).** A ghost player is a name a buddy typed into a play they logged; until now the person behind it had no way to say so, because `bgb_link_ghost` only ever ran owner→ghost. The claimant now asks and the owner approves, and approving performs that same merge. Three sections on this screen (all `ui/ghost-claim-suggestions.js`, so the 1200-line view stays out of it) and one sheet reachable from a play. **Is this you?** lists ghosts on the viewer's *accepted buddies'* rosters whose name resembles theirs — "Lachie Brown's ghost **Davo** · 12 plays · last 4 Aug 2026" — with Claim and Not me. **Link requests** is the other side: "Julia Reyes asked to link **Davo** · on 12 plays of yours", Accept / Decline. **Accept is confirmed first** — `PolaroidPopup.confirm()`, the project's one confirm surface, asking "Move 12 plays to Julia Reyes?" and spelling out that undoing it means *they* remove themselves from each play by hand. The dialog leads with the figure because that is the part the owner has to weigh, and Accept sits a thumb's width from Decline in a list they are skimming; a row seeded from the profile bundle carries no count, so the tap fetches `GET /ghost-claims` before opening rather than saying "your plays". Confirming merges and toasts how many plays moved; it also calls `Play.invalidateDeps()`, because the plays themselves changed hands. Declining costs the claimant a strike — they may ask once more, and a second decline is final; withdrawing your own ask (**Link requests sent**) is a delete, not a decline, and costs nothing.

   The same claim is reachable from a play's player list — the back of a polaroid and the play-detail popup (`widgets/ghost-claim-sheet.js`, opened by `ui/player-row-action.js`). Those ghost rows were inert before, which made the one row a person most needs to tap do nothing. **That path deliberately does no name matching:** the suggestion list is the app volunteering a guess and stays conservative, but a tap on a specific row is not something the matcher gets to veto, and a nickname is exactly what it misses. The claim is withheld only where it could not succeed — the viewer's own roster, or a play they already sit on, which would seat one person twice.

   The count of incoming claims rides on `/profile/bundle` (migration 071) rather than its own fetch, so the Profile tab's dot and the Buddies card's count are right on first paint. It is a **third source on the same dot**, not a third dot; the hub's Buddies card sums it with buddy requests, because both are answered on the one screen it opens.

   **Mutations here patch in place; they do not restructure the lists.** A tap on a list control repaints every control bound to that person (`data-rel-control` + `_syncRelationControls`) and nothing else — the person does not leave the suggestion rail, no section appears or disappears, and nothing re-sorts. The lists re-form on the next *continuity break*: a mount, a page turn, a search, or a confirm dialog. That is the timing half of `.claude/rules/web-frontend.md`'s surgical-repaint rule, which exempts membership changes by scope but says nothing about when: a full repaint in the tap's own frame slid the rail sideways and the next tap sent an invite to the wrong person. Because the row stays put, its control shows a **verb** for what this session did — Sent / Accepted / Declined / Cancelled — never a state like "Buddies", which would contradict the heading above it. `_unfriend` is the one that restructures immediately, and that follows from the rule: its confirm dialog has already broken continuity.
10. **Play importer** (Settings → Play importer, `/settings/import`): one wizard, several sources, one ending. `views/import-wizard-view.js` owns the LIFECYCLE only — header, step bar, nav and its blocker, step arithmetic, the error banner, the write, close-and-discard — and each branch (`widgets/import-notes-branch.js`, `widgets/import-photos-branch.js`, `widgets/import-bga-branch.js`, `widgets/import-bgg-branch.js`) owns its own markup, handlers and draft model behind a small contract (`steps`, `renderStep`, `continueBlocker`, `stepNext`, `stepBack`, `navLabel`, `onEnter`, `resetFormState`). **Step 1 Source** — `widgets/import-source-step.js`: Notes, Photos, Board Game Arena, and BoardGameGeek as the one remaining disabled *coming soon* row (the BGG row points at the collection sync under Connections, which is a different thing and is untouched). The BGA row names its cost on the row itself — it needs a real password and BGA's terms don't allow this — because that is the one thing that might make somebody not want to open the door at all. An unfinished draft leads the list as a **Pick up where you left off** row rather than resuming behind the user's back. No progress bar on this step, on purpose. 

    **The notes branch** (`domain/play-import.js`, `widgets/import-notes-steps.js`) — **Source**: paste a note, or read a `.txt`/`.md`/`.csv` in with `FileReader` (nothing is uploaded), or photograph the page (up to 4, inline base64, never persisted). **Details**: optional, how the note is organised, with two one-tap examples; Continue here fires the parse. **Players**: every distinct name, auto-suggested via `domain/name-match.js` against the buddy bundle (which is what offers "Jasmine" for a note that says "Jas"); a row opens `widgets/player-picker-sheet.js` in single-select mode. **You** is the first candidate and the viewer's own display name is pre-matched — `/play-partners` never returns the viewer, and without this an import landed with the importer absent from their own history and their own wins. **Games**: every distinct game name against the catalog; Continue names how many plays leaving one unmatched would cost. Resolving a name ONCE here is why this branch keeps two steps the photo branch has no equivalent of: a 106-play tally names maybe eight people, and doing it per row would be forty corrections instead of eight.

    **The photos branch** (`domain/photo-import.js`, `widgets/import-photos-steps.js`) — **Photos**: pick up to 30. Each file is opened twice: by `domain/exif.js`, which walks the JPEG segment chain to the APP1/TIFF block for `DateTimeOriginal` plus the GPS IFD (the date is taken verbatim, never through a `Date` — an EXIF timestamp is already local wall-clock time where the shutter fired, and reparsing it in the phone's current zone moves a late holiday play to the next day); and by `preparePhotoForUpload` with `PHOTO_IMPORT_OPTS`, whose `alwaysReencode` defeats the fast path so the copy reaching the bucket carries no EXIF at all. The coordinate goes to `domain/geo-grid.js` and is then dropped — never written to the draft, never sent anywhere. A photo with no GPS inherits the country of another taken the same day; a file with no EXIF at all falls back to its modified time and the row says so. **Assign**: the pager — one photo on screen, a filmstrip above it showing which still have no game, and **Same as the last one**, which copies the game and the table forward but never the date or country, because those came out of this photo's own EXIF. The roster starts with the importer, seeded at creation and never again. A guest typed on one photo is offered on the rest of the run, deduped by name, because reaching it by typing it again is how one person becomes two ghosts.

    **The Board Game Arena branch** (`domain/bga-import.js`, `widgets/import-bga-steps.js`) — **Account**: the consent surface, and the only place an account can be unlinked. BGA has no API and no app passwords, so this needs a real account password, and **their terms prohibit automated access** — both are said above the field, not behind a disclosure, and an acknowledgement checkbox gates Continue. **Fetch**: the sweep, narrated by the server's own ledger (`GET /bga/tables/progress`, polled at 1.5s) because it takes minutes rather than seconds and a spinner is indistinguishable from a hang. **Players**: one row per BGA handle, and **every row says WHY it resolved the way it did** — "Matched before", "@handle is Marcus Chen on BoardgameBuddy", "closest to @handle" — because a handle is not a name and a score would tell the user nothing about whether to leave it. A remembered mapping and the viewer's own handle apply silently; a cross-account match does not, because it is somebody else's claim about a shared username. The local fuzzy fallback ranks **username before display name** (`ImportPeople.closestTo`'s optional `fields` argument), the opposite of the note importer, because a BGA handle *is* a username. **Games**: BGA's names against the catalog, the same step the note branch has. Resolved handles are remembered after a successful import (`POST /bga/players/remember`), which is what makes the second import a glance. Winner comes from BGA's own `rank === 1`, not from the scores — the site already decided, and re-deriving would disagree on any game where the low score wins. Dedupe is `bga_table_id`, unique per user, so a re-run offers only what is new. The password lives on the branch for the length of one request and is never on the model, never in the draft, never in `localStorage`. Full rationale in `Docs/BGA_IMPORT.md`.

    **The BoardGameGeek branch** (`domain/bgg-play-import.js`, `widgets/import-bgg-steps.js`) — **Plays**: one `POST /bgg/plays/pending`, which is the branch's equivalent of the note's paste box and the only step in the wizard whose content arrives rather than being typed. Four faces, genuinely four rather than a loading flag over one: reading, a dead link (a pointer to Settings → Connections, not an error with a Try again that cannot help), nothing new, and a count with a date span. `onEnter` runs on every mount including a resume, so the read refuses to run over a draft that already holds plays unless **Read them again** asks it to — otherwise coming back to a half-reviewed import would throw the review away. **Players**: as the notes branch, plus one thing neither other source has — a seat BoardGameGeek recorded under the **linked handle** is matched to the viewer's account outright, because that is an identity rather than a guess. **Games**: not a search. A BGG play names its game by the very id the catalog stores in `bgg_id`, so the primary action is *Bring it over* (`BggImport.start`, one `/thing` fetch, `silent` so a batch does not stack a toast per game) with a search sheet as the fallback for a game already here under another id; **Bring over all N** loops sequentially, because firing thirty throttled BGG reads at once is how a user gets rate-limited out of their own import, and invalidates the catalog caches once at the end through `BggImport.catalogChanged()`. Two things this source does NOT do: expand a `quantity` into several plays (N rows sharing one `bgg_play_id` would be rejected by the partial UNIQUE, so the review warns instead), and offer to resize a row (a cloned play would have no BGG id of its own). A play BGG recorded no roster for — most of them — is seated with the account it came from, as an ordinary player so it appears in the Players step where it can be corrected; without it migration 023 would refuse those plays and the wizard would import far fewer than the sync it replaced.

    **The shared review** (`widgets/import-review-step.js` + `widgets/import-review-host.js`) — every source ends here. Live plays grouped per game, each row expandable to its table, and the table is **editable**: per-seat score, winner toggle (several is a tie), add via the player sheet, remove, plus the game, the date and — for a run — its count. A run of indistinguishable plays collapses into one row ("58 identical plays"), and the list is windowed four game-groups at a time through `ui/infinite-scroll.js`. **Every edit applies to the whole row**, which is what this screen always did for dates and game overrides; two rows edited into agreement therefore MERGE, which the host re-anchors around so the open row does not close under the user. A score is **disabled on a multi-play row** — fifty-eight plays that all scored 112 is not a thing that happened. A seat is addressed by `whoOf()`, never by display name: an account and a same-named ghost are two seats, which is exactly what the collapse exists to keep apart. Notes rows are edited through a per-play `seatsOverride` (seats there are DERIVED through the one global Players mapping, so editing the map would take somebody off every play in the note); the first edit seeds the override from what the mapping already says, so materialising it is a byte-identical no-op, and the row then says it no longer follows the Players step.

    **The summary and the write** — one implementation, parameterised by three values per source (`summaryTile`, `reviewNotices`, `ctaNote`): Plays / Games / (Players | Photos), the by-game breakdown counting the plays that will LAND rather than the review's groups, and two warnings counted apart because they have different fixes. Then the write, chunked 50 at a time through `POST /plays/import` behind a progress bar; the photo branch uploads first, one at a time, through `POST /plays/photo`, and a photo that won't upload costs the picture and not the play. Runs of indistinguishable plays share an `import_group_id` (migration 005) so the feed shows one card rather than 58; every play in the import shares an `import_batch_id` (007) so the whole thing can be read back and undone from the imports spoke. Photos never get a group id — one photo of one table is never one of the indistinguishable repeats that field exists to collapse. Every draft play carries its own `client_key`, so a failed run resumes by importing again and re-writes nothing.

    The four models stay four models on purpose — a parse → name-map → run-collapse machine, an EXIF → per-file-upload machine, a sign-in → sweep → handle-map machine, and a fetch → name-map → game-map machine — and what lets one review render all of them is the interface they share, typed as `ImportSource` in `domain/import-draft.js` and gated by `tools/check-import-wizard.mjs` (127 assertions). That interface gained `gameOf(item)` when the third source landed: the shared summary used to read `sourceKey === "notes" ? playGame(item) : item.game`, which quietly assumed every non-note source had the photo shape — a shared step that names a source is a shared step with a countdown on it. The seat collapse moved to `domain/import-seats.js` at instance #3 (`.claude/rules/ui-object-design.md` §4 says #2); only the BGA model reads it so far, deliberately — migrating two shipping importers in the change that adds a third source risks all three at once, and the gate already asserts all three `whoOf()` agree on the key shape, which is what makes that migration safe later. No `BgbBackGuard`: this is a routed screen with its own history entry (`.claude/rules/overlays.md` §8b).

    **The history** (`views/imports-view.js`, `views/import-detail-view.js`) — what the wizard wrote, after the fact, at `/settings/imports`. Settings carries one row into it; the list used to be rendered out in full there, with a trash can per row and no way to see what any of them had written. The index is a row per batch; opening one shows its facts and then its contents collapsed to **runs**, with the three affordances the app already has hung off them — a one-off opens the play popup, which edits; a run opens `widgets/play-run-sheet.js`, which deletes it; the footer deletes the import. **A run row opens something here and does not on the plays log**, because `bgb_plays_page` returns no `import_group_id` and the log therefore has nothing to hand the sheet. And **there is no import to edit** — a batch is a `GROUP BY` with no row of its own, so editing an import means editing the plays in it, which is why the screen has no rename field.

11. **Dev feedback** (Settings → Add feedback / Report a bug, `/settings/feedback`): the board of what users want built next, and the app's only general user→maintainer channel — chapter reports moderate one community object and carry nothing else. Everyone reads it, everyone posts to it, and the ordering is the point: `bgb_feedback_list` sorts by like count then newest, so what surfaces is demand rather than a queue. A like is togglable by anyone on anything including their own item, and submitting inserts the author's own like so nothing sits at 0. `views/feedback-view.js` paints the like optimistically and repaints one row rather than the screen (the `feed-view.js` "Good game" shape, guard Set and all), reconciling against the server's count so a concurrent like does not leave a row one behind — and it does **not** re-sort on a tap, which would move the row out from under the finger that tapped it. `widgets/feedback-compose-sheet.js` is the first sheet in this project to hold a `<textarea>`: type is the shared `.bgb-sheet__tabs` strip, topic the `.bgb-sheet__opt` radio list (seven tabs do not fit 390px), and focus lands on the panel rather than the field so the keyboard does not bury the controls above it. Admins get an Open/Resolved toggle and Resolve/Reopen per row; resolving is what hides an item from everyone else and is reversible, and the gate is `_effective_status` on the server, not the control.

12. **Admin tools**: chapter-reports moderation. Each row has Resolve (no action) and Delete chapter (remove from the pool). (Reachable only when `is_admin=true`.)

## Active Development Notes
- **The trending refresh is one endpoint with two callers, and the cron one has no user.** `get_admin_or_service_key` (`api/routes/dependencies.py`) accepts the app's `ADMIN_API_KEY` as a bearer before it tries the session path, because a GitHub Actions cron has a secret and nothing else. The secret is `BGB_ADMIN_API_KEY` in the repo's Actions secrets and must equal the Railway service's `ADMIN_API_KEY` — a mismatch is a silent daily 403, which is why `ENV.md` §2 says to rotate the two together. The refresh calls `game_routes.import_game_from_bgg` from inside the function, not at module top: `game_routes` imports the services package, so a top-level import is a cycle (the same shape `bgg_link_routes`' pending-import drain uses).
- **Discover paints from the last bundle in the tap's frame and repaints per rail.** `views/discovery-view.js` puts the shell and four section hosts up in `renderLoading()`, seeded from `Discovery.cachedBundle()` when the SWR cache holds one, and `_paintAll()` rewrites each host on its own — the loader while the first fetch is in the air, one retry card (not four) when it failed with nothing to show, then the rails or their empty copy. The trending rail has a fourth branch for BGG being down while everything else is fine. Loads are sequence-guarded (`_loadSeq`) so a pull-to-refresh over a mount fetch cannot be overwritten by the older answer. `domain/discovery.js` owns the staleness contract: ten minutes fresh to match the server's own cache, a day stale for the instant first frame, and a `_dirty` flag set by any collection or play write so the next fetch asks with `refresh=true` — the write and the next mount are different screens, so the flag cannot live on the view.
- **The game picker answers from the device first; the network only refines it.** Every keystroke in `widgets/game-finder.js` paints synchronously before any request, from three free sources in order: an exact cached `/search` answer, `Game.cachedSearchPrefix()` (the cached answer to a shorter query this one extends — typing "catan" asks five questions whose answers all live inside the first), and the device pool of the viewer's own games. That pool is `game.recent` plus every `game.bundle` entry `Bootstrap.warmGameBundles()` warmed, i.e. the whole collection, and it used to be reachable only when `BgbNet` said offline — which was backwards, because a host on Gather is nearly always reaching for a game they own whether or not there's signal. It is also where a *failed* `/search` now lands: keeping real tappable rows beats replacing them with "Search failed" to report that there are no more of them. `/search` then replaces the provisional list in place. Three consequences worth knowing: **queries under 3 characters never reach the server** (pg_trgm has no trigram to match under three, so those were the two most expensive and least useful queries of every search — they're device-only now, and the empty state says "keep typing" rather than "no matches"); **a superseded keystroke aborts its request** via a caller `signal` threaded through `api.get`, and a caller abort is deliberately *not* counted as a network failure by `BgbNet` (`err.aborted`, no `noteFailure()`) or typing would walk the app into offline mode; and **provisional rows are tappable** — `_gameById` is populated by the provisional paint, so a host can pick their game before the response lands. The dimming under `.game-finder-dropdown--loading` was softened to 0.75 accordingly: those rows are real matches now, not the previous query's leftovers. `index.html` also preconnects to `APP_CONFIG.apiBase` right after `config.js`, so the first search of a session doesn't pay DNS + TLS on top of its round trip.
- **The Game Explorer repaints surgically; a chip tap touches no node it doesn't have to.** Caching alone didn't make filtering feel fast — the view rebuilt the whole container twice per tap, which destroyed the chip *under the user's finger* (so `:active` never painted and the tap read as ignored), reset the horizontally-scrolling `.lp-chip-row` to `scrollLeft` 0, and recreated all nine `<img>` nodes. Those images are cached, but they carry `loading="lazy"`, which defers a freshly-inserted image to the next rendering opportunity — hence a one-frame blank photo on every tap.
  - `render()` now ensures the shell (`#gx-grid-host` / `#gx-pager-host`) and otherwise patches. It needs no `_structuralSig` (unlike `collection-view.js`) because nothing in the shell outside the patched regions is state-dependent.
  - **Chips are updated by class only, never re-emitted.** That required making the chip `onclick` strings state-*independent* — `_setFilter` toggles rather than the markup encoding which of set/clear a tap means. A value-encoding onclick would go stale the instant the class changed without the markup.
  - `_paintGrid()` reconciles by `data-game-id`: retained cards are *moved* (which preserves their live `<img>` and decoded pixels) and only new cards are built. New cards pass `eager: true` to `renderGamePolaroid` — a 3×3 grid is one viewport, so lazy-loading only costs a frame there.
  - The warm path is fully synchronous: `_loadGames` peeks `Collection.cachedShelf()` and paints in the tap's own frame. It used to set `_loading = true` and render *before* knowing whether the data was local, paying two paints for a loading state that (being microtask-adjacent) was never visible.
  - The `added_at` sort is memoised per shelf object. Filtering only removes rows, so the order is filter-independent; it previously re-sorted up to 1000 rows with `localeCompare` on every tap. ISO-8601 strings compare identically with `<`/`>`, and `game_id` breaks ties so paging is stable.
  - A `truncated` shelf only falls back to the server when the user is actually *narrowing* it, matching `ShelfController.serverFallback`.
- **Three more surfaces page or read from cache instead of round-tripping.** Same model as the Collection spokes.
  - **Game Explorer** (`web/views/game-explorer-view.js`): the "My Collection" scope pages, filters and sorts off the already-warmed owned shelf via `ShelfFilter` — zero requests for a page turn or a filter chip. It re-sorts by `added_at DESC` because that grid orders by when a game was added, not when it was last played; `added_at` is NOT NULL, so it needs none of the NULLS-LAST care the collection spokes take. The "All BgB Games" scope is cached per query string under `game.explorer` (3 min fresh / 30 min stale), so page-back and scope-toggle-back are free. A shelf past the endpoint's row cap falls back to `/collection/grid`.

Now SWR under `play.list` keyed `user|game|buddy|search|page|perPage`, with `Play.cachedList()` for the first-frame paint. Paging is offset-based, so a single insert shifts every page after it — `_invalidatePlayDeps()` therefore clears the **whole namespace**, never one key.

- **The Owned shelf lists games you sold as well as games you have.** A `prev_owned` row (migration 069) keeps its alphabetical place in the grid, with its box art greyscaled to 55% and a rotated "Prev. owned" stamp across it — the tile has to carry that, because the corner status chip is one neutral glyph whatever the status by design. The header count and the shelf picker's own count *exclude* those rows — they read "12 games" over a shelf drawing 15 tiles, and the stamp on the three is what explains the difference rather than a tally in the header. `bgb_collection_shelf` and `bgb_profile_bundle`'s `owned_page` widen to the set `('owned','prev_owned')` and report a `parted_total` alongside `total`; every other owned count in the schema keeps its bare `status='owned'` predicate and is correct unchanged. The Expansions shelf drops `prev_owned` rows entirely — its tally is the same number `expansion_counts` reports, and an expansion you sold is no longer clutter on the base game's shelf — so a base game you sold falls out of the tree and any expansions of it you still own land in the trailing "Not in your collection" group. Setting the status is the third radio in the app-wide status sheet ("Prev. owned — sold, gifted or donated"), which keeps **Remove from collection** below it as a separate action: Prev. owned means "I had this and let it go", Remove means "this was never mine".
- **The Collection spoke has four shelves: Owned, Wishlist, Played-not-owned and Expansions**, chosen from a dropdown (`widgets/shelf-picker-sheet.js` — a bottom sheet, per `.claude/rules/overlays.md`, behind a `.shelf-picker` trigger) with the shared search + filter bar underneath it. Wishlist was its own spoke until the two were merged; `/profile/wishlist` survives as a match-only route alias. The first three are flat grids over one ShelfController. The fourth is a tree: each base game you own that BgB has expansions for, with the expansions *you own* nested beneath it and a per-game **Add expansion** row. The header counts how many expansions you own. It is deliberately **not** a ShelfController mode — that class passes its mode through as the `status` query param and hard-codes `excludeExpansions` in its filter spec, so a fourth mode would have meant conditionals in a class the other three shelves also use; the tree keeps small view-local state instead. It carries the shared search field but no filter button and no scroll sentinel: players, playtime and play mode mean nothing for an expansion, and the tree tops out around 40 groups, so it renders every group it has. Its search is a name match over the groups (`_visibleTree`) rather than a `ShelfFilter` pass — a group whose base game matches is kept whole, otherwise it survives only for the kids that match and renders open, so the row you searched for is never hidden inside a collapsed group; both halves go through the one `ShelfFilter.matchesName`. Grouping happens client-side rather than in SQL so that two cases stay visible instead of being silently dropped — an owned expansion whose base game you don't own, and one whose denormalized `base_game_bgg_id` is null — both of which land in a trailing "Not in your collection" group. Base games are alphabetical within each partition (groups holding something still come first), and each group's expansions are alphabetical too — the owned ones first, then the unowned catalog rows when **Show all expansions** is on — through the same comparator the flat grids use. A **Show all expansions** switch flips each group between the expansions you own and everything BgB has for that base game; the ones you don't own are dimmed, still tap through to their game page, and carry a **+** that adds them in place. The catalog arrives in one `GET /collection/expansion-catalog` call, fetched on first turn-on and kept for the session, and the switch is remembered per device in `localStorage` (`bgb.collection.expansionsShowAll`). If that fetch fails the switch flips back off and the tab keeps showing what you own rather than blanking. The header and each group's tally always count what you **own**, never what's merely listed — and, like the flat shelves, they follow the search. Showing all, the per-group footer becomes **Import from BoardGameGeek** — the catalog is already on screen, so the only thing left to reach is what BgB doesn't have yet; showing owned only, it stays **Add expansion**. Every group opens **collapsed**, and the switch's row carries an **Expand all / Collapse all** control at its trailing edge; that row is pinned under the spoke's back row (`#collection-tree-controls-host`, sticky at `--bgb-header-height + --bgb-spoke-head-height`), which is why it lives in its own shell host rather than inside the body that `_paintTree()` rewrites. Open/closed state is session-only — every entry to the tab starts collapsed. Children are indented past a rail descending from the base game's thumbnail.

  **Add expansion** opens `widgets/expansion-picker-sheet.js`, which lists the catalog's expansions for that base game minus the ones you own (`GET /games/{id}/expansions`), adds the pick with `POST /collection` optimistically (the row paints in the same frame and rolls back on failure), and always offers a route into the BGG import popup — that popup remains catalog-only and never touches your collection.
- **The collection shelves scroll, and window entirely on the client.** Each fetches one whole shelf via `GET /collection/shelf` (cached in `bgbCache` under `collection.shelf`, key `${target}|${status}|${base|all}`, 60s fresh / 5min stale) and derive the visible window, filter and search from it. Instead of a docked prev/next pager the grid grows a batch at a time — 21 rows, seven rows of the 3-up grid — revealed by an `IntersectionObserver` on a sentinel below the last tile (`web/ui/infinite-scroll.js`, shared by both spokes). Revealing a batch, tapping a filter chip and typing a keystroke all cost **zero** requests. Before the shelf endpoint, each of those was its own uncached `/collection/grid` round trip — ~1s apiece — even though the backend was reading the whole shelf on every one of them and slicing it in Python (it no longer does — migration 024 pushed the grid's filter, sort and page into SQL). The one path that still hits the network mid-scroll is a shelf past the endpoint's row cap being narrowed: there `ShelfController.loadGridPage` fetches the next `/collection/grid` page and **appends** it, reporting through `loadingMore` so the rows already on screen aren't dimmed.
  - Shared logic lives in `web/domain/shelf-controller.js` (load / derive / page / filter state) and `web/domain/shelf-filter.js`. **`shelf-filter.js` is a line-for-line port of `_passes_grid_filters` in `collection_routes.py` and must be kept in step with it** — three behaviours look like bugs and are deliberate: search is a plain case-insensitive substring test; the "6+" player chip skips the `min_players` check; and a game with no `playing_time` passes a `playtime_max` filter but fails a `playtime_min` one.
  - **Every collection screen shows games alphabetically by name**, applied client-side in `ShelfFilter.sortShelf` after the filters and before the window slice. The RPC still answers in the server's recency order (`last_played_at DESC NULLS LAST, added_at DESC`; wishlist `added_at DESC`) — that is what the Profile hub's preview strip and the feed want, and re-ordering there would have meant a migration on `bgb_collection_shelf` and `bgb_profile_bundle` for an order only these two spokes need. The comparator is one shared `Intl.Collator` (`numeric: true`, `sensitivity: "base"`), so "Catan 10" follows "Catan 2" and case/accents don't split a run; `game_id` breaks ties so the order is stable across re-derives. `ShelfController.loadGridPage` passes `sort=alphabetical` so a truncated shelf's server fallback sorts on the same axis — the endpoint keys on a plain lowercased name, so the two agree except on the margins (accents, `Catan 10` vs `Catan 2`), which is not worth reimplementing `Intl` in Python for. Two consequences: the Game Explorer keeps its own `added_at DESC` sort (its grid orders by when a game was added, and it sorts the shelf itself rather than through `ShelfController`), and the profile-bundle *partial* seed — 12 recency-ordered rows used to paint a first frame on a cache miss — is only an approximation of the alphabetical head of the shelf until `load()` replaces it with the whole thing. `ShelfController.hasMore` compares against `available` (what the derived list can actually yield) rather than `total` (which under that seed reports the whole shelf), so the sentinel can't ask for rows the client hasn't got.
  - Invalidation is namespace-wide (`Collection.invalidateShelves()`), hooked into `Collection.invalidateMyStatusMap()` and `Play._invalidatePlayDeps()`. Per-key wouldn't do: an add lands on owned *or* wishlist, a status change moves a game *between* shelves, and removing an owned game can make it reappear on the played shelf.
  - A shelf past the endpoint's row cap comes back `truncated`; narrowing one of those falls back to `/collection/grid`, so search never silently misses games in a huge collection.
  - **The search field is on every shelf; the filter panel is not.** Players / playtime / play mode are `ShelfFilter` predicates over a flat shelf and say nothing about an expansion, so the Expansions shelf renders the field without the filter button. Its search is a name match over the tree instead (`_visibleTree`): a group whose base game matches is kept whole, otherwise it survives only for the kids that match and renders open, so the row you searched for is never hidden inside a collapsed group. Both halves go through the one `ShelfFilter.matchesName`.
  - Repaints are surgical — `#collection-grid-host` / `#collection-more-host`. Revealing a batch rewrites those two subtrees only. A full `container.innerHTML` per batch is itself the "laggy" feel, independent of the network — and mid-scroll it would also throw away the position the user is reading from. The sentinel is re-observed after every paint: an observer whose target stays intersecting never fires a second time on its own, so a batch too short to push the sentinel out of range would otherwise stall the list.
- **The deployed app is one hashed bundle; the repo is still ~120 `<script>` tags.** `projects/boardgame-buddy/scripts/bgb-bundle.mjs` runs in the deploy workflow, after the Tailwind precompile and before the `sw.js` stamp, and rewrites only the checkout the Pages deploy uploads — nothing is committed back, and local dev loads the tags as it always did. `index.html` stays the manifest (the same property `sw.js`'s precache sweep relies on), so a new module needs no second list. Four things about it are deliberate and easy to undo by accident: the files are joined with `\n;\n`, because a file whose last statement omits its semicolon followed by one opening `(function () {` parses as a *call*, and this is 121 IIFEs in a row; it is **not** `esbuild --bundle`, which would wrap classic scripts that share one global scope and change the scoping of every top-level `let`/`const`/`class`; it is **not** `--minify-identifiers`, because the bytes are in the comments and mangling is the one risky part given inline `onclick="window.router.go('feed')"` handlers and dynamic lookups like `window[host]._setRoundScore(...)`; and the output sits at the site **root**, not `build/` or `dist/`, which are names Vercel's zero-config detection treated as output directories — the app is on Pages now, but the root placement stayed, so `web/_headers` needs a `/bgb-*` rule alongside `/assets/*` to mark the two hashed files immutable. Two gates fail the deploy loudly rather than shipping a blank app — `node --check` on the concatenation and a 450 KB gzip budget (`BGB_JS_GZIP_BUDGET`). `web/_headers` marks those two names immutable for a year via `/bgb-*`; nothing else at the root is given a header, so there is no precedence question. Measured: 121 requests and 635 KB gzipped JS down to 1 and 215 KB, CSS 125 KB down to 40 KB, and the worker's precache list from 129 entries to 11.
- **The QR codecs load on demand, and the boot can no longer strand you.** `ui/qr-decode.js` alone was 258 KB — about 9% of the whole JS budget — for the buddy-QR sheet, which most sessions never open. `ui/lazy-script.js` pulls both in on first use (a rejected load is deliberately *not* memoised, so a retry after a dead connection is a real second attempt). They stay listed in `index.html` as `<link rel="prefetch" as="script">` rather than being deleted, because `sw.js` scans `src=` **and** `href=`: that keeps them in the offline precache — the thing `qr-decode.js`'s header says the same-origin vendoring exists to protect — while taking them off the parser's critical path, at a priority that cannot race `/bootstrap`. The scanner loads the decoder *before* opening the camera and has its own error code for a failed load, because a preview running against a missing `window.jsQR` looks like a scanner that simply never recognises anything, and blaming the camera sends the user to the wrong settings screen. Separately, `BOOT_WATCHDOG_MS` is now spent from **navigation** rather than from `DOMContentLoaded` — armed at DCL it only started counting after every script had run, so slow assets added 12s on top of their own 45 instead of covering any of it — with a 3s floor so a boot that has already blown the budget doesn't fire before supabase-js has read localStorage and bounce a signed-in user to `/auth`. An inline `<head>` timer reveals a reload control at 8s, in HTML and CSS only, for the case the watchdog cannot cover: `init.js` never arriving.
- **`/bootstrap` no longer scales with everybody else's play history.** `bgb_profile_bundle` is composed into `bgb_bootstrap`, so it runs on the one call a cold boot waits for, and five of its blocks wrote play visibility as `p.user_id = target OR EXISTS (…play_players…)`. Postgres cannot serve a disjunction spanning two tables from any index, so each was a full sequential scan of `boardgamebuddy_plays` — a table every account shares and that grows by hundreds of rows per BGG import. Migration 011 moves them to the `my_plays` UNION form `bgb_user_stats` has used since 003: one arm per index, `UNION` not `UNION ALL` so a play you both logged and are seated in still counts once. ~800ms to ~275ms at 201k plays. **The two owned/wishlist `LATERAL` blocks keep their `OR EXISTS` on purpose** — they also filter `p.game_id`, which `idx_bgb_plays_game_played` serves, and converting them measured 0.5ms → 98ms, so the pattern is right where the only predicate is the viewer and wrong where an index already applies. `bootstrap_version` is not bumped: the shape is unchanged, and a bump wipes every client's cache, which would make the first boot after the deploy slower for everyone.
- **Boot cost is measured, not inferred.** "It takes about a minute to open" is produced by two different failures — the shell taking 45s to download, where nothing has run, versus `/bootstrap` hanging after the app is up — and they need opposite fixes. A `boot_timing` analytics event carries `dcl_ms` beside `bootstrap_ms`, plus `landed_on`, `js_requests`/`js_bytes`, `warm` (the optimistic cache path, a different population that must not be averaged with cold boots), service-worker control, connection type and standalone. It fires from all three ways a boot can end, including the signed-out open, which reaches neither `routeAfterBoot` nor the watchdog — without it the numbers would cover only sessions that had a token. `trackEvent` gained the `metadata` argument the backend's `TrackBody` always accepted and nothing ever sent. Server-side, `api_logger.log_self_call` writes an `api_logs` row (`api_name="self"`) for `/bootstrap`, `/bootstrap/game-bundles` and `/feed` — an allowlist, because that table is unbounded — from a middleware registered outermost so `response_size_bytes` is the *compressed* body on the wire.
- **BgB is an installable PWA, and its service worker caches where travel-scrapbook's deliberately doesn't.** `projects/travel-scrapbook/web/sw.js` is a documented no-op: "the app is a thin shell over the API and stale HTML/JS causes more trouble than offline support is worth." That holds for an app whose every screen needs the server. It doesn't hold here, because the host cascade genuinely runs with no backend — without a cached shell, offline mode would only work for someone who never closed the tab. The stale-bundle risk is answered rather than accepted: `sw.js` keys its cache on a `__BGB_BUILD_ID__` placeholder that `.github/workflows/deploy-frontend*.yml` stamps with the commit SHA, so every deploy lands in a fresh cache and `activate` deletes the old one. Left un-stamped in the repo, which `sw.js` reads as local dev and disables itself — a dev editing JS is never served yesterday's copy.
  - The precache list is **derived at install time** from `index.html` and `styles.css`, not hand-written: this is a no-build-step project where modules arrive as `<script>` tags, and a hand-kept list would silently drift the first time someone added one.
  - the `_redirects` catch-all returns `index.html` with a **200** for a missing asset, so a mistyped or deleted script would otherwise be cached as a `.js` file containing the whole page and break the app on the *next* boot. `precacheOne` rejects an HTML body under a non-HTML URL and fails the install loudly instead, leaving the previous worker in charge.
  - The API and `*.supabase.co` are never intercepted. Read freshness is `bgbCache`'s job (TTLs, schema version, explicit invalidation); write retry is the outbox's.
  - **Registration waits for `load`, and the precache runs 6 at a time.** A first-ever install fetches the whole shell with `cache: "reload"` — ~60 requests — and that is the one launch where the app also has nothing cached and is fetching `/bootstrap` and the feed over the same radio. Nothing in the precache is needed until the *next* launch, so it gives way rather than racing the screen the user is looking at.
