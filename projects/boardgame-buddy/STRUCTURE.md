## What It Does
A Strava-style log for board game plays. The home view is a chronological feed of plays from the user and their accepted buddies, interspersed with "hot games this week" and suggested buddies. Logging a play is a guided three-screen cascade — Gather → Play → Settle Up — that walks the host through the play and mirrors read-only to everyone else (the host is the only person who scores; joiners and spectators watch the grid update live). The Play tab is split in two: hosting on top (host a game, replay the last one, or browse the Game Explorer) and joining on the bottom (enter a short code, or pick a live session hosted by a buddy). Hosting also works with no connectivity at all — the cascade runs from cache, the play queues on the device, and it uploads on the next online session. That switches itself on and off with the device's connection; there is nothing to toggle. Profiles are fully public and show a Strava-style stats strip + collection grid. The reference-guide system is fully user-driven: each user builds their own per-game guide by adding "chapters" — either creating new ones or browsing the community pool. The pool sorts by popularity. Reports on offensive chapters route to admin review.

Logging a play also surfaces the reference guide in-line: once a game is picked, a collapsed Expansions section lets the player toggle which expansions are active for this session — its rows paint from the device's warmed `game.bundle` cache in the same frame as the pick, with `GET /games/{id}/expansions` refining them in place behind a dimmed-with-a-sweep treatment, so an owned game never waits on a round trip to show what it has — and a Reference guide section appears below Scoring (on both the host's Play step and the spectator's mirror) with a centered Rulebook button + the parchment scroll merging chapters from the base game and every active expansion (each tagged with a colored dot matching the expansion's identity color). Adding chapters from this in-play scroll routes through the same Browse/Create UI, with each chapter saved against its source game's pool so it propagates automatically the next time the user opens the guide. A header bell collects everything that has happened **to** the account — being seated in somebody's play, a buddy request, a request of yours being accepted — all three derived rather than stored, so answering one empties it by construction. Since migration 017 that same set can also leave the app as **push notifications**, behind one Settings control with three positions: everything, only the things that need you, or off. It is opt-in, per-account (so it follows you to a new phone) with a subscription per device, and on iOS it requires the app be added to the Home Screen — which the install prompt already asks for. Bulk paths deliberately stay silent: a 214-play BGG import that seats six buddies fills the bell without waking six phones.

## Tech Stack
- **Frontend (web):** Vanilla HTML/CSS/JS, DaisyUI v4 + Tailwind CDN, Phosphor icons vendored in `ui/icons.js`, Supabase JS SDK (CDN). Installable PWA (`manifest.json` + `sw.js`) so the host flow works with no connectivity — see Recording a play offline under Screen Flow §3. `ui/install-prompt.js` surfaces the install itself: a dismissable strip docked above the bottom nav on phone-sized viewports (the phone tier per `BgbLayout.auto()` — the viewport's own answer, so a desktop that pinned the phone layout is still a desktop), replaying Chrome's `beforeinstallprompt` on tap and falling back to a "Share → Add to Home Screen" hint on iOS (which has no install API). It is shown only on the feed, and only when signed in and not already running standalone; dismissal is session-scoped via the `bgb.pwa.installDismissed` sessionStorage key.
- **Backend:** Python FastAPI, Supabase (DB + Auth)
- **Auth:** Supabase Auth (email/password + Google OAuth) — pilot for the whole monorepo
- **External API:** BoardGameGeek XML API v2 (for live search fallback)

## Design system — "Lamplight Study"

Game night under a warm lamp: espresso ground, amber glow, terracotta wins. Full write-up in `Docs/ARCHITECTURE.md` §4; the repo-wide rules are `.claude/rules/theming.md`, `overlays.md` and `mobile-web.md`. The four things to know before touching any UI here:

- **Two themes, equal.** Light and dark, switched by `data-bgb` on `<html>` — set by a pre-paint inline script in `index.html`, owned thereafter by `domain/theme.js`. `data-theme="luxury"` is DaisyUI's attribute and is deliberately *not* the lever; leave it alone. Settings offers Light / Dark / **Auto**, and Auto is the absence of a stored key, so the app keeps following the OS live (including across a backgrounded appearance change, which needs more than a media-query listener on iOS).
- **Every colour is a token**, declared in one of three blocks at the top of `styles.css`: theme-independent scales, dark, light. The only legitimate inline colour is data-derived (`--game-accent` from a game's `theme_color`, `--exp-color` from an expansion's).
- **Three kinds of surface, and the trap is picking the wrong one.** *Ground* is the page. *Paper* is anything that is a photograph — play cards, the Gather grid, the parchment scroll — and it is light in **both** themes. *Chrome* is plain UI cards — the profile hub, the five spokes, Settings, the picker sheets — and it follows the ground. Point a ground token at a paper surface and it inverts.
- **Three layout tiers, one attribute.** `data-bgb-layout` on `<html>` — `phone` (< 768px, the layout everything above was drawn for), `tablet` (768–1023px: a 720px column, bottom bar stays) and `wide` (≥ 1024px: a left rail replaces the bottom bar and the header, 1040px column). Set pre-paint by an inline boot in `index.html`, owned by `domain/layout.js` (`BgbLayout`), published to the store as `layout`. `#app`'s width and every docked bar's width are the `--bgb-col-max` token; the rail's width is `--bgb-rail-width`; fixed chrome centres on `--bgb-col-center`. Per-tier rules select `:root[data-bgb-layout="…"]`, never a `min-width` media query, so a Settings pin (Auto / Phone / Tablet) and the viewport go through one lever. Full write-up in `Docs/ARCHITECTURE.md` §4.6; the design board is `Docs/mocks/tablet-layout-mock.html`.
- **Choice lists are bottom sheets**, on the shared `ui/bottom-sheet.js` shell, never `position: absolute` dropdowns; centred cards share `ui/modal-shell.js` the same way, and every confirm, alert or prompt is `PolaroidPopup` (never `window.confirm`/`prompt`). The app-wide status sheet, the Stats by-game picker, both Gather pickers, the data export and the buddy-alias sheet among them. A new sheet must be added *by name* to the theme re-point list in `styles.css`, because a body-level sheet lands outside the screen that opened it.

### boardgamebuddy_buddy_edges
The mutual friendship graph (migration 008). One row per pair, stored
canonically as `(user_a, user_b)` with `user_a < user_b` so a pair can never
have two rows. `requested_by` records who sent the request, which is what makes
an incoming request distinguishable from an outgoing one. The row also carries
each party's **private alias** for the other (migration 012) — see the two
`alias_by_*` columns below.
| Column | Type | Notes |
|--------|------|-------|
| id | UUID PK | |
| user_a | UUID FK | → profiles; always the lower UUID of the pair |
| user_b | UUID FK | → profiles |
| status | TEXT | `pending` / `accepted` |
| requested_by | UUID FK | → profiles; the sender |
| created_at | TIMESTAMPTZ | |
| accepted_at | TIMESTAMPTZ | nullable; set when the request is accepted |

### boardgamebuddy_buddy_suggestion_dismissals
"Stop suggesting this person" (migration `014_buddy_suggestion_dismissals`).
Every suggestion surface offers people the viewer is not connected to, and
until this table the only way to make one go away was to add them — so a
suggestion already decided against came back on every visit.

**Per-viewer, one-directional and silent.** It is read only by the three
suggestion RPCs, is never shown to the person dismissed, and is **not a block**:
they can still find the viewer, still send them a request, and still turn up in
`/profiles/search` — which is also the way back from a mis-tap, since sending
that person a request deletes the row (`buddy_service.send_request`). Blocking
is a `status` on `boardgamebuddy_buddy_edges` and cuts both directions; if it is
ever wanted it belongs there, not here.

serves both query shapes — everyone one viewer dismissed, and one exact pair.

### boardgamebuddy_ghost_claims
Ghost account claims — "is this you?" (migration 070). A ghost player is not an
entity: it is a `play_players` row with `player_user_id IS NULL`, owned
implicitly by whoever logged the play. So a claim is keyed by the only thing
that identifies one, `(owner_id, ghost_name_key)`, plus the claimant.

Consent runs **claimant → owner**, the opposite direction from `bgb_link_ghost`,
and accepting performs that same merge. Two deliberate differences from
`boardgamebuddy_buddy_edges`: there is no `requested_by` (direction is
structural — `claimant_id` asks, `owner_id` answers), and the UNIQUE is on the
full triple rather than partial on `pending`, so status mutates in place and
declines cannot stack into a nag.
| Column | Type | Notes |
|--------|------|-------|
| id | UUID PK | |
| owner_id | UUID FK | → profiles; whoever logged the plays the ghost sits on |
| ghost_name_key | TEXT | `lower(btrim(player_display_name))` — the match key |
| ghost_display_name | TEXT | original casing, denormalized so a sent request survives a rename |
| claimant_id | UUID FK | → profiles; who is asking |
| status | TEXT | `pending` / `accepted` / `rejected` / `dismissed` ("not me", claimant-side) / `superseded` (another claimant's accept took the ghost) |
| rows_merged | INT | nullable; how many `play_players` rows the accept moved |
| reject_count | INT | two strikes, then no more asking |
| created_at | TIMESTAMPTZ | |
| resolved_at | TIMESTAMPTZ | nullable |

`UNIQUE (owner_id, ghost_name_key, claimant_id)`; `CHECK (owner_id <> claimant_id)`.

**Merge safety:** since migration 023 `boardgamebuddy_play_players` carries a
partial UNIQUE on `(play_id, player_user_id) WHERE player_user_id IS NOT NULL`,
so one account appearing twice in one game is refused by the database. The
explicit guard stays and still lives in four places — the suggestion RPC drops
the ghost, `bgb_create_ghost_claim` 409s, `bgb_accept_ghost_claim` re-checks
(state moves between request and accept), and the client withholds the
affordance — because a merge the index would reject has to read as "You're
already a player on one of those plays", not as a failed write. A colliding
ghost is blocked **whole**, not partially merged: if the owner logged both the
claimant's account and the ghost on one night, that is evidence they are two
people.

### boardgamebuddy_play_players
One row per participant in a play. Since migration 009 a participant is either a
real account (`player_user_id`) or a free-text label (`player_display_name`);
migration 013 dropped the old `buddy_id` reference.

**Two invariants, both added by migration 023 after imports broke them.** Every
play has **at least one** of these rows — a play with an empty scoreboard counts
towards nobody's record and leaves no ghost for anyone to claim — and **no
account holds two seats** on one play, enforced by
`uq_bgb_play_players_play_user`, a partial UNIQUE on

finalize and both wizard importers; `PUT /plays/{id}` is the one write path that
is not that RPC and checks them in `PlayUpdate`; the BGG sync writes the tables
directly and normalizes in `bgg_link_routes._player_rows`, where a play BGG
recorded no roster for is seated with the syncing account. All three importers
used to write rows that broke one or the other — see the migration header.

## API Endpoints

### boardgamebuddy_bgg_push_queue

Outbound queue for BgB→BGG (migration 070). One planned change per game per user, `UNIQUE(user_id, bgg_id)`, drained by a `BackgroundTasks` worker at one BGG write per throttle tick. `change` is `add` / `update` / `clear` and `target_status` is NULL exactly when `change='clear'` (enforced by `bgb_push_change_status`). `payload` JSONB is the **complete form field set, frozen at plan time** — the three flags BgB owns at their target values plus every other `<status>` attribute echoed verbatim — so the worker never re-reads BGG and a shelf edit mid-push cannot produce a half-old, half-new write set. `bgg_collid` is nullable and is what the payload branches on, **not** `change`: a game flagged only `fortrade` is invisible to the status sweep, so a change planned as `add` can still turn out to have an existing BGG collection row, and sending no collid for one of those would create a duplicate and orphan the user's rating and comment on the original — `bgg_push_routes._resolve_collids` looks those up by id before queueing. `attempts` promotes to `status='error'` after 3; a 429 backs off without burning one, and a 409 (dead session) aborts the whole run rather than hammering BGG's login with a bad password. State lives in Postgres, not memory, so a restart mid-push resumes instead of replaying. Deliberately **not** `kind='push'` on `boardgamebuddy_bgg_pending_imports`: `bgb_bgg_sync_status` counts every row for the user with no `kind` filter, so a queued push would inflate the *import* poll's `pending_count` and pin it open forever.

Four datasets (`collection`, `plays`, `plays_detail`, `guides`), each with a **live** count so the Settings sheet can say "Reference guides · 0" rather than making somebody download an archive to find out there is nothing in it. It was eight: `profile`, `expansions`, `buddies` and `achievements` were retired — the profile row is one line the README's own header already states, owned expansions now ride in `collection.csv`, and the other two were checkboxes nobody opened this sheet for. - `GET /api/v1/boardgame_buddy/export?dataset=collection&dataset=plays` — the archive itself, `application/zip`, one CSV per thing, plus a `README.txt` naming every file and its row count. **Plays is two ticks, deliberately.** `plays` is `plays.csv` alone: one row per play, complete on its own, with the roster folded into a `|`-delimited `roster` cell of `name:score` pairs (a bare name where a play kept no scores) beside `winners` and `expansions` cells in the same form — so the file has the same shape for a two-player game and a seven-player one and never grows a column. `plays_detail` is `play_players.csv` + `play_expansions.csv`, the same plays broken back out one row per seat and per expansion for pivoting, joined on `play_id`; it deliberately does **not** re-emit `plays.csv`, because two ticks writing one filename with different columns is a collision waiting for whoever ticks both. The summary is lossy on purpose — per-round scores only exist in `play_players.csv`, and a name containing `|` (or, in `roster`/`winners`, `:`) has it flattened to a space in the summary columns only, with the detail files carrying it verbatim. `collection` is the other multi-shape tick, and goes the other way: shelf rows and owned expansions share **one** `collection.csv` under a leading `row_type` column (`shelf` / `expansion`), because nobody thinks of their shelf and the expansions on it as two things to ask for separately. An expansion carries no shelf status, so `status` is left blank on those rows rather than given an invented `owned_expansion` value the app's own shelf never writes. Both play datasets read the same rows, so the plays/seats/expansions load is cached on a per-export build context and paid for once. **Self-only, and there is deliberately no `user_id` parameter** — profiles being public was not a decision about bulk-dumping somebody's notes, purchase prices and private BGG comments. `plays` is the union of plays the caller logged and plays they were seated in, matching what `GET /plays` shows, with `logged_by_you` telling the two apart. Nothing off `boardgamebuddy_profiles` is exported for its own sake any more — not the linked `bgg_username`, and so by construction not the encrypted BGG password or the live session cookies sitting beside it on that row. Every read is paged at 1000 (`EXPORT_PAGE_SIZE`) because a PostgREST cap would otherwise truncate an export **silently**, and the whole build runs in one `asyncio.to_thread` — the Supabase client is synchronous and this is dozens of round trips. CSVs are UTF-8 **with a BOM** (Excel reads a BOM-less file as the system codepage and mangles accented game names) and cells that would run as a spreadsheet formula are tab-prefixed. `shared-backend/routes/boardgame_buddy/services/export_{csv,reads,plays,service}.py`; covered by `shared-backend/tests/test_export.py`

Returns `{items, total, parted_total, truncated, generated_at}`, pre-sorted the same way `/collection/grid` sorts by default so the caller can slice without re-sorting. Deliberately takes **no** search/filter/page params — one cache entry per shelf, with the visible window, filter and search all derived on the client. One DB round trip (`bgb_collection_shelf`), down from the grid's two-to-three: it reads the denormalized `game_*` columns rather than embedding the games row — `image_url` is the one exception, a LEFT JOIN added in migration 055 because 020 never denormalized the full-size art — folds play stats in as a LATERAL, and computes `expansion_count` in SQL. `truncated` marks a shelf past `limit`, and the web client then falls back to `/collection/grid` for search/filter rather than narrowing an incomplete list. This is what the Collection and Wishlist spokes use; scrolling to the next batch there costs **zero** requests. The Collection spoke's Expansions tab calls the same endpoint with `exclude_expansions=false` and groups the result client-side (`web/domain/expansion-tree.js`); it is cached under a separate key (`|all` vs `|base`) so the superset can't overwrite the flat grid's entry.
- `GET /api/v1/boardgame_buddy/collection/grid` — paginated owned collection sorted by `last_played_at DESC NULLS LAST, added_at DESC` by default. Supports `search`, `players`, `playtime_min/max`, `play_mode`, `exclude_expansions` (default true), `sort` (`last_played` / `added_at` / `alphabetical`), and `user_id` (target user; defaults to the viewer — owned and played shelves are public, `status=wishlist` for another user returns an empty page, as `/collection/shelf` does). `status=owned` matches `('owned','prev_owned')` and reports `parted_total`, exactly as `/collection/shelf` does — a shelf past the shelf endpoint's row cap falls back here mid-scroll, and a different row set would reshuffle the grid under the reader. **One round trip** (`bgb_collection_page`, migration 024): the filter, the sort, the count and the page all run in Postgres, with play stats and `game.expansion_count` — the catalog-wide number of expansions pointing at that base game, which drives the tile badge — folded in as LATERALs. It previously read the *whole* shelf on every page turn and did all four in Python across two round trips (three on the played shelf); worse than slow, those reads carried no limit, PostgREST silently caps an unbounded select at 1000 rows, and the filter ran **after** that truncation — so on a large shelf a matching game could be missing because it sat past row 1000. Every ordering now ends in a unique tiebreak (the game id), so a tied row can no longer appear on two pages or on none. Still the paginated/server-filtered path, used by the web game explorer; the Collection and Wishlist spokes moved to `/collection/shelf`.

Photos are read once and dropped with the request, never persisted: a play photo earns a bucket row because the play keeps it forever, whereas a picture of somebody's notebook is scaffolding for one call. Each is capped at 4 MB decoded and 8 MB across the request, and a photographed note goes to `GEMINI_MODEL_STRONG` (`gemini-flash-latest`) instead of Flash-Lite — Lite is fine at restructuring text that is already text and unreliable at deciding whether a smudged row of tally marks is fourteen or fifteen. The wizard filters both roster cases out before it sends, so those codes are a backstop rather than a path users travel. Every play carries a `client_key`, so re-running a half-finished import lands only what is missing. Each play may also carry an `import_group_id` (migration 005) and an `import_batch_id` (migration 007) tying it to the other plays in its run; the client computes that from the play's own content — a score on any seat or a note disqualifies it — so what the feed collapses is what a reader genuinely cannot tell apart, not merely what the model wrote as one line.
- `POST /api/v1/boardgame_buddy/plays/{play_id}/leave` — a non-owner participant self-removes from a play they didn't take part in. Turns their `player_user_id` row into a ghost (nulls the id, keeps `player_display_name`) instead of deleting the play — the owner keeps it and sees them as a named ghost; the play drops out of the leaver's history/played-with. 400 if the caller owns the play (use edit/delete), 404 if they aren't a player in it. - `POST /api/v1/boardgame_buddy/plays/reactions` — say **"Good game"** to plays; body `{play_ids: [...]}`. The surface is the feed's session footer, so one tap covers a whole game night and the body is a list; one play is a list of one, which is what a per-card control would send if one ever ships. The server mints one `reaction_group_id` for the tap, **drops any play the caller logged** (you don't congratulate yourself, and a session can contain plays logged by several people) and upserts `ON CONFLICT DO NOTHING`, so a double tap keeps the original row's group id and `created_at` rather than re-stamping them. Returns `{play_ids, reacted, reaction_group_id}` where `play_ids` is what was actually affected — shorter than what was sent whenever the caller's own plays were in it — so the client reconciles against it rather than assuming its optimistic patch covered everything. **200, not 201:** the write is idempotent and "Created" would be a lie half the time. Registered ahead of `play_routes` in `__init__.py`, and that ordering is load-bearing — FastAPI resolves in declaration order, so `DELETE /plays/reactions` would otherwise be swallowed by `DELETE /plays/{play_id}` with `play_id="reactions"`.
- `DELETE /api/v1/boardgame_buddy/plays/reactions` — take it back; same body. Deletes only rows whose `user_id` is the caller, so there is nothing to authorize and no ownership check: a play deleted since the page loaded should still let its stale row go. There is deliberately **no GET** — the counts, `viewer_reacted` and the avatar stack ride the feed payload (`bgb_feed_plays`, migration 016), so reacting never costs the client a read. Neither route busts the client's cached feed page — that would make every tap refetch the feed, which is the cost this design exists to avoid — so the accepted write is folded into that page instead (`Feed.applyReaction`, which re-persists the entry via `bgbCache.persist`). Without the write-back the patch lived only as long as the tab did: `bgbCache` hands its value out by reference, but localStorage holds a copy taken when the page was fetched, so the next launch inside the 24h stale window painted the pre-tap state and a "Good game" you had just taken back came back with it.
- `GET /api/v1/boardgame_buddy/notifications?limit=&before=&before_key=` — everything that has happened **to** the viewer, merged into one feed (`bgb_notifications`, migration 009). Returns `{items[], next_cursor, next_cursor_key, unread}`. Each item carries `kind`: `play_link` (somebody seated you in a play they logged), `buddy_request` (somebody asked to be your buddy), `buddy_accepted` (somebody accepted the request you sent). `kind` says which block of fields is populated — the `play_*`/`game_*` group on `play_link`, `edge_id` on the two buddy kinds — and `actor_*` is the only group on all three, because "who did this" is the one question every kind answers. A `play_link` item is one **act of linking**, not one play: `play_group` is `batch` (one paste of an imported note), `run` (identical plays inside a pre-batch import) or `act` (everything else, keyed on owner + `linked_at`, which collapses a retroactive `bgb_link_ghost` across forty old plays into the one thing it was). Without that grouping a 214-play import is 214 rows and the multi-select it exists for is pointless. **The cursor is a pair** — send `next_cursor_key` back alongside `before`, because three sources feeding one ordering makes ties on `occurred_at` ordinary and a cursor on the timestamp alone silently drops every row sharing a page boundary. **Deliberately omits the roster, notes, photo and scores:** this screen necessarily shows plays logged by people the viewer may not be buddies with — you cannot decide whether to unlink from something you can't see — which is wider than the feed's accepted-edge rule, so it is held to the minimum that supports the decision: who, what game, when, how many **The client never fetches this cold on the common path.** `/bootstrap` carries the first page, the tab-focus `warmRefresh` renews it and the bell's `pointerdown` starts one, all coalesced into a single request by `bgbCache`'s single-flight map; the entry is written `freshTtl === staleTtl` at 20s so it is a prefetch and never a stale read — past that the screen waits on the network as before. Server-side the two reads (page, unread) run concurrently in threads rather than back to back on the event loop, and migration 010 rewrote both RPCs so neither reads more of the account than the page needs (see `db/migrations/boardgamebuddy/010_notifications_perf.sql` for the equivalence arguments).

- `POST /api/v1/boardgame_buddy/bgg/check` — the comparison both sync buttons act on. Sweeps the live BGG collection (the same 8 throttled `(subtype, status-flag)` requests the import makes, reused via `bgg_collection_read._fetch_collection_items`), reads the BgB shelf, and classifies every game **in both directions from one sweep**: the push view (`add` / `update` / `clear`) and the pull view (`add` / `update` / `held`). Statuses are compared **derived, not raw** — the importer collapses BGG's `wanttoplay` into `wishlist`, so a wanttoplay-but-not-wishlist game derives to `wishlist`, matches a BgB wishlist row and is left alone; comparing raw flags would push `wishlist=1` onto it purely because the import is lossy. `held` is the pull-side expression of `_hold_prev_owned`: a game marked Prev. owned in the app is never resurrected as owned. A POST, not a GET, because of one write — games on the BGG shelf that BgB's catalog has never seen are queued as `kind='catalog'` pending imports so the comparison can name them instead of listing bare ids; that imports the **game only, never a shelf row**, so those games still read as "only on BGG" and the push still decides their fate. Returns `{bgg_username, checked_at, in_sync_count, local_total, remote_total, push_total, pull_total, push_changes[], pull_changes[], unpushable[], truncated, catalog_pending, warm_up_retry_pending}`; item lists cap at 500 while the totals stay true. 409s while an import or a push is draining. The finished plan — and the sweep it was built from — is parked in the in-process cache for 5 minutes (`services/bgg_check_cache.py`, matching the FE's `DIFF_MAX_AGE_MS`) so **neither sync button repeats this work**; `checked_at` is the key the push matches its stored plan against. Same in-process argument as `bgg_progress`: the sweep dies with the request that ran it, so a durable row would outlive the only thing that could vouch for it, and a miss just means the sync sweeps as it always did.
- `GET /api/v1/boardgame_buddy/bgg/check/progress` — what an in-flight comparison is doing right now, so the flow screen can tick a checklist instead of spinning for 40 seconds. Returns `{state, kind, check_id, started_at, updated_at, steps[], warm_up_failed, error}`, where each step is one phase (`guards` / `collection` / `shelf` / `compare` / `catalog` / `collids` / `queue`) carrying `state`, an optional `done`/`total` and an optional `retry` `{attempt, of, wait_seconds, resume_at}` while BGG is warming up. Polled at 1s **alongside** the in-flight `POST /bgg/check`, which is only possible because that handler spends most of its time in `asyncio.sleep` between throttled BGG calls. The ledger lives in the in-process cache (`services/bgg_progress.py`), not the DB, because the sweep is in-handler work: a restart kills the sweep, the connection and the result together, so a record that dies with them is correct where a durable row would outlive all three and lie. `state='unknown'` therefore means *no record* — a restart, or a second uvicorn worker — and the client renders it as **still working**, never as done; completion comes from the POST's own resolution. `POST /bgg/push` writes the same ledger under `kind='push_plan'` while it re-plans, which is otherwise a blank 10-40s wait.
- `POST /api/v1/boardgame_buddy/bgg/push` — make BoardGameGeek mirror the BgB shelf. **Collection status only** — `own`, `prevowned`, `wishlist` — with every other `<status>` attribute echoed back verbatim, so ratings, comments, private info and the user's own `want` / `fortrade` / `wanttobuy` / `preordered` flags are never authored. A game flagged on BGG but absent from the BgB shelf has those three flags *cleared*; the collection item is never hard-deleted, so its rating and purchase details survive. Commits the plan **the server** built for the comparison the user reviewed: the client sends only `checked_at` and gets back the stored plan or nothing, so it still cannot dictate a single write, and a stamp that does not match the stored one re-plans from scratch rather than guessing. Falls back to a full re-sweep when the cache no longer holds it (a restart, or a comparison older than 5 minutes), which is what it used to do unconditionally — charging the user the same 40 seconds a second time for pressing a button on the answer. Then writes one row per change to `boardgamebuddy_bgg_push_queue` and drains it with a `BackgroundTasks` worker (`BGG_PUSH_THROTTLE_SECONDS`, default 2.0s). **Refuses outright (503) when the sweep hit a warm-up failure**: a batch that gave up returned zero items, which reads as "not on BGG", and pushing that plan would clear flags off games we simply failed to see. Body `{checked_at}` only. Returns `{bgg_username, queued, adds, updates, clears, unpushable, warm_up_retry_pending, reused_comparison}` — `reused_comparison` is what the push log narrates, so it never claims a re-check nobody ran. The worker aborts the whole run on a `BggRefusedError` as it does on a 409: every remaining row would be refused identically. 409s while an import is draining, and `POST /bgg/sync` 409s while a push is — both directions drive the same BGG session.
- `GET /api/v1/boardgame_buddy/bgg/push/status` — the push poll target, one RPC (`bgb_bgg_push_status`). Same shape as the sync status plus `session_errors[{game_name, message}]`: a half-failed import can be re-run and idempotency cleans up, but a half-failed push has left flags on a third-party account in an unknown state, so the games have to be named.
- `POST /api/v1/boardgame_buddy/games/{game_id}/chapters` — create a brand-new chapter (type + title + markdown) and auto-add to the creator's guide
- `POST /api/v1/boardgame_buddy/games/{game_id}/chapters/generate` — AI-draft a chapter of the given `chapter_type` for this game and return `{chapter_type, title, content}`. Body also takes an optional `prompt` (≤500 chars, 422 past that) — the free-text steer from the create wizard's head-start step ("just the endgame trigger"); blank or absent drafts a general chapter for the type. **Saves nothing** — the wizard loads the draft into its form and the user reviews, edits, and saves it themselves. Synchronous (the user is waiting in the wizard), backed by Gemini Flash Lite via the shared `shared-backend/gemini.py` caller; 400 on an unknown chapter type, 404 on an unknown game, 502 when the model call fails (missing `GEMINI_API_KEY`, safety block, transport error). The prompt is four banner-delimited sections in a fixed order — **1** what to write (game, year, chapter type), **2** supported formatting and preferences, **3** the player's optional guidance, **4** the output format — and the markdown spec in section 2 is the app's own authoring guide, so see the sync note below. The game's BGG `description` is deliberately **not** in the prompt: up to 1500 characters of publisher marketing copy was the most expensive part of it and the least load-bearing, since a model that doesn't know the game is told (section 1) to write a fill-in skeleton rather than lean on a blurb. Section 3 is untrusted text a player typed into a form, so it is delimited, truncated, and told by name which sections it cannot change.
- `PATCH /api/v1/boardgame_buddy/chapters/{chapter_id}` — edit own chapter (creator-only)
- `DELETE /api/v1/boardgame_buddy/chapters/{chapter_id}` — delete from pool (creator or admin); cascades to user_chapters + reports
- `POST /api/v1/boardgame_buddy/chapters/{chapter_id}/report` — body `{reason?}`; flag a chapter for admin moderation. Idempotent per user.
- `GET /api/v1/boardgame_buddy/games/{game_id}/my-chapters` — chapters the caller has added to their guide for this game (empty list when none). Supports `?expansion_ids=a,b,c` to also merge in chapters from the listed expansions in one round-trip; each row carries `source_game_id` / `source_game_name` / `source_color` for FE colored-dot rendering.
- `POST /api/v1/boardgame_buddy/games/{game_id}/my-chapters` — body `{chapter_id}`; add an existing pool chapter to my guide (idempotent)
- `DELETE /api/v1/boardgame_buddy/games/{game_id}/my-chapters/{chapter_id}` — remove from my guide (does NOT delete the chapter)
- `POST /api/v1/boardgame_buddy/games/{base_id}/expansions/{expansion_id}/toggle` — body `{is_enabled}`; per-user expansion toggle. Read back by this module's expansion list and joined into `bgb_game_detail_bundle`; the chapter system does not consume it, and the web client does not call it (kept for the bundle's `is_enabled` column)

Batches 20 games per BGG call and caps the pass at `limit` (default 200), returning `{updated, failed, remaining}`; the admin panel re-invokes until `remaining` is 0. Note this sits under `/games/admin/` unlike the older bulk image route at `/games/refresh-images`

**Inbound-only, and deliberately NOT in the router's path table:**

- `/b/<token>` — the add-a-buddy QR link. `init.js` matches it before `matchPath()` and rewrites it to `{name: "buddies", params: {qr: token}}`, which inherits the `pendingRoute` stash and therefore the bounce through `/auth` for a signed-out scanner. It stays out of `_routes` because nothing in the app ever navigates *to* it, and `pathFor()` resolves by name with `.find()` — a second entry named `buddies` would silently make every future `router.go("buddies")` build the wrong URL. `buddies-view` consumes the param and `replaceUrl`s the token straight back out of the address bar, so a refresh or a much later back navigation can't replay a spent code.

**Routes intentionally not in the URL:**

- `splash` — transient loading view between boot and Supabase auth resolving. Never pushed to history, never appears in the back stack. It is also the one screen with no bottom nav, so a boot that never finishes has no escape hatch: `init.js` arms a **12s watchdog** that routes forward anyway — to the normal destination when a session is in hand (the destination paints its own skeleton and reconciles when `/bootstrap` lands), to `/auth` when nothing resolved at all. The fallback never sets `_bootRouted`, so a late auth callback still routes the user correctly on its own.

**Back-stack semantics:** `router.back()` defers to `history.back()`; the popstate handler replays the entry's state (or falls back to `matchPath()` for direct loads). An internal `_stack` is kept in parallel only because the browser doesn't expose history-entry metadata — `peekBack()` reads it to label back affordances ("Back to game details", etc.).

## Screen Flow
Bottom nav has three tabs: **Feed**, **Log**, **Profile**. On the wide layout tier (≥ 1024px) the same nav stands on its end as a left rail and also carries the header's brand mark, bell and gear — see the design-system section above.

1. Auth (login/signup) → splash → **first-run setup, when the profile carries `needs_setup`** → 2. **Feed** (home): chronological mix of plays from the viewer and their accepted buddies, plus inline "hot this week" / "buddies you may know" rails. A search pill at the top opens the **Game Search** screen.

   **Cards are bundled into sections client-side, on two different keys, because the feed carries two different things** (`groupCards` / `sessionKey` in `views/feed-view.js`). A **game night** keys on `played_at | participants`: the people at the table are what make it one night, and they are the clickable names in its header — "You and Sam played 3 games". An **import** keys on `played_at | logger` and is headed "**JasBot imported 19 games**". Grouping an import by roster is what the second key exists to stop: a pasted notebook writes a play per line and the rosters differ line to line, so one afternoon's import used to land as five or six stacked sections — each with its own border, header and "Good game" footer, all under one date heading, each saying almost the same thing. The flag is `import_batch_id` (on the feed payload since migration 022), **not** `import_group_id`: the group id is set only on plays the importer judged indistinguishable from another in the same paste, so every one-off in an import carries no group id and would have been left behind as its own section beside the runs it arrived with. Both keys deliberately stay within one day, since `render()` prints the date once above each day's sections; two pastes covering the same day still merge, because to the person reading the feed they are one day's import. Each card inside a section keeps its own winner line, and a run of identical plays keeps its `group_count` stack ("4 PLAYS"), so collapsing the sections costs no information — only the repeated chrome. A live-logged play never joins an import section: it carries no batch id, so it keys on its roster as it always did.

   **First-run setup is five counted steps, run from `init.js` and nowhere else.** (The step-by-step below predates the slide deck that replaced the three modals — see `Docs/ARCHITECTURE.md` §4.3c for the current shell; the steps themselves are unchanged, plus **Notifications** at position three: the offer that turns an opt-in feature nobody would otherwise find into a real choice, placed straight after Add buddies so "we'll tell you when they accept" lands on requests the user sent ten seconds earlier. Turning them on there sets `push_tier` to `all` and subscribes the device; declining leaves the account off and writes the receipt `ui/push-prompt.js` reads, so the boot-time card does not immediately ask again.) Step one is the existing "Create your profile" card (`PolaroidPopup.avatarCustomizer` with `includeNameField`); saving it clears `needs_setup`, and dismissing it leaves the flag set so the whole sequence returns next load. Step two is **Add buddies** (`widgets/add-buddies-modal.js`): a wrapping grid of suggestions the user multi-selects, with one button that sends every tick as a single batch and one that skips. That card is no longer setup-only — the Buddies screen's Add button opens the same one, which is why its dismiss label is a parameter ("Skip" only makes sense inside a sequence) and why it tolerates an empty suggestion list, since its search field always gives the user something to do. The guard that stops first-run opening an empty one survives for its own reason: an account ninety seconds old has nobody to search *for*. Step three is **Link BoardGameGeek** (`widgets/onboarding-bgg-modal.js`). All three are modals rather than router views — the sequence has no URL worth deep-linking and a real view would leave a back-stack entry that means nothing once setup is done.

   **The BGG step goes last because it is the only one that can take minutes.** The two before it are a tap and a batch of taps; an import of a large collection legitimately sits on screen while the worker fetches a game at a time, and what waits behind the last card is the user's own feed rather than another step. Second, it would have parked "Add buddies" behind an import nobody asked to watch to the end.

   The buddy grid's tiles are **the same canonical buddy-suggestion tile the Feed and Buddies rails render**, in its `select` mode instead of its `add` mode (`ui/buddy-suggestion-rail.js`, one component with an `opts` variant per `.claude/rules/ui-object-design.md` §2). Step two is entirely best-effort: if the suggestion fetch fails, or returns nobody, it is skipped silently and the user moves on with a finished profile — an "Add buddies" screen with nothing on it reads as a broken feature in the first minute of the app. A transport failure *during* a send keeps the modal up with the ticks intact and an inline retry, because nothing was sent; per-target rejections come back inside a 200 and close it.

   **Step three is one card in two states.** The first is the pitch plus a BGG username / password pair, with **Skip** and **Link account** as equal-weight 52px buttons — skipping is a real destination here, and the copy says the link is still one tap away in Settings. On a successful `POST /bgg/link` the card switches, in place, to the import: `POST /bgg/sync` goes out immediately and the step log stays on screen, polling `GET /bgg/sync/status` every 2s, so the user watches the collection and play counts land and then each previously-unknown game's title stream into a bullet list as the worker fetches it (~1.5s each). The heading and the intro line are patched alongside the log — "Importing your games / this may take a while" while it runs, "Your games are in" when it lands — because a screen still claiming to be importing above a finished log is a contradiction. **Leaving does not stop the import**: the primary button reads *Continue* while the queue drains and *Done* once it is empty, ×/Escape/backdrop all mean the same thing, and the collection status map and the feed are invalidated on the way out because a half-drained import has already written every game we already knew about. The link form is never re-rendered — errors and the "Linking…" state patch in place, so the credentials being typed survive them; a rejected login clears only the password and puts the caret in it.

   **The step log is one component, `ui/bgg-import-log.js`, shared with Settings' Sync button** — it was `SettingsView._renderBggProgress` before this step needed the same readout of the same import (`.claude/rules/ui-object-design.md` §4). It is a pure function of the `POST /bgg/sync` summary and the latest `GET /bgg/sync/status`; the caller owns the poll. Two behaviours it made shared rather than doubled: `Bgg.importDrained(status)` is the one definition of "the queue is empty" (session counters, not the lifetime `pending_count`, so a row left over from an earlier failed sync can't pin the poll open), and `Bgg.invalidateImportedData()` is the one post-sync cache drop. `Bgg.sync()` also runs on a **120s deadline** rather than the client's 15s default (`api.post(path, body, {timeoutMs})`): the handler fetches a whole BGG collection and play history before it answers, and a 15s abort was both routine and a lie — the server finishes the sync and queues the worker whether or not the client is still listening, so both surfaces now report a tripped deadline as "still importing in the background", not as a failure, and offer no *Try again* beside it.

   Step three is best-effort like the one before it: a failed link keeps the user on the form, a failed sync offers one retry and a Done, and every exit lands them on their feed with a finished profile. Note it can only be *offered* once — saving the profile in step one already cleared `needs_setup`, so a reload mid-sequence skips straight to the feed. That is the same trade step two makes, and the reason both steps say where to find the thing again.
3. **Log a play**: the Play tab is split — **Host on top, Join on the bottom**.
   The Host half offers three cards: **Host a game** drops straight into the cascading three-screen flow (`play-flow`) with an empty game slot; **Another Round** (only when there's a recent play) reseeds the last game + roster and lands on Gather; **Game Explorer** opens `/games`, where players / play time / type filters over the user's collection or the whole library help pick a game — selecting one opens Gather with it prefilled. A "Resume hosting?" banner sits above the cards whenever a non-terminal draft exists.

   **Host a game always means a NEW game** — fresh draft, fresh session code, empty game slot — even when a resumable draft exists. The Resume banner is the only thing that continues a session. Starting a new play ends the previous one (`bgb_create_session` abandons the host's other open sessions), the same way Another Round already abandons deliberately. Until 2026-08-25 the card skipped its draft-clear whenever a resumable session existed, so a host who tapped it landed back in the old session, code and all.
   The Join half is the `JoinPanel` widget: a 5-char code input plus a 10s-polled list of active sessions where the user is a participant or the host is a buddy (sessions past Gather are labelled **Spectate**).
   The Log a play cascade has three snap-scroll screens:
   - **Gather** — pick a game, set game type (competitive/team/co-op), manage the player list. Both pickers are **bottom sheets** (`widgets/game-search-sheet.js`, `widgets/player-picker-sheet.js`) on the shared `ui/bottom-sheet.js` shell. They replaced inline `position: absolute` dropdowns: the Players card is the lowest on the screen, so with a few players seated `ui/dropdown-fit.js` had to squeeze the buddy list to its own 132px "keyhole" floor on top of the docked Continue CTA, and it still ran off the bottom edge. A sheet is `position: fixed` and sized off `--bgb-vv-h`, so there is no fit pass, no flip, and no z-index race with `.cascade-cta-wrap`. The player sheet is **multi-select** — tick several, then Add — and tick order is the seating order. Ticked people ride at the top under **Selected**, in that order, and leave the body list, so the sheet always shows what it is about to do rather than scattering your picks back through forty buddies the moment the search box empties; a query filters that section like every other row, because a pick that does not match what you typed is not an answer to what you typed. The game sheet hosts the same `widgets/game-finder.js` as before, its results the sheet's own scroller rather than an overlay (the finder has no other mode now); library search and the BGG escalation are unchanged; the offline branch is gone — a failed `/search` falls back to the device pool instead of a check taken before the request. The Game card also surfaces the three most recently played games as tappable tiles, which used to be invisible until the search input took focus. **Each player row carries a drag handle: hold it and drag to reorder the roster.** The players array *is* the scoring grid's column order — `round-score-grid.js` maps it straight to the columns with no sort anywhere — so moving a row here moves a column there, and the order is pushed to the lobby (`PUT /participants/order`, debounced 300ms and flushed before the phase advance, since the RPC is Gather-only) so every spectator's mirror follows. The gesture lives in `widgets/player-reorder.js`: one *delegated* pointer machine per `<ul>` (the poll rebuilds the rows with `innerHTML`, which would orphan per-row listeners), pick-up after a 120ms hold or 3px of movement *on the grip only*, a fixed-position clone with the live input values copied across (`cloneNode` copies the value attribute, not the property), and the dragged `<li>` moved through the live list as the pointer crosses each row's midpoint — the list parts around it, so there is no separate drop indicator to keep in sync. The lobby poll stands down while a drag is in flight (`PlayerReorder.isDragging()`) because its repaint would replace the row under the user's finger, and a capture-phase click swallower stops the post-drop synthetic click from hitting whichever row landed there. `_movePlayer` repaints both index-keyed surfaces rather than patching them, because `_patchScoringCells`, `_refreshTotalsCells` and `_setInitials`'s `heads[i]` all address columns positionally. A session code opens on entry and is shown at the top of the screen; other phones can join via code while the host is on Gather. Joiners stream into the player list via polling.
   - **Play** — scoring grid on top, full-width reference guide below. (It was the other way round until the guide's parchment scroll, open by default, grew long enough to push the grid off the first screen: the grid is what the host touches every round, the guide is what you reach for occasionally, so the thing you use most is the thing you don't scroll to. The spectator mirror carries the same order.) **The host is the only person who scores.** They have full grid access (add rounds, override winners) and every cell they touch streams one-way to everybody else via Supabase Realtime against `boardgamebuddy_play_session_scores`; joiners and spectators get the same grid, read-only, and cannot write at all (RLS enforces it — migration 053). Guests are on the table like anyone else: scores are keyed by participant row rather than by account, so a guest's column streams too. Scores may be negative; a "± Negative" header toggle (default off, remembered) reveals per-cell +/− sign buttons for keyboards that lack a minus key.

     **Tapping any column header switches every column between the player's bubble and their name, and the choice is remembered.** One preference (`RoundGridNames`, `bgb.scoring.headerNames`) shared by the host grid, the spectator mirror and the play-detail popup, so the next game opens on the last setting. It is an *override*, not a default: while the key is absent each surface keeps its own starting look (the live grids on names, which is what you scan mid-game; the popup on bubbles), and the first tap anywhere settles it everywhere. The header button mutates the `is-named` class on every `.scoring-head` in the document directly rather than routing through a host repaint — the two states differ by one class, so there is nothing to rebuild, and an `outerHTML` repaint would reset `.scoring-table-wrap`'s horizontal scroll (snapping a 6-player grid back to column 1), blur whatever cell was being typed in, and hand the read-only spectator mirror a host contract it has never needed. Reading the preference at paint time is also what makes the choice survive the repaints that used to silently reset the old per-column toggle: a round added, the ± pill, a play-mode change, a player added, or the popup's re-render on every keystroke.

     Joiners used to own their own column. Collapsing that to host-only removed the whole reconciliation problem it created — the per-column edit mode in the grid widget, the caret-preservation dance on every repaint of the mirror, the two-principal RLS policy, and the finalize-time merge of "what the host typed" against "what joiners streamed in" that migration 052 existed to un-break.

     The read-only grid is the same widget in its other mode: same columns, same score font, same round labels, same Total row, minus the input chrome. Read cells carry `.scoring-cell--read` and deliberately **not** `.scoring-cell` — the border/fill/radius there is input chrome, and a table of boxes nobody can type in reads as a different component.

     **The mirror is built out of the host's screen, card for card.** The spectator's Play step carries the same cards in the same order the host sees: the game (`Now playing`), the session code, the scoring grid, then the reference guide (with the game's Rulebook CTA — the bundle has carried `rulebook_url` all along). Both sides use the same `.cascade-card` / `.cascade-invite` / `.cascade-game` families and the same three-column screen header, whose left 44px slot rolls the phase back for the host and leaves the session for the spectator. Two things went the other way: the crumb bar that used to sit above the cascade (`Session {code}`, the view's only back affordance) is gone — the code has its own card now and the back arrow moved into the screen header — and `<main data-view="session-viewer">` dropped its `px-4 py-4`, which had been stacking on top of `.cascade-screen`'s own 12/16px gutters and squeezing every spectator card, the scoring grid included, narrower than the host's.

     **A late spectator reads the grid through the bundle, not the table.** A user who joins *after* Gather gets no row in `boardgamebuddy_play_session_participants` (`bgb_join_session`), and `bgb_session_scores_select` is scoped to host-or-participant — so their own client reads the scores table and gets zero rows back (not an error), and Realtime, gated by the same policy, never fires for them. Their grid used to sit blank at 0 for the whole game. `bgb_session_bundle` now folds a `scores` array into the (already unauthenticated, code-as-token) `GET /sessions/{code}` response while phase='play' (migration 054), and `LiveScores.seed()` takes it. The RLS SELECT policy was deliberately **not** broadened — an unfiltered grant would dump every open session's scores to every authenticated user. Two rules keep the seed honest: it is the base only for a client that has never read a row itself (`isSeedOnly()`), so a readable table always wins and an empty read from a client that can see the table means "the host cleared it", not "fall back to a stale bundle"; and the session viewer's poll drops to a 4s cadence on the seeded path, because for those spectators the poll *is* the live channel and the "Realtime is carrying it, stand down" gating would otherwise freeze the grid.

     **The Total row is the visible cells, added up — always.** `widgets/round-score-grid.js` owns the one implementation (`window.roundGridTotal`), summing the same `getCellValue` resolver over the same round count it just rendered; there is no "total resolver" opt for a caller to supply its own arithmetic, and any surface that repaints the totals row between renders (the host grid, the joiner's mirror, the play-detail popup) calls that same helper. Two rules keep it honest upstream: every player carries a dense `roundScores` array of the grid's full length (`_normalizeRoundArrays`), and a typed edit repaints the total from local state *before* mirroring to Realtime, never awaiting the write. On Save the host folds the live overlay into its own draft (`_commitResolvedScores`) so the recorded play is the grid that was on screen, and `PlayerEntry` on the backend re-derives `score` from `round_scores` whenever a breakdown is present.
   - **Settle Up** — host only. Date, a **Where** card, optional photo upload + "Key moments" notes textarea (reuses the play's `notes` column), then Save. The Where card arrives already filled in — `domain/geo.js` resolved the country from the device timezone when the draft was born — and opens `widgets/country-picker-sheet.js` (search matches the localized country name *and* the raw code, with a pinned "Don't record a country" row above the results). It is shown rather than recorded silently on principle: a value the app writes onto a play and never admits to is not a thing this app should have, and showing it is what makes it correctable, which is the only way the eventual by-country numbers are worth reading. Save calls `/sessions/{code}/finalize` which merges live scores into the canonical play and marks the session finalized.
   When the host advances Gather→Play, the lobby closes (`POST /sessions/{code}/join` returns 409 thereafter). When the host enters Settle Up, every non-host joiner sees a polaroid splash popup centered on the screen with the game thumbnail and current winner; tapping the X dismisses to a refreshed feed.
   **The host's Save doesn't wait for anything.** Tapping Save puts the same "Well played!" polaroid up in the same frame, with the host-only **Another round?** and the corner **X** live immediately, and runs the finalize behind it (photo uploading *in parallel* rather than after). The card carries no save state at all: the upload queue guarantees the play is recorded, so there is nothing for the host to watch. A failed write — any failure, not just a network one — hands the play to `domain/outbox.js` under the same `client_key` the live attempt carried, so a request that actually landed and only lost its response can't be written twice; the header's upload indicator owns it from there, and the card says "Saved on this device" if it's still up. The one case that stops the host is the queue write itself failing (no room in localStorage): that gets a modal and puts the draft back on Settle Up. A failed photo upload is still just a warning line on the card. **Another round?** opens a *new* session pre-seeded with the same game, expansions, play mode and roster — teams included, scores and winner reset — landing on Gather under a new code. Because it can now be tapped mid-write, two things are guarded: every post-write touch of view state is skipped when the draft it belonged to has been replaced (`_isStaleSave`), and the new lobby's `POST /sessions` waits for the previous write to settle (bounded at 8s) — `bgb_create_session` abandons the host's other open sessions, and minting early would close the lobby the finalize is about to write to, leaving spectators on 'abandoned' instead of their wrap-up card. The carried-over roster is pushed to the new lobby as participants, so the previous joiners see it in their Join list.
   The draft auto-persists to localStorage (metadata only, plus current phase); the photo blob stays in memory. The chooser surfaces a "Resume hosting?" banner when a non-terminal draft exists.

   **The roster reaches the lobby however the run started.** `POST /sessions` seats only the host, so every other player needs an explicit participant row before anyone else can see them — and since migration 053 keys live scores by participant, a player without one has *no column at all* on a spectator's screen, not merely no name. That row used to be pushed only by `_addPlayer`, one player at a time, plus a bulk `_syncRosterToLobby()` on two paths that both required the lobby to have been *replaced*. A run that arrived already holding a roster therefore never pushed it: `_ensureLobbyOpen` guards its bulk sync on `priorCode`, which is null on a fresh draft, so **Another Round** on the Play tab (`log-play-view._anotherRound`, which seeds the whole roster from the last play) minted a lobby containing one row. Spectators watched a six-player game as a one-column grid with nothing in it. Four things close that now: a fresh mint pushes the roster it was born holding; `_syncRosterToLobby()` awaits `_lobbyReady()` instead of bailing when the code hasn't landed yet, and is single-flight so the poll, the mint and the phase advance share one batch; the Gather poll re-pushes anyone still missing a row (bounded by `ROSTER_RECONCILE_MAX`, refilled whenever the pending set changes size, because `_withLobby` swallows every failure that isn't a 404/410 and a dropped POST would otherwise cost that player the whole game); and `_advancePhase` flushes the roster **before** the gather→play PATCH, because `bgb_add_participant` is Gather-only and answers `roster_locked` afterwards. `POST /participants` returns the whole bundle, so each push adopts its own `participant_id` immediately rather than waiting up to 2s for the poll to match it back by name, and the grid is republished once the phase reaches `play` so cells typed under a late-arriving id still reach the table. Stale ids are cleared on entry when the run's code has changed — deliberately *not* in `_resetRunState()`, which also runs on a plain refresh, where a host who reloads mid-Play holds ids that are still valid against a roster that is now locked. `_onLobbyReplaced` re-adopts the host's own row from the replacement bundle for the same reason: it clears every id, `_syncRosterToLobby` skips the host by design, and mid-Play the Gather poll is disarmed, so the host's own column would otherwise stop streaming.

   **The lobby is a nice-to-have; recording the play is not.** Nothing about the session code can stop the host from playing and saving — the cascade runs off the draft, and Save falls back to `POST /plays` when there is no usable code. Every `/sessions/{code}` write goes through `_withLobby()`, which on a *definitive* dead-lobby answer (404/410/403/409, and the 400 for a transition out of a terminal session) drops the lobby, mints a replacement and retries once; a blip (offline, 5xx) is left alone, because minting abandons the host's other open sessions and reacting to a hiccup would kill a live one. Healing is single-flight (`_healLobby`) — `_syncRosterToLobby` fails N writes at once, and without it each would mint a session that abandoned the one before it. When the code does change mid-run, `_onLobbyReplaced` clears the now-dangling `participant_id`s, re-pushes the roster, restarts live scores, and the invite card says *"New code — share it again"* for a few seconds. No toast, no modal: the swap can happen while the host is typing in the scoring grid.

   `PlayFlowView` is a singleton, so `onMount` drops `_lobby` unless it still matches the draft's (or the URL's) code — `_resetRunState()`. Without that a finished session's code survived into the next one: `_lobbyReady()` short-circuits on `_liveLobbyCode()`, so `_ensureLobbyOpen()` never re-ran, the invite card showed a code nobody could join, and Continue bounced off a 404 with the phase rolled back. `_advancePhase` no longer rolls back or reports at all — the local phase is the truth the host is looking at and the lobby only mirrors it.

   **Recording a play offline.** This is the *only* place in the app where being offline is a concept the user is told about, and the scope is deliberate: it is the one flow that genuinely changes. The same three screens with the entire lobby subtracted — no `POST /sessions`, no code, no 2s poll, no Realtime, no phase PATCH, no photo. All of that exists to serve joiners, and there can't be any without a server. What remains already ran locally: the game and player picker sheets paint from `bgbCache` (`game.recent` / `buddy:all`, warmed by `/bootstrap` at 24h fresh / 7d stale), the draft lives in localStorage, and Save hands the play to `domain/outbox.js` instead of the API. The host is told two things and no others — **the play saves to this device and uploads next time you're online**, and **scores won't sync live** — in exactly two places: the Gather invite card (`_renderInviteCard`) and the Play step's game-info strip (`widgets/game-info-bar.js`, `state: "offline"`). Both sit in the slot the session code would have occupied, so the notice is where the missing thing was.
   - **Everywhere else there is no offline mode at all.** `domain/net.js` is internal truth, not something the app renders. There is no banner, no switch, and nothing that disables itself or hides because the latch is set — that was the old design, and it answered questions nobody had asked and was wrong every time the latch was stale. Instead **every action is attempted**, and one that turns out to need the network says so, naming the action: `helpers.js#notifyRequestError(err, action)` → *"You're offline — joining a game needs a connection."* Screens holding cached data keep showing it and say nothing, because a cached feed is an answer and a toast on top of it is noise. `api.js#_fetch` short-circuits while the latch is set, throwing the exact shape a real network rejection throws, so the failure is instant instead of 15 seconds late and every call site still handles one path rather than two. The one throttled exception is the game picker, where every keystroke is a search: it says it once per open, not once per row.
   - **Entering — entirely automatic, never chosen.** `domain/net.js` (`window.BgbNet`) is the single source of truth. Two signals decide: `navigator.onLine === false`, and **two** consecutive `fetch` network failures (two, not one — a single request can fail for reasons unrelated to the link, and flipping the whole app on that is worse than the problem). A completed HTTP response outranks both: it is direct proof of reachability, so it overrides a stale `navigator.onLine === false`, which would otherwise strand the app with no way out since every probe would be judged by the flag it was trying to correct. The Play tab's cards are identical online and offline — only the Host card's copy changes. `PlayFlowView` latches the answer once at mount so its guards can't disagree mid-cascade; **Save is the one place that re-checks**, so a host who walked back into signal gets a live write.
   - **Every request has a deadline** (`domain/api.js`): 15s for JSON, 60s for a photo upload, with one automatic retry for a stalled `GET` on a fresh connection. A dead network *rejects* and the app recovers; a stalled request never settles at all, and no browser imposes a timeout worth waiting for — so one stalled first-paint call used to be the whole app, hanging on a loader with no error and no retry (reported from an iPhone's first launch of the freshly-installed PWA). A timeout is normalized into the same shape as a network error (`err.offline`, `err.status = 0`, plus `err.timeout`) and counts as one strike toward offline mode: a link on which requests never complete is offline as far as this app is concerned, and the outbox's `client_key` de-duplicates a write that may in fact have landed.
   - **Leaving.** Four paths, all converging on `BgbNet._publish()`'s offline→online edge, which is also the single place the outbox is drained: the browser's `online` event, any ordinary request succeeding, the backing-off auto-probe ladder (5s → 60s, only while the page is visible), and **any request the short-circuit blocks**, which kicks a probe of its own. That last one is what replaced the offline banner's *Try again* button: with the banner gone, the user's own retry tap is the active probe, so a first tap reports and a second one goes through if the link really is back. It is throttled to the ladder's own first rung so a background poller that forgot to stand itself down can't turn it into a continuous probe. The probe hits `GET /health` (unauthenticated, and mandated on every project by `.claude/rules/backend-python.md`, so it can't fail for a reason that isn't connectivity) and passes `allowWhileOffline` so it isn't short-circuited by the very latch it exists to clear; any status counts as reachable, since a 500 still proves we got there.
     - **Known gap:** on a connection that resolves and then times out (captive portal, one bar), auto-detection has to wait for two requests to actually fail, so the host sits through those timeouts before the app flips. Narrower than it was: until the latch sets, the cost is those two requests rather than a whole app painted as offline. A per-request timeout would close it, but not a blanket one — a photo upload on bad mobile upstream can legitimately run long.
   - **Uploading.** `domain/outbox.js` (`window.Outbox`) queues finished plays in `localStorage['bgb_outbox_v1']` — deliberately NOT a `bgbCache` namespace, which evicts its oldest 25% under quota pressure. Each entry carries a `client_key` UUID and the account that recorded it (a shared device must never file one user's play into another's history). `flush()` runs on boot once a profile load reaches the server, on the `online` event, and on the debounced tab-focus refresh. A network failure stops the loop with everything intact; a definitive 4xx parks that one entry as `failed` so a bad play can't wedge the queue behind it, surfaced in Settings → Pending uploads for manual discard. The queue is also where a *live* write goes when it fails, not just an offline one — see the host's Save above. When a flush lands anything it re-pulls the feed's first page and dispatches `plays-uploaded` carrying it, so a feed the user is sitting on splices the new play in rather than showing it only on the next mount.
   - **What fails, and how each one says so.** Joining (the lobby is server-side; the code field and Join button stay live and a tap toasts), signing in (the auth screen's own error line, since Supabase Auth carries none of `api.js`'s error normalisation and the message has to outlast a toast), BGG search/import, and live scores and photos inside the cascade (the blob is never persisted, so a queued play can't carry one — said up front on Settle Up, because the host would otherwise attach a photo that quietly never reaches the play). Picking a game degrades rather than fails: `PlayCreate.game_id` is required and the catalog can't be searched, so a failed `/search` falls back to the device pool — `game.recent` plus every warmed `game.bundle`, i.e. the user's whole owned collection — which is what the picker paints provisionally on every keystroke anyway. The reference guide keeps working: its chapter and template reads take the full stale window unconditionally (`Chapter.cachedMyChapters(..., { stale: true })`), because a guide cached yesterday beats an empty scroll at the table, while the *freshness check* behind `prefetchMyChapters` deliberately does not — a stale entry must not look like a reason to skip the refresh that would replace it.
   - **Cold start.** `web/sw.js` precaches the app shell so BgB opens from a home-screen icon with no signal at all; without it the feature would only work for people who left the tab open. See Active Development Notes.
4. **Game Search** (search pill on Feed/Profile): single ranked list — collection hits first, then DB matches. A "Search BoardGameGeek for more" button appends BGG hits on demand. **Expansions never appear here** — base games only, on every source. They live in the base game's Expansions section instead.
4b. **Profile → Achievements** (`/profile/achievements`): twenty-one medallion badges of the BoardgameBuddy character, grouped into At the table (10 / 100 / 300 plays logged, a two-player-only game, and a five-player table), On the road (plays in 2 countries, plays on 2 continents, plays in 5 countries — from `plays.country_code`, which the client resolves from the device timezone, so these start at zero for everybody and fill forwards; a country with no continent in `boardgamebuddy_countries` still counts toward the country tiers), Victories (10 / 100 / 300 wins), The reference guide (1 / 10 / 50 chapters kept, a chapter of yours that someone else keeps, a play you recorded on a custom scoring grid, and a scoring grid of yours that 5 other players keep — the last of those is a MAX over your own grids rather than a sum, so "Gold Standard" means one grid everybody uses) and Making it yours (first buddy, notes on a logged play, the BGG link, the app installed to a home screen). Every badge but one is derived from data the app already writes; the install is reported by the web app itself, because an installed PWA is indistinguishable from a browser tab server-side. Earned badges are **permanent** — the unlock row is what `earned` reads, so deleting a play later does not take the badge back. Each group is one horizontally-scrolling rail, ordered done → in progress → not started. Locked badges keep their art (desaturated) and print what they still want; tapping any badge opens its detail sheet, which shows the same grey medallion plus the badge's flavour line and what it takes to earn it. **Earning a badge mid-session pops an "Achievement unlocked!" polaroid** (`ui/polaroid-popup.js#achievement`, queued by `ui/achievement-popup.js`): the medallion as the photo, the name and flavour line under it, and a **See my achievements** CTA that jumps straight to the spoke. The writes that can move a badge schedule the check (`Achievements.invalidate` → `scheduleUnlockCheck`, debounced 1.5s) rather than anything polling. The queue waits for a clear screen before showing anything — the commonest way to earn a badge is finishing a game, which is the one moment the app is already showing the "Well played!" wrap-up card, and `PolaroidPopup` is a singleton — and it shows several unlocks one at a time with a "2 of 3" counter. Nothing pops while the user is already on the Achievements spoke.
5. **Game Detail** (tap any game card): box art hero, status pill (a labelled `--lg` variant of the app-wide status tag — tapping it opens the same bottom-sheet radio group every other surface opens, not a cycling toggle), Log a Play button, BGG + Rulebook links, Expansions section, a rolled-up parchment **Reference Guide scroll** (tap either roll to open/close), and recent plays. The scroll is per-user per-game and starts empty; tap **Add a chapter** at the bottom to either Create a new one or Browse the community pool.

**Add games** (the `+ Add` on the Collection spoke, `/games/add`): the whole BgB catalog as one alphabetical scroll, 30 rows a batch behind the shared scroll sentinel. The back row, an **"Add to:"** label with the Collection / Wishlist pills, and the search box are all pinned to the top of the screen — the label is the screen's whole explanation, and the shelf the pills select is what every row's + writes to, so neither may scroll away from a list this long. Each row is a game tile that opens the game page, with a quick action beside it: **+** puts the game on the active shelf, **✓** means it is already there and takes it off. A game sitting on the *other* shelf (or one you've only played) says so in a chip, and the same tap moves it — `POST /collection` upserts on (user, game), so wishlist → owned is one tap, not a remove and an add. The Collection ↔ Wishlist toggle at the top retargets every button without a single request. A search box narrows the catalog server-side; below it, **Import from BoardGameGeek** opens the import sheet for the one case a catalog scroll can't cover — a game BgB has never imported.

**Import from BoardGameGeek** (`widgets/bgg-import-sheet.js`) is a bottom sheet, and it **opens on the search you already ran**: reaching that button means the catalog came up empty on it — the button says so — so the query comes along, prefilled and already running, and the sheet lands showing BGG's answer rather than an empty box. Reopening on an unchanged query keeps what is on screen instead of spending a second round trip; a changed one, or a query the last search came up empty on, re-runs. Otherwise the search in it is an explicit act rather than a keystroke: hitting **Search** blurs the field, so the software keyboard collapses and the panel grows into the space it gives back — results land in a list that is nearly the whole screen. The box takes a **title, a BGG id, or a pasted boardgamegeek.com link** — the number off a shelf label or a forum post reaches the game directly, which BGG's own name-matching search cannot do. Every row prints its `#id` beside the year, which is also what makes a numeric search legible: search `1830` and the game with that id comes back alongside the game with that name. The row's second line carries only what its button does not already say — the year, the id, `Expansion`, and then either why an import failed or which shelf it landed on.

**Expansions appear here, ranked below base games** rather than excluded as they are everywhere else. This is the one screen whose job is reaching what BgB doesn't have, and an expansion is one of those things; importing one records its `base_game_bgg_id` exactly as the dedicated expansion import does, so it lands under its base game. It has no step two — expansions are never top-level shelf entries — so the row stops at **In library**.

The list is **windowed at 25 rows a batch**, revealed on scroll with a count line underneath (`Showing 25 of 412`). Everything is already in memory, so a reveal is a synchronous append with no request behind it — an append rather than a repaint, so a row mid-import keeps its animation and the scroll position holds. `ui/infinite-scroll.js` is deliberately not used: it observes against the viewport, and this list scrolls inside a fixed panel. Each result carries one button, and it names which of two steps it is. **Import** pulls the game into the *shared library* and stops there; the row then offers **Add to collection** (or wishlist, whichever shelf you came from) as a second, separate tap. Importing has never put a game on your shelf since — looking up whether BgB has something is not the same act as owning it.

An import is `domain/bgg-import.js`'s, not the sheet's: it keeps running when the sheet is closed, and `ui/bgg-import-toast.js` pops a notification when it lands — carrying that same **Add to collection** button, so step two is still reachable from wherever you have got to. While a job is on the wire its row sweeps a progress bar along its bottom edge, because a BGG fetch takes seconds of BGG's own throttling and a static "Importing…" reads as a hang.

**Expansions section.** Rendered on every base game — on the Game Detail page (a reel of expansion polaroids) and on the host's Gather card (a collapsible toggle list). The Gather list caps at five visible rows and scrolls, with a sliver of the sixth showing so it reads as scrollable; past five rows a client-side filter field appears above it (with a × to clear), matching the displayed label or the stored full name so typing the base game's name still hits. Import expansions sits *below* the scroll box, so it stays reachable however far down the list you are. Both carry an **Import expansions** button, and it stays available when nothing is imported yet. It opens `widgets/import-expansions-modal.js`, which lists the expansions BoardGameGeek links to this game that BgB doesn't have (`GET /games/{id}/expansions/available`); each row's name has the base game's name stripped off the front, and a **+** imports it into the catalog and pins it to this base game. A filter field above the list narrows it by name — the whole list arrives in one response, so filtering is client-side (no debounce, no second request) and matches both the displayed name and BGG's full name, so typing the base game's name still hits. Rows arrive most-owned-on-BGG first and carry an owner-count chip so that order is legible; the client never re-sorts (filtering preserves it). Rows with no count, and rows nobody owns, sit at the tail without a chip. Escape backs out of the filter before it closes the popup. Import is catalog-only — it doesn't touch the caller's collection. On the Game Detail page the new expansion appears in the reel as soon as the import returns — the endpoint answers with the finished `ExpansionListItem`, so the reel takes it directly (name-ordered, matching the bundle RPC) and only that section repaints, with a forced bundle refetch reconciling in the background. Since expansions are hidden from search, this popup is the only way one enters the catalog, so the base game has to be imported first.

**Expansion count badge.** Collection tiles carry a `git-fork N` chip counting every expansion **the catalog holds** for that base game — the same number as the game page's "Expansions (N)" heading, tooltip "N expansions in Boardgame Buddy". It used to count only expansions the viewer *owned*, which read as zero for a game with eleven of them, since importing is catalog-only. The count rides on `game.expansion_count`, which `bgb_collection_shelf` computes in SQL — so the badge is correct on the first cached paint. (It previously came from `/collection/grid` only, and the profile-bundle seed doesn't compute it, so the badge used to pop in when the grid fetch landed.) Feed rails still show the owned count (their rows come from `bgb_hot_games`, which doesn't carry the total) — their tooltip says "owned", so the two stay truthful.

**Expansion labels drop the base game's name** wherever the base game is already the surrounding context: the Game Detail reel, the host's Gather picker, the reference guide's expansion chips, and a play's expansion list. "Carcassonne: Abbey & Mayor" reads as "Abbey & Mayor" there. This is display-only via `stripBaseGameName()` in `web/helpers.js` (the frontend twin of the backend's `_strip_base_prefix` — keep the pair in sync); the stored name is untouched, the full name stays on the element's `title` and on the `gameName` navigation param, and every other surface — the expansion's own page, collection, search, feed, plays — shows it in full.
6. **Reference guide chapter add**: full-screen view. **Browse** searches the per-game pool (sorted by popularity, tap + to add); each row also carries the actions its viewer is entitled to: **Edit** and **Delete** for the chapter's creator (Delete for an admin too, matching `DELETE /chapters/{id}`, and gated behind the destructive confirm), **Report** for everybody else. **Create** is a three-step wizard sharing one fixed keyboard-safe shell, with a step counter + segment bar (`web/ui/wizard-progress.js`, shared with the play importer) above the body and a two-button footer below it:
   1. **Pick type** — the seven chapter types as 56px rows, plus the "Save to" expansion-target selector when expansions are in scope. **Scoring Grid Template** is the first row: the list is ordered by the lookup table's `display_order` and the grid type is seeded at 5, above Setup's 10, so the thing you reach for mid-game leads the list with no client-side special-casing. There is no second question underneath — the layout follows from the type, 1:1, derived in `_pickType`. Continue reads "Pick a type" and stays disabled until one is chosen. Cancel returns to Browse.
   2. **Head start (optional)** — an optional free-text focus prompt (≤500 chars) and nothing else in the body: the step's two exits are its footer, **Skip** and **Generate**. Generate jumps to step 3 on success; a failure keeps the user here with the error and the prompt intact. Back from step 3 preserves the prompt, so tweak-and-regenerate is two taps. There is no footer Back — the picked type shows as a chip with a **Change** link to step 1, and the device back gesture still walks the steps.
   3. **Edit** — title, Write/Preview toggle and the markdown editor. The chosen type shows as a read-only chip with a **Change** link back to step 1. The toolbar's trailing group holds the two document-level actions: **Import a file** and the authoring guide. Import opens a bottom sheet (`web/widgets/chapter-import-sheet.js`) that takes a `.md` or `.txt` file and drops it straight into the editor — a leading `# Heading` becomes the title, the rest becomes the body. Overwriting an already-drafted body — by Generate or by Import — goes through the project's `PolaroidPopup.confirm()` first.

   Steps 1 and 2 are pure-function bodies in `web/widgets/chapter-wizard-steps.js`; step 3 stays in the view because its toolbar reads and writes the live textarea selection. The device back button walks the steps rather than popping the view (one `ui/back-guard.js` guard for the whole wizard, re-armed from its own close).

   **Edit does not enter the wizard**: `mode=edit` and the browse-row Edit both open step 3 directly, with no step bar and with the horizontal type pill scroller instead of the read-only chip — the chapter already has a type and a body, and re-drafting over it is not what Edit is for.

   **Scoring grids** (`layout='scoring_grid'`, migration 018) replace step 3's markdown editor with a row list (`web/widgets/scoring-template-editor.js`): one card per scoring category, each a *Row Name* field, a colour chip, reorder chevrons and a remove ×, over a live preview rendered by `window.renderRoundGrid` itself so the author's picture and what a scorer sees cannot disagree.

   **A grid has no title field, and no name of its own.** The backend derives one from the game (`services/chapter_grid.grid_title` — "Everdell score sheet") on create *and* on every edit, so a renamed game re-titles its grids and a grid authored before the field was retired is normalised the next time it is saved. Naming was the wrong question: a grid belongs to one game, a player keeps at most one per game, and the pool already sorts by `popularity DESC` and prints the author under every row — which is what a reader actually chooses on. `ChapterCreate.title` is therefore optional for (and only for) a grid; a text chapter still 422s without one. The picker sheet leads its rows with **whose** grid it is (*Your grid* / *Dan's grid*) rather than with a title every grid for that game would share.

   **The colour picker is a disclosure, not a permanent radiogroup.** The ten swatches used to sit open under every row, costing 52px each — more than a phone screen of them on a full twenty-four-row grid, for a decision each row is done making after one tap. Now the row carries the chosen swatch as a chip in its header; tapping the chip opens the 5×2 picker under that row, and picking a colour folds it away again. A row added by hand (or the first row a new grid is seeded with) opens on the picker, because it has no colour yet. At most one picker is open at a time, and the open index lives on the *view* rather than inside the row objects — those get posted to the server.

   **Each row takes an optional description** — how that row is scored, in the author's words, up to 200 characters (`ScoringRow.note`, which the model has carried since 018 with nothing authoring it). It is a template feature and never a play one: it does not print in the row header, does not show in the guide's own listing, and reaches a scorer only through an **info button on the row's label** in the scoring grid, which opens the text in `PolaroidPopup.alert`. That is why the whole label cell is the button rather than the glyph — a grid row is ~36px tall, so nothing inside one can carry a 44px target vertically, and width is the only dimension there is any to buy back. In the editor the description is one 28px line under the label in all three of its states (absent, written, being written), so a grid whose rows need no explanation pays almost nothing for the feature. A grid **skips step 2 in both directions** and its bar reads 2 steps rather than 3 — that step drafts markdown against `CHAPTER_AUTHORING_GUIDE`, and a grid is six labels the author already knows, so `services/chapter_ai.py` and its sync obligation stay out of this entirely. The markdown toolbar, the Write/Preview toggle and Import do not render. The type is fixed at `scoring_grid` and read-only even in Edit: a grid stranded under another type is a 400 from the backend's `chapter_grid.validate_layout_pairing`, which checks the pairing in both directions. Edit's type scroller leaves the grid type out for the mirror reason — converting prose into a grid would throw the prose away, and PATCH cannot clear a `grid` to make the trip back.

   **The round-label column pins, like the header row.** A six-player table is wider than a phone, so scrolling right to reach the last column used to carry the row labels off the left edge — a screen of bare digits with nothing saying which row is Prosperity and which is Events. It is now `position: sticky; left: 0`, the horizontal half of what `.scoring-table thead th` already did vertically. Three cells are sticky on **two** axes at once (the corner cell, the totals band's label, and — where they meet — nothing else), and equal-`z` cells settle on document order, which is the wrong answer for every corner; so the table carries one documented z ladder: score cells `< 2` round labels `< 3` totals band `< 4` totals label `< 5` column headers `< 6` corner cell. Every pinned cell also has to be **opaque**, which is why `.scoring-table tbody th` moved its `opacity: 0.7` onto the ink — a faded sticky cell lets the score columns ghost through the label sliding under it. That repair was already written twice (the totals label, the tinted template row) for exactly this reason; it now lives once, in the base rule. The column rule at the pinned edge moved from column 2's `border-left` to column 1's `border-right` so it travels with the column it belongs to — same pixels, and `nth-child(n + 3)` picks up where `:not(:first-child)` left off.

   **Adopting one changes the scoring table.** With exactly one scoring grid in the viewer's guide for the game, the Play step's grid opens already labelled and tinted, its rows locked (no remove ×) while **+ Round** still appends removable extras below them and keeps absolute numbering (R7 under a six-row template — the number a row shows is its `round_index`, which is the key live scores are stored under). With two or more, nothing auto-applies and a bottom sheet (`web/widgets/scoring-template-sheet.js`) picks *which*. Auto-apply is refused on a grid that already holds numbers, so a resumed draft is never restructured under the host. The play keeps a **snapshot** of the rows it used, so the play-detail popup and the spectator's mirror render the same labels forever, independent of what later happens to the chapter.

   **The template is a switch, not a one-way Clear.** The strip above the grid names this game's template and carries an on/off switch (`web/ui/switch.js`); *Change* joins it only when the guide offers two or more. Off is immediate and non-destructive — the rows and the scores stay exactly where they are, only the labels go — and on goes through the same confirm a Change does, because relabelling rows somebody has already scored into is the same event either way. It replaced a **Clear** link that was a one-way door: with one adopted grid, clearing removed the only control on the strip, so the labels could not be put back for the rest of the game, and a template auto-apply had declined (a resumed draft with numbers on it) rendered no strip at all — the same dead end reached from the other side. Flipping back on restores the grid that was last on rather than a guess; where there is no such history and the guide offers several, the switch opens the picker instead of choosing for the host, which is the guess auto-apply already refuses to make. Off is a **persisted field of the draft** (`scoringTemplateOff`), not the absence of a template: `scoringTemplate === null` alone cannot tell "nothing chosen yet" from "the host took it off", and reading it as the first is how a guide reload used to put the grid back on a host who had just removed it.

   **A grid is not a chapter of the guide.** It is stored as one — its own `chapter_type`, its own pool row, adopted and dropped like any other — but the reference-guide scroll does not draw it (`web/widgets/reference-guide-scroll.js#isScoringGrid`). It is the shape of the scorepad, read in the table it labels, and rendered as a section it was a heading and a table duplicating the grid two cards up the same screen — at `display_order` 5, the *first* section, pushing the rules somebody did open the scroll for below it. The rows still load on the same fetch (the play screen is fed from it, via `guide-chapters-loaded`), and Browse is still where a grid is added, edited, reported and dropped. The scroll's empty state is what a guide holding nothing but grids now shows.

   **Templates you haven't added announce themselves.** When the pool holds scoring grids the viewer has not adopted, the parchment scroll shows *"…custom scoring grids are available — tap to add"* in `.scroll-panel__peek`, the strip that stays visible with the scroll **rolled up** — which is how the Play screen opens it — and again inside the empty state, which renders no peek at all and is exactly the case the nudge is most for. Tapping lands in Browse filtered to Scoring Grid Template. Dismissal is stored as the set of chapter ids turned down, per game, not a boolean, so a grid published later can say so once more.

   **And on the Play step they ask outright.** A host with **no** scoring grid in their guide for a game that **has** some gets a sheet on arriving at the Play step: *Score on a shared grid?*, **the three most players keep**, each drawing its **real grid** through the same `ScoringTemplateEditor.preview` the author's editor and the guide use — because "6 rows · Everdell" is not enough to pick a scorepad by with your friends waiting. Every grid for one game carries the same derived title, so a card leads with **whose** it is and how many guides hold it: the author says which one, the count says which one the table usually uses, and the count is also the sort key, so it rides beside the name it is ranking rather than in the meta line under it (absent at zero — a grid nobody keeps is not a fact worth a chip). The pool already arrives `popularity DESC`, but the sheet sorts again before it takes three: "the three most players keep" has to be true of the three that survive the slice, not of whatever order the caller happened to hand over. Picking one puts it on the table **and** adds it to the reference guide, so next time it is simply there and auto-apply handles it; the table is painted first and does not wait on the write, because the draft carries a complete snapshot of the rows and only the *next* play depends on the adoption landing. *Continue without* is the other answer, and it is an answer: it writes the ids it was shown into the same dismissal store the scroll's notice reads, so the notice two cards further down the same screen goes quiet with it (`domain/chapter.js#dismissTemplates` — one store, two surfaces, or the host answers the same question twice). Backdrop, Escape and the device back gesture mean *not now* instead and record nothing.

   It is the same widget as the picker sheet with a second mode (`web/widgets/scoring-template-sheet.js#offer`) — one grid object, one CSS family — but its own panel, because "which of mine" is a list of one-line rows and "adopt one of these" cannot be answered without seeing the rows. Each candidate is a card with a real button inside it rather than one big button, since a row carrying a description renders a note button of its own inside the preview and a button cannot contain a button. Long grids are cropped in **JS** at five rows with a *+N more rows* line, not clamped in CSS: a height clamp cannot tell a preview it cut short from one that simply fits.

   **Every guard on the offer is "the host has not already answered this".** A grid in their guide, a template on the draft, the scoring bar's switch deliberately off (`scoringTemplateOff`), rounds or scores already on the table (the same bar auto-apply refuses to cross — restructuring a table mid-game is worse than never offering), a game already asked this mount, an id already turned down, or offline. It runs on the Play step and not on Gather: Gather is a roster, and the scorepad is not a question worth interrupting it with. Neither half of the question is fetched here — `views/play-flow-view.js` gets the guide from `guide-chapters-loaded` and the pool from `guide-templates-loaded`, both announced by the reference-guide scroll that mounts on the same screen in the same frame, so nothing on the Play step doubles a request the guide has already made.
7. **Profile** (own): Strava-style stats strip (plays / games / wins / hours), collection grid, recent plays. Admin users get an "Admin tools" link.
8. **Profile (other user)**: fully public — same stats strip + collection grid for any account. The header surfaces buddy-state ("Add buddy" / "Accept request" / "Request sent" / "Buddies").
9. **Buddies**: accepted mutual edges, plus incoming and outgoing pending requests. Search-by-display-name to send a new request.

   **Ghost account claims — "is this you?" (migration 070).** A ghost player is a name a buddy typed into a play they logged; until now the person behind it had no way to say so, because `bgb_link_ghost` only ever ran owner→ghost. The claimant now asks and the owner approves, and approving performs that same merge. Three sections on this screen (all `ui/ghost-claim-suggestions.js`, so the 1200-line view stays out of it) and one sheet reachable from a play. **Is this you?** lists ghosts on the viewer's *accepted buddies'* rosters whose name resembles theirs — "Lachie Brown's ghost **Davo** · 12 plays · last 4 Aug 2026" — with Claim and Not me. **Link requests** is the other side: "Julia Reyes asked to link **Davo** · on 12 plays of yours", Accept / Decline. **Accept is confirmed first** — `PolaroidPopup.confirm()`, the project's one confirm surface, asking "Move 12 plays to Julia Reyes?" and spelling out that undoing it means *they* remove themselves from each play by hand. The dialog leads with the figure because that is the part the owner has to weigh, and Accept sits a thumb's width from Decline in a list they are skimming; a row seeded from the profile bundle carries no count, so the tap fetches `GET /ghost-claims` before opening rather than saying "your plays". Confirming merges and toasts how many plays moved; it also calls `Play.invalidateDeps()`, because the plays themselves changed hands. Declining costs the claimant a strike — they may ask once more, and a second decline is final; withdrawing your own ask (**Link requests sent**) is a delete, not a decline, and costs nothing.

   The same claim is reachable from a play's player list — the back of a polaroid and the play-detail popup (`widgets/ghost-claim-sheet.js`, opened by `ui/player-row-action.js`). Those ghost rows were inert before, which made the one row a person most needs to tap do nothing. **That path deliberately does no name matching:** the suggestion list is the app volunteering a guess and stays conservative, but a tap on a specific row is not something the matcher gets to veto, and a nickname is exactly what it misses. The claim is withheld only where it could not succeed — the viewer's own roster, or a play they already sit on, which would seat one person twice.

   The count of incoming claims rides on `/profile/bundle` (migration 071) rather than its own fetch, so the Profile tab's dot and the Buddies card's count are right on first paint. It is a **third source on the same dot**, not a third dot; the hub's Buddies card sums it with buddy requests, because both are answered on the one screen it opens.

   **Mutations here patch in place; they do not restructure the lists.** A tap on a list control repaints every control bound to that person (`data-rel-control` + `_syncRelationControls`) and nothing else — the person does not leave the suggestion rail, no section appears or disappears, and nothing re-sorts. The lists re-form on the next *continuity break*: a mount, a page turn, a search, or a confirm dialog. That is the timing half of `.claude/rules/web-frontend.md`'s surgical-repaint rule, which exempts membership changes by scope but says nothing about when: a full repaint in the tap's own frame slid the rail sideways and the next tap sent an invite to the wrong person. Because the row stays put, its control shows a **verb** for what this session did — Sent / Accepted / Declined / Cancelled — never a state like "Buddies", which would contradict the heading above it. `_unfriend` is the one that restructures immediately, and that follows from the rule: its confirm dialog has already broken continuity.
10. **Import plays** (Settings → Import plays, `/settings/import-plays`): six counted steps behind one pinned counter and segment bar. **1 Source** — paste a note, or read a `.txt`/`.md`/`.csv` in with `FileReader` (nothing is uploaded); the read fills the textarea so what was read is still editable. **2 Details** — optional: how the note is organised, with two one-tap examples. Continue here fires the parse, the first of the two steps in this flow that block. **3 Players** — every distinct name, auto-suggested against `GET /play-partners` (exact → case-insensitive → a two-character-minimum prefix, which is what offers "Jasmine" for a note that says "Jas"); tapping a row opens `widgets/player-picker-sheet.js` in its new **single-select** mode, whose guest row is worded "Keep X as a ghost player" and is offered even when a buddy of the same name is listed. **4 Games** — every distinct game name against the catalog; an unmatched one opens `widgets/game-search-sheet.js`, and Continue names how many plays leaving it unmatched would cost. **5 Plays** — grouped into per-game subsections, each row expandable to its seats, scores, winner, date and a per-play game override; a run of identical repeats collapses into one row ("58 identical plays") because 58 rows saying the same thing is a list nobody scrolls, and the list is windowed four game-groups at a time through `ui/infinite-scroll.js`. A "Date for plays without one" control fills every play the note gave no date for; per-play dates win. **6 Import** — the summary, then the write, chunked 50 at a time behind a progress bar. Runs of indistinguishable plays are tagged with a shared `import_group_id` here (migration 005), so the feed and the plays log later show each run as **one** card rather than 58 identical polaroids; every play in the import also shares an `import_batch_id` (007) so the whole paste can be undone from Settings. Step 3 offers **You** as the first player candidate and pre-matches the viewer's own display name — `GET /play-partners` never returns the viewer, because every other caller has already seated them, and without this an import landed with the importer absent from their own history and their own wins. Step 5's run rows carry an editable **count**, so a misread tally is corrected before anything is written rather than after. Every draft play carries its own `client_key` from expansion onward, so a failed run resumes by importing again and re-writes nothing. The whole draft is saved to `localStorage` under a versioned key on every step change, so a refresh resumes; closing asks first (`PolaroidPopup.confirm`) and clears it.
11. **Import from photos** (Settings → Import plays from photos, `/settings/import-photos`): three counted steps behind the same pinned counter, sharing the notes importer's whole `.imp-*` chrome. **1 Photos** — pick up to 30 from the camera roll. Each file is opened twice: once by `domain/exif.js`, which walks the JPEG segment chain to the APP1/TIFF block and reads `DateTimeOriginal` plus the GPS IFD (the date part is taken verbatim, never through a `Date` — an EXIF timestamp is already local wall-clock time where the shutter fired, and reparsing it in the phone's current zone moves a late holiday play to the next day); and once by `preparePhotoForUpload` with the new `PHOTO_IMPORT_OPTS`, whose `alwaysReencode` defeats the fast path so the copy that reaches the bucket carries no EXIF at all. The coordinate goes to `domain/geo-grid.js` and is then dropped — it is never written to the draft and never sent anywhere. A photo with no GPS inherits the country of another photo taken the same day, which is not a guess: a lock that hadn't landed yet is the ordinary reason one shot of an evening has a tag and the next doesn't. A file with no EXIF at all (a screenshot, a chat re-encode) falls back to its modified time, and the row says so. **2 Assign** — a pager, one photo at a time, with a filmstrip above it that shows at a glance which photos still have no game. Game opens `widgets/game-search-sheet.js` and Players opens `widgets/player-picker-sheet.js` in the same multi-select mode Gather seats a table with; the seats are then winner toggles (several is a tie). **The roster starts with the importer** — every photo in a camera roll is a game they played, and since migration 023 a seatless play cannot be written at all, so without it thirty photos meant thirty trips through the picker; it is seeded when the shot is created and never again, so a photo somebody takes themselves out of stays that way and a restored draft does not re-seat them. A **guest typed on one photo is offered on the rest of the run**, at the top of the empty-query list: until the final write that name lives only in that shot's roster, and reaching it by typing it a second time is exactly how one person becomes two ghosts. Date, country (`widgets/country-picker-sheet.js`) and a note are editable per photo. **Same as the last one** copies the game and the table forward but never the date or the country — those came out of this photo's own EXIF and are the part the importer already knows better than the user does. A photo can be left unassigned; it is simply left out, and the last step names the cost. **3 Import** — the photos upload first, one at a time (thirty parallel multipart uploads on a phone is where the connection gives up), each URL memoised on its shot so a retry never re-pushes bytes; then the plays go in chunks of 50 through the same `POST /plays/import`. A photo that won't upload costs the picture, not the play. One `import_batch_id` for the run, so Settings can undo the whole thing; no `import_group_id`, because one photo of one table is never one of the indistinguishable repeats that field exists to collapse.

12. **Admin tools**: chapter-reports moderation. Each row has Resolve (no action) and Delete chapter (remove from the pool). (Reachable only when `is_admin=true`.)
